## Type signature

```python
class Action[P, R]:
    @property
    def plan(self) -> ActionPlan: ...
    def perform(self, principal: str | None, params: P) -> R: ...
```

`P` is the parameter type, `R` what the action returns. Both are held to at the call site:
`executor.execute(DepositMoneyAction, DepositParams(...))` returns a `Wallet` with no cast, and
passing the wrong parameter object is a type error rather than a runtime one.

There is no abstract base to satisfy beyond `perform`. No decorator, no registration marker,
nothing scans for it.

## Declaring an action

```python
@dataclass(frozen=True, kw_only=True)
class DepositParams:
    wallet_id: WalletId
    amount: Decimal


class DepositMoneyAction(Action[DepositParams, Wallet]):
    def __init__(self, wallets: WalletRepository, clock: Clock) -> None:
        super().__init__(clock)
        self.wallets = wallets

    def perform(self, principal: str | None, params: DepositParams) -> Wallet:
        wallet = self.wallets.get(params.wallet_id)
        return self.plan.update(wallet.deposit(params.amount))
```

Dependencies come through `__init__`, once, in the wiring. An action with no parameters is
invoked with `None`; a bare scalar is refused, because a string in the `action_params` column is
unreadable six months later.

**Nothing discovers this class.** Java marks an action `@EkbatanAction` so its DI integrations
can find and register it; here you put the instance in an `ActionRegistry` yourself:

```python
actions = (
    ActionRegistry.builder()
    .with_action(OpenWalletAction(wallets, clock))
    .with_action(DepositMoneyAction(wallets, clock))
    .build()
)
```

That is what lets `executor.execute(DepositMoneyAction, params)` take the **class** — the
registry is the map from class to constructed instance. Pass an instance directly and no registry
is needed, which is the form a test usually wants.

The registry also decides nothing about *how* the action runs. Retries and cross-shard allowance
are [`ExecutionConfiguration`](/reference/action-executor/), set as the executor's default or on
a single `execute(...)` call — never on the action class, so an action's behaviour cannot depend
on where it was declared.

## The two-phase lifecycle

```
executor.execute(DepositMoneyAction, params)
         │
         ▼
┌─ Phase 1 — perform() — no transaction ───────────────────┐
│  read · build · attach events · plan.add / plan.update   │
└──────────────────────────────────────────────────────────┘
         │
         ▼
┌─ Phase 2 — the executor — one atomic transaction ────────┐
│  1. group the plan's changes by ShardIdentifier          │
│  2. open the transaction on that shard                   │
│       repository writes   → domain rows                  │
│       outbox writes       → events rows                  │
│  3. commit                                               │
└──────────────────────────────────────────────────────────┘
```

Phase one touches no transaction. Phase two is the only place one is opened, and it always wraps
every staged change together with the matching event rows. **A partial write is not
expressible** — there is no code path that writes a domain row without its outbox row, because
they are the same statement batch in the same transaction.

The grouping step in phase two is what makes sharding invisible to phase one: `perform()` stages
objects, and only afterwards does the executor work out which database each one belongs to. An
action reads the same whether there is one database or eight.

Each attempt gets a **fresh plan**. A retry re-runs phase one from the top rather than
re-committing a stale plan, so a half-staged attempt cannot leak into the next one.

## Methods

### `plan`

The accumulator for this invocation. A property rather than a field: it resolves the
`ContextVar` bound for the duration of `perform()`, so one shared action instance serves every
concurrent invocation safely. See [ActionPlan](/reference/action-plan/).

Ambient because it cannot be anything else. A repository call three frames down stages onto the
same plan without ever mentioning it, and threading it through every signature between would put
framework plumbing in the middle of domain code.

### `clock`

A constructor field, set by `super().__init__(clock)` and **required**. Use it for anything
time-derived inside `perform()`; an action calling `datetime.now()` directly is one that cannot
be tested at a fixed instant, and whose timestamps disagree with the row it is writing.

Pass **the executor's clock**. The executor checks this at construction and refuses an action
holding a different one, naming it:

```
DepositMoneyAction was built with a different clock than this ActionExecutor. Pass the
executor's clock to every action it runs - a unit of work reading one clock while its rows
are stamped from another cannot be tested at a fixed instant.
```

Java cannot make that check: a DI container hands the same `Clock` bean to the action and to the
executor, so the question never arises. Here the two are wired by hand, which is where they can
be wired differently.

### `perform(principal, params)`

Your logic. Read what you need, build the new immutable objects, stage them, return the result.
It must be free of side effects you would not want repeated — a retry replays it whole.

`principal` is whoever the caller named — `executor.execute(action, params, principal="ada")` —
and `None` when nobody did. It is a parameter rather than ambient state, as in Java: a helper
that needs it is passed it, like any other value.

It is **not persisted**. No column of [`events`](/reference/tables/events/) holds it; it reaches
the log line and the `ekbatan.action.principal` span attribute. If "who did this" has to survive,
put it in the action's parameters, which *are* stored in full.

## Actions are singletons

One instance per class, shared by every concurrent invocation, so an action must hold no mutable
instance state. What the constructor sets — repositories, the clock — is fine, because it does
not change.

The plan is the only per-invocation value that is ambient, and it lives in a `ContextVar`, which
is per-thread *and* per-async-task. Work handed to a pool does **not** inherit the binding. That
is correct rather than a limitation: fan out, join, and stage only on the thread running
`perform()`.

## Retry semantics

The default is one retry after 100 ms, on `StaleRecordError`.

```python
config = ExecutionConfiguration(
    retry_configs=(RetryConfig(on=StaleRecordError, max_retries=3, delay=0.05),)
)
executor.execute(DepositMoneyAction, params, config=config)
```

- **`max_retries` counts retries, not attempts.** `max_retries=1` runs the action twice.
- **Matching looks through the cause chain**, so a driver wrapping a conflict still matches —
  `__cause__` only, which is what Java's `getCause()` reaches. An error raised inside an
  `except` block without `from` is not followed.
- **Matching is by exact class**, as Java's is. A policy for `EkbatanError` does not catch a
  `StaleRecordError` — name the class that is thrown. Order is the only precedence rule —
  put narrow policies first.
- **A retry replays the whole action from phase one, with a fresh plan.**

`ExecutionConfiguration.no_retry()` is the policy for a unit of work whose side effects are not
safe to repeat.

## Cross-shard execution

By default an action's staged changes must all route to one shard; one that spans two raises
`CrossShardError`, naming both. Opt in for a single invocation:

```python
executor.execute(
    TransferAction,
    params,
    config=ExecutionConfiguration(allow_cross_shard=True),
)
```

The executor then opens **one transaction per shard**, each committing independently. There is no
two-phase commit — not as an omission, but because there is no atomic commit across separate
databases to have. A partial commit is the dual-write trap in another hat.

Three things happen that you would want to happen:

- **A warning is logged before the first commit**, not after the last. An action that spans
  shards and then fails partway is exactly when someone needs to know it spanned shards, and a
  warning written after the final commit is never written at all in that case.
- **A partial failure logs at `CRITICAL`**, naming which shards are committed and will not roll
  back, and which one failed. That log line is the only notice anyone gets, and it is the
  documented consequence of opting in.
- **The span is annotated** — `cross_shard`, and on failure `partial_commit_failure` with the
  committed and failed shards — so it is visible in tracing rather than only in logs.

The failure is caught as broadly as possible, deliberately. A `KeyboardInterrupt` between two
commits — a pod going away mid-action — is the realistic case, and it must not be the thing that
decides whether the alarm is raised.

Prefer opting in **per call**, where the risk is visible at the call site. If a partial commit
would need compensating, write a [saga](/learn/sagas/) instead.

## No nesting

An action must not execute another action inside `perform()`. If two things must happen
together they are one action; if one must follow the other, chain them after the commit — which
is what a [saga](/learn/sagas/) is.
