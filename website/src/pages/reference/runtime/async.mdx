## When to use it

Use it when the service is an asyncio app - FastAPI or Starlette with `async def` endpoints -
and many requests wait on the database at once. Here is the same deposit measured both ways, on
one PostgreSQL with a pool of 40 connections:

| requests in flight | sync API in a 40-thread pool | `ekbatan.aio` on asyncpg |
| ---: | --- | --- |
| 1 | 199 a second, median 4.5 ms | 128 a second, median 7.2 ms |
| 50 | 626 a second, median 75 ms | 977 a second, median 47 ms |
| 1000 | 576 a second, median 1621 ms | 874 a second, median 587 ms |

Under load, async does about one and a half times the work, and most requests wait much less.
A lone request is a little slower on asyncpg than on psycopg. The full tables, and what a short
pool timeout changes, are [below](#the-pool-is-the-cap).

How to choose between the two, and what stays the same, is on [Sync or async?](/learn/sync-or-async/).
This page has the async details: drivers, the pool, tasks, locks and event handlers.

## Install

Each database has an async extra. Install it beside the sync one:

| extra | async driver | sync driver it sits beside |
| --- | --- | --- |
| `postgres-async` | asyncpg | `postgres` - psycopg |
| `mysql-async` | aiomysql | `mysql` - PyMySQL |
| `mariadb-async` | aiomysql | `mariadb` - PyMySQL |
| `sqlite-async` | aiosqlite | none needed - sqlite3 |

```bash
uv add "ekbatan[postgres,postgres-async,migrations]"
```

Keep the sync extra. Migrations, `schemagen`, distributed jobs, and the event fan-out and
dispatch jobs are sync, and connect through the sync driver.

## What is async, and what is not

- **Async:** every class that waits on the database has an async version in `ekbatan.aio`, with
  the same name and an `Async` prefix.
- **Shared by both:** models, events, ids, the registries of actions and repositories, and config.
- **Sync, on threads:** fan-out, dispatch, jobs, migrations and `schemagen`.

`to_record` and `from_record` stay plain `def`, because mapping a row waits on nothing. The full
list, side by side, is on [Sync or async?](/learn/sync-or-async/#what-differs).

## A service, written async

The wallet deposit, async. What changes: the classes come from `ekbatan.aio`, `perform` and the
custom finder are `async def`, and every database call is awaited.

```python
from ekbatan.aio import AsyncAction, AsyncActionExecutor, AsyncDatabaseRegistry, AsyncModelRepository
from ekbatan.config_files import load_sharding_config


class WalletRepository(AsyncModelRepository[Wallet, WalletsRecord, UUID]):
    def to_record(self, wallet: Wallet) -> WalletsRecord: ...          # plain def
    def from_record(self, record: WalletsRecord) -> Wallet: ...

    async def find_all_by_owner(self, owner_id: UUID) -> list[Wallet]:
        return await self.find_all_where(WALLETS.c.owner_id == owner_id)


class WalletDepositMoneyAction(AsyncAction["WalletDepositMoneyAction.Params", Wallet]):
    def __init__(self, clock: Clock, wallet_repository: WalletRepository) -> None:
        super().__init__(clock)
        self.wallet_repository = wallet_repository

    async def perform(self, principal: str | None, params: Params) -> Wallet:
        wallet = await self.wallet_repository.get_by_id(params.wallet_id.value)
        return self.plan.update(wallet.deposit(params.amount))


registry = AsyncDatabaseRegistry.from_config(load_sharding_config("ekbatan.yaml"))
wallet_repository = WalletRepository(Wallet, WALLETS, registry, clock=clock)
executor = AsyncActionExecutor(
    namespace="example.wallet",
    registry=registry,
    repositories=[wallet_repository],
    actions=[WalletDepositMoneyAction(clock, wallet_repository)],
    clock=clock,
)

wallet = await executor.execute(None, WalletDepositMoneyAction, params)
await registry.aclose()                     # or: async with registry: ...
```

Everything is built as in the sync API, builders included: `AsyncDatabaseRegistry.builder()`
and `AsyncActionExecutor.builder()`. Each executor refuses the other kind of action when it is
built, so a sync `Action` cannot end up awaited by mistake.

## One config file, two drivers

An async service still has sync parts, such as the jobs and the event fan-out and dispatch. So
one layout file serves both. The url names the database, and each side picks its own driver:

| url in the file | sync registry connects with | async registry connects with |
| --- | --- | --- |
| `postgresql+psycopg://` or `postgresql://` | psycopg | asyncpg |
| `mysql+pymysql://` | PyMySQL | aiomysql |
| `mariadb+pymysql://` | PyMySQL | aiomysql |
| `sqlite:///path.db` | sqlite3 | aiosqlite |
| `postgresql+asyncpg://` | - | asyncpg, as written |
| `postgresql+psycopg_async://` | - | psycopg's own async mode, as written |

A url that names a sync driver, or none, connects through the database's async default. A url
that names an async driver is used as written. `async_url(config)` shows which url a config
connects to, and `ASYNC_DEFAULT_DRIVERS` holds the defaults.

psycopg's own async mode needs no extra install, since it is psycopg itself, and it reads the
same driver settings as sync psycopg. It is tested as fully as asyncpg.

## Driver settings, and UTC

`data_source_properties` - the extra settings a layout hands to the driver - reach the async
driver as given, with one exception. psycopg's settings are those of libpq, PostgreSQL's own
client library, and asyncpg does not read them. So the framework translates the ones written for
libpq:

| written for libpq | reaches asyncpg as |
| --- | --- |
| `options: -c TimeZone=UTC -c statement_timeout=5000` | `server_settings: {TimeZone: UTC, statement_timeout: "5000"}` |
| `application_name: svc` | `server_settings: {application_name: svc}` |
| `connect_timeout: 10` | `timeout: 10.0` |
| `sslmode: require` | `ssl: require` |

So the documented way to keep each session on UTC works on every driver, unchanged:

```yaml
dataSourceProperties:
  options: -c TimeZone=UTC                       # PostgreSQL, psycopg and asyncpg
  # init_command: SET time_zone = '+00:00'       # MySQL and MariaDB, PyMySQL and aiomysql
```

Checked against a database whose own default zone is Tehran: with the setting, the session
reports UTC on asyncpg and on aiomysql; without it, Tehran.

The edge cases:

- A layout that only async code reads can also use asyncpg's own spelling,
  `server_settings: {TimeZone: UTC}`.
- Anything in `options` that is not a `-c` setting is refused, and so is a setting given in two
  places.
- The error never repeats the value, because every `data_source_properties` value is treated as
  a secret.

**asyncpg is strict about time zones.** It refuses a `datetime` that carries a zone (an aware
one) for a zone-less `TIMESTAMP` column, where psycopg accepts it. The framework hands every time
to the driver as it is, so you only meet this with an aware value you pass in yourself. The
default clock's `instant()` has no zone attached and works on every driver
([What you give is what is stored](/reference/multi-database/#what-you-give-is-what-is-stored)).

## The pool is the cap

The framework sets no limit of its own on how many units of work run at once. The connection
pool is the limit. An async pool is built from the same `DataSourceConfig` as a sync one, with
the same settings: `pool_size`, `max_overflow`, `pool_timeout`, `pool_recycle`, and pre-ping - a
check that a connection still works before it is handed out. When the pool is full:

- past `pool_size + max_overflow` connections, requests queue for one;
- a request that waits longer than `pool_timeout` fails with SQLAlchemy's `TimeoutError`
  ("QueuePool limit of size 10 overflow 0 reached, connection timed out, timeout 5.00"). The
  message carries no url and no password. Answer it with a 503 and a `Retry-After` header.

Limit the requests in flight at the server too, so a burst is turned away at the door rather
than queued inside. `uvicorn --limit-concurrency 50` answers 503 itself once 50 requests are
open. Keep that number a small multiple of the pool size.

The measurements: 2000 deposits per row, a pool of 40, PostgreSQL in a local container. This is
one laptop, so read the shape, not the exact numbers. p50 is the median wait, and p99 the wait of
the slowest request in a hundred.

**`pool_timeout` 30 s, the default**

| requests in flight | sync API, 40 threads | `ekbatan.aio`, asyncpg | `ekbatan.aio`, psycopg async |
| ---: | --- | --- | --- |
| 1 | 199/s, p50 4.5 ms, p99 9.7 ms | 128/s, p50 7.2 ms, p99 15.8 ms | 196/s, p50 4.6 ms, p99 11.2 ms |
| 50 | 626/s, p50 75 ms, p99 149 ms | 977/s, p50 47 ms, p99 92 ms | 716/s, p50 65 ms, p99 141 ms |
| 200 | 581/s, p50 342 ms, p99 427 ms | 955/s, p50 123 ms, p99 786 ms | 780/s, p50 162 ms, p99 922 ms |
| 1000 | 576/s, p50 1621 ms, p99 1839 ms | 874/s, p50 587 ms, p99 2196 ms | 796/s, p50 773 ms, p99 2382 ms |

Nothing timed out. At 200 and 1000 requests the slowest one in a hundred waits longer on async:
every request starts at once and then queues at the pool, less evenly than in front of 40
threads.

**`pool_timeout` 0.5 s**

| requests in flight | sync API, 40 threads | `ekbatan.aio`, asyncpg |
| ---: | --- | --- |
| 200 | none failed; p50 317 ms, p99 375 ms | 84 of 2000 failed fast; p50 138 ms, p99 609 ms |
| 1000 | none failed; p50 1557 ms, p99 1674 ms | 967 of 2000 failed fast; p50 399 ms, p99 797 ms |

With a short timeout, overload is refused quickly instead of queued, and the requests that are
served stay fast. The sync API never waits at the pool here, because its 40 threads hold the work
back in front of it.

Pre-ping costs 1.5 to 2.5 ms per unit of work on both drivers, since each unit of work takes a
connection from the pool twice. It is on by default, as on a sync pool.

## Reads across shards run at once

A read that names no shard asks every shard **at the same time**, so it costs about one shard's
round trip rather than one per shard. These reads do it: `find_all_where`, `find_all`, `count`,
`count_where`, `exists_where`, `find_one_where`, and `find_all_by_ids` (across the shards its
ids live on).

The answer is the one the sync read gives:

- rows come back first shard first, as in sync;
- if one shard fails, the whole read fails. The reads still running on the other shards are
  cancelled, and that shard's own error is raised, with the same note naming the shard as in
  sync - e.g. `ekbatan: reading shard 1:0 (mexico) failed, so the whole read failed and the
  reads still running on the other shards were cancelled`. There are no partial results;
- `find_one_where` and `exists_where` take the answers in shard order and stop at the first
  shard that has the row, as the sync calls do. The reads after it are cancelled, so a broken
  shard after it does not fail the call. A broken shard fails the call only when every shard
  before it said "not here" - exactly when the sync call, asking one shard at a time, would have
  reached it.

`dbs()` and `readonly_dbs()` hand connections to your own code, so they work as in sync: one
shard at a time, each opened only when you reach it -
`async for shard, conn in wallet_repository.readonly_dbs():`.

## Transactions, tasks, cancellation and timeouts

The open transaction is kept in a `ContextVar` - a Python variable that holds a separate value
for each asyncio task - so two requests on one event loop never see each other's transaction.

- **Inside `perform`** no transaction is open, and each read takes a connection of its own:
  reads gathered with `asyncio.gather` run at the same time.
- **Inside one transaction** every statement uses its one connection. Statements gathered there
  take turns (SQLAlchemy queues them) and commit together: no error, and no speed-up either.
- **A cancelled task** rolls its transaction back, and the connection goes back to the pool clean.
- **`asyncio.timeout(...)`** around `await executor.execute(...)` is a cancellation: whether it
  fires during `perform` or while the transaction is open, nothing is committed.

## Keyed locks, around the unit of work

Take the lock around `await executor.execute(...)`, as on the sync side. The lock then covers
both `perform` and the commit, and the action knows nothing about it:

```python
from ekbatan.aio.locks import AsyncPostgresKeyedLockProvider

locks = AsyncPostgresKeyedLockProvider.builder().data_source(AsyncDataSource.from_config(lock_config)).build()

async with locks.acquire(f"wallet:{wallet_id}", timedelta(seconds=30)):
    wallet = await executor.execute(None, WalletDepositMoneyAction, params)

lease = await locks.try_acquire(key, max_wait=timedelta(seconds=5), max_hold=timedelta(seconds=30))
if lease is None:
    ...                                   # someone else has it: a 503 with Retry-After
async with lease:
    ...
```

There is an async provider for each sync one, on the same backend and holding the same keys:

- `AsyncPostgresKeyedLockProvider`
- `AsyncMySQLKeyedLockProvider`
- `AsyncMariaDBKeyedLockProvider`
- `AsyncRedisKeyedLockProvider`, in `ekbatan.aio.locks.redis`, on redis-py's own `redis.asyncio`

So an async service and a sync one contend for the same lock - and on Redis, so does a service
built on Ekbatan for Java ([Running beside a Java service](/reference/beside-java/#keyed-locks)).

The rules are the sync ones:

- `max_hold` bounds every hold, and the outermost hold's `max_hold` is the one that counts;
- `try_acquire` returns `None` when someone else still holds the key after `max_wait`, and
  raises `LockAcquisitionError` when the backend is broken;
- a blank key is refused;
- releasing a lease twice is allowed.

How the async ones behave:

- **The holder is the task.** A task that takes a key it already holds re-enters it. Any other
  task waits - including one it started inside the held region, and the tasks of an
  `asyncio.gather`.
- **Waiting does not block the loop.** Other requests run while one waits for a lease.
- **A wait that is cancelled or times out** hands its connection back closed, so no lock can be
  left behind on a pooled connection. A cancelled holder releases the lock on its way out of
  `async with`.
- **A SQL lease holds an async connection** for its whole hold: give the locks a pool of their
  own (`lockConfig`), sized for the leases held at once.

The sync providers refuse to run on an event loop's thread, and their error says to use these.

## Event handlers, after the unit of work

A handler never runs inside an action. The action commits its rows and its events. Later,
fan-out and dispatch - jobs, on threads of their own - pick the events up and run the handlers, a
batch at a time. This is the same whether the request path is sync or async.

A handler may extend `AsyncEventHandler`, whose `handle()` is `async def`, to await an
`AsyncActionExecutor`:

```python
class WalletMoneyDepositedEventHandler(AsyncEventHandler[WalletMoneyDepositedEvent]):
    def __init__(self, executor: AsyncActionExecutor) -> None:
        self.executor = executor

    def name(self) -> str:
        return "wallet-money-deposited-notification"

    def event_type(self) -> type[WalletMoneyDepositedEvent]:
        return WalletMoneyDepositedEvent

    async def handle(self, envelope: EventEnvelope[WalletMoneyDepositedEvent]) -> None:
        await self.executor.execute(None, CreateNotificationAction, CreateNotificationAction.Params(...))
```

Dispatch runs an async handler on its **handler loop**: one event loop, on a thread of its own,
open for as long as dispatch is. The delivery thread waits for it, and a batch of async handlers
runs on that loop at the same time. Success, retry, backoff and expiry are decided exactly as for
a sync handler, from what the handler returned or raised. Sync and async handlers can be
registered side by side.

**What an async handler awaits belongs to the handler loop.** An async pool is tied to the event
loop it is used on. So give the handlers a database registry and an executor of their own (the
examples use a `handlersConfig` pool), and at shutdown close them on that loop, before closing
the loop itself:

```python
handler_loop = HandlerLoop()
job = (
    EventHandlingJob.builder()
    .registry(events_registry)                  # sync: fan-out and dispatch read the queue
    .handlers(handlers)
    .handler_loop(handler_loop)
    .build()
)
# at shutdown, after the jobs have stopped:
handler_loop.run(handler_registry.aclose())
handler_loop.close()
```

Without `.handler_loop(...)`, dispatch makes its own loop, started only when an async handler
first runs. Fan-out and dispatch themselves read and write the `events` and
`event_notifications` tables through a sync registry, built from the same layout file.

The `fastapi-wallet-rest-uv-async-pg`, `fastapi-wallet-rest-uv-async-mysql`,
`fastapi-wallet-rest-uv-async-mariadb` and `fastapi-wallet-rest-uv-async-sharded-pg` examples are
built this way: async requests under an async keyed lock, an async handler, and a pool for each
use. `fastapi-wallet-saga-uv-async-pg` runs a whole saga's later steps as async handlers.

## A job whose work is async

A distributed job is sync in every service. The scheduler claims its row, calls `execute` on one
of its threads, and sends its heartbeat from another. The *work* inside it can still be async:
`execute` hands a coroutine to a `HandlerLoop` with `loop.run(...)`, and waits for it. A
`HandlerLoop` is an event loop on a thread of its own - the same kind dispatch runs async
handlers on.

```python
class WalletStipendJob(DistributedJob):
    def __init__(self, loop: HandlerLoop, executor: AsyncActionExecutor, wallet_repository: WalletRepository):
        self.loop = loop                  # the loop `executor` and `wallet_repository` were built for
        self.executor = executor
        self.wallet_repository = wallet_repository

    def execute(self, ctx: ExecutionContext) -> None:
        self.loop.run(self.pay())         # on the scheduler's thread: run it there, and wait

    async def pay(self) -> None:
        for wallet in await self.wallet_repository.find_open_below(Decimal("100.00")):
            await self.executor.execute(None, WalletDepositMoneyAction, WalletDepositMoneyAction.Params(...))


loop = HandlerLoop(name="worker-loop")
registry = AsyncDatabaseRegistry.from_config(layout)    # used only on `loop`
# ... the async repositories and executor over it, WalletStipendJob(loop, executor, wallet_repository)
# at shutdown: jobs.stop(), then loop.run(registry.aclose()), then loop.close()
```

The job's thread waits, so whatever the coroutine raises, `execute` raises. The claim, the
heartbeat, a failure and its retry are the scheduler's, exactly as for a sync job. Everything the
work awaits is built for that loop, and closed on it after the jobs have stopped. Give dispatch
the same loop (`.handler_loop(loop)`) and an async handler can share the work's registry.

This is worth it when the work waits on many things at once and can await them together. A job
that runs a few statements in a row gains nothing: write it sync, over a sync executor. An async
service can run such a job beside itself unchanged. `job-worker-uv-async-pg` is built this way.

## One kind per service

A service is all-sync or all-async on its request path. Two registries over one database are
two pools, and **one transaction cannot span them**. Never call the sync API from inside an
`async def`: it blocks the event loop, and with it every request at once. See
[Sync or async?](/learn/sync-or-async/).

## Testing an async action

Both helpers run the action's `perform` against a bare plan, with no executor and nothing
committed: `async_run_action` returns what it staged, and `AsyncActionSpec` adds the checks.

```python
staged = await async_run_action(None, WalletDepositMoneyAction(clock, wallet_repository), params)
assert staged.updated(Wallet)[0].balance == Decimal("150.00")

checked = await AsyncActionSpec.of(WalletDepositMoneyAction(clock, wallet_repository)).execute(params)
checked.assert_updated(Wallet, lambda w: w.balance == Decimal("150.00"))
```

`execute` and `assert_throws` are awaited. What comes back is the sync `ActionAssert`, so every
check works as in sync. `count_statements(registry)` takes an async registry as well, around
awaited work.

## Passwords

As on the sync side, no password is ever printed. That covers:

- an async data source, its engine and its url, a transaction manager, and a registry;
- the error when asyncpg, psycopg's async mode or aiomysql refuses a connection;
- an async keyed lock, its lease and its errors, including the password in a Redis url;
- the SQL the engine logs with `echo` on.

This is checked with a test password on PostgreSQL (asyncpg and psycopg async), MySQL, MariaDB
and Redis.

## gevent

`ekbatan.aio` does not run under gevent's monkey-patching: aiosqlite's worker threads, for one,
become greenlets that block the event loop's own thread, and units of work stall at the pool.
gevent and asyncio are two answers to the same question, so pick one per service. Running the
sync API under gevent is covered in
[Concurrency](/reference/runtime/concurrency/#gevent-cheap-blocking-with-nothing-to-change).

## Reference

Everything is in `ekbatan.aio`, its `locks` package, and two names in `ekbatan.events`:

| name | what it is |
| --- | --- |
| `AsyncDatabaseRegistry` | shards to managers; `from_config`, `builder()`, `aclose()`, `async with` |
| `AsyncTransactionManager` | one shard's pools; `transaction()`, `connection(readonly=)`, `current()` |
| `AsyncDb` | the connection every accessor hands out: SQLAlchemy's `AsyncConnection`, plus `rows()` |
| `AsyncTransaction` | an open transaction: `execute`, `rows`, `shard`, `dialect` |
| `AsyncModelRepository`, `AsyncEntityRepository`, `AbstractAsyncRepository` | the repositories, every read and write a coroutine |
| `AsyncRepository` | what the executor needs of a repository |
| `AsyncAction` | a unit of work with `async def perform` |
| `AsyncActionExecutor` | runs them; `execute` is awaited; `builder()` |
| `AsyncSingleTableJsonEventPersister`, `AsyncEventPersister` | the outbox write, and its protocol |
| `AsyncChangePersister` | writes one shard's slice of a plan |
| `AsyncActionSpec`, `async_run_action` | testing without a database |
| `ekbatan.aio.locks`: `AsyncPostgresKeyedLockProvider`, `AsyncMySQLKeyedLockProvider`, `AsyncMariaDBKeyedLockProvider`, `AsyncKeyedLockProvider`, `AsyncLease`; `ekbatan.aio.locks.redis`: `AsyncRedisKeyedLockProvider` | keyed locks, taken around `await executor.execute(...)` |
| `ekbatan.events`: `AsyncEventHandler`, `HandlerLoop` | an event handler with `async def handle`, and the loop dispatch runs it on - which a job can run its async work on too |
| `AsyncDataSource`, `async_url`, `ASYNC_DEFAULT_DRIVERS` | the async pool for one config (`AsyncDataSource.from_config`, closed with `aclose()`), and which driver it uses |
