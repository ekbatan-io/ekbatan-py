- **yours** - `wallets`, `orders`, `notifications`;
- **the framework's** - written by the framework or one of its runtime helpers.

This is the map. The individual pages carry the full DDL per dialect, column by column.

| table | needed when | written by | shape |
| --- | --- | --- | --- |
| [`events`](/reference/tables/events/) | you use the default outbox persister, which is the normal setup | the executor, inside the action's transaction | `outbox_table()` |
| [`event_notifications`](/reference/tables/event-notifications/) | optional - only with the in-process event handler | the fan-out job creates rows, the dispatch job updates them | `notifications_table()` |
| [`scheduled_tasks`](/reference/tables/scheduled-tasks/) | optional - only with distributed jobs, or anything built on them | db-scheduler | `scheduled_tasks_table()` |

The in-process event handler is built on distributed jobs - fan-out and dispatch *are* jobs - so
using it means all three tables.

## Do I need each table?

| what you are doing | `events` | `event_notifications` | `scheduled_tasks` |
| --- | :---: | :---: | :---: |
| action persistence only | yes | no | no |
| Debezium or CDC reading committed events | yes | no | no |
| in-process fan-out and handling | yes | yes | yes |
| distributed jobs only | no | no | yes |
| a custom [`EventPersister`](/reference/action-executor/) that writes somewhere else | up to you | no, unless you also handle in-process | only if you use distributed jobs |

The last row is the one that surprises people. The outbox table is the *default* persister's
choice, not the framework's requirement: swap the persister and `events` is yours to shape —
a different retention, a partitioned table, a second column your consumers need. What you cannot
swap is *when* it is written, which is the part that makes it atomic.

## Table pages

- [`events`](/reference/tables/events/) — the committed action and event rows the default
  persister writes. Every deployment has this one
- [`event_notifications`](/reference/tables/event-notifications/) — one row per (event, handler),
  holding what the in-process pipeline has delivered and what it has not
- [`scheduled_tasks`](/reference/tables/scheduled-tasks/) — the scheduler's own table, used by
  distributed jobs and, through them, by the in-process handlers

## Getting them into your database

They are SQLAlchemy `Table` objects, not DDL you copy. Build them into your own metadata:

```python
from sqlalchemy import MetaData
from ekbatan.schema import notifications_table, outbox_table, scheduled_tasks_table

metadata = MetaData()
EVENTS = outbox_table(metadata)
EVENT_NOTIFICATIONS = notifications_table(metadata)
SCHEDULED_TASKS = scheduled_tasks_table(metadata)
```

**Where the two event tables are is fixed**, and nothing passes them to the framework: the
executor's default event writer, the fan-out job and the handling job name them themselves.
`outbox_table()` and `notifications_table()` take no name and no schema - they describe exactly
the tables the framework uses:

| database | the two event tables |
| --- | --- |
| PostgreSQL | `eventlog.events`, `eventlog.event_notifications` - a schema of their own, in each database |
| MySQL, MariaDB | `events`, `event_notifications` - in the connected database |
| SQLite | `events`, `event_notifications` - in the file |

On MySQL and MariaDB a schema is a database, and one `eventlog` database would be shared by every
database on the server - shards and other applications would read each other's events - so there,
as on SQLite, every data source maps `eventlog` onto the connected database - and so does a
connection you open from its `sqlalchemy_engine`. An engine you build yourself with SQLAlchemy needs
the same mapping before you read these tables through it:

```python
from sqlalchemy import create_engine
from ekbatan.schema import eventlog_translation

engine = create_engine(url, execution_options={"schema_translate_map": eventlog_translation("mysql")})
```

In practice you do not write the tables by hand at all - `schemagen` emits them alongside your
own tables, and `migrate()` creates them from your migration files. See [schemagen](/reference/schemagen/)
and [Migrations](/reference/migrations/). On PostgreSQL, `create_all` makes the `eventlog` schema before
the two tables.

In a sharded application every shard gets its own copy of all three. `migrate()` applies the same
migration files to each.

### Tables already in PostgreSQL's default schema

A PostgreSQL database whose migrations put the two event tables in its default schema moves them
in its next migration. Rows, keys and indexes go with each table:

```sql
CREATE SCHEMA IF NOT EXISTS eventlog;
ALTER TABLE events SET SCHEMA eventlog;
ALTER TABLE event_notifications SET SCHEMA eventlog;
```

Nothing to move on MySQL, MariaDB or SQLite: there they stay in the database itself.
