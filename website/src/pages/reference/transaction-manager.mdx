For those, take a transaction manager directly. It is the same primitive the executor uses
internally: one transaction, one connection, commit-or-roll-back, with the connection bound to
the calling context so any repository you call from inside joins it.

## What it owns

You rarely construct one. Reach through the registry:

```python
tm = registry.default                      # the default shard
tm = registry.manager(MEXICO)              # a specific one
```

Each one owns four things, for exactly one shard:

- **One pool pair** — the primary `Engine`, and the replica `Engine` if that shard has one. An
  `Engine` is pool, dialect and lifecycle in one, which is why there is no separate connection
  provider here.
- **A dialect**, read off `engine.dialect.name`. It is what picks the keyed-lock provider, the
  `RETURNING` support and the column renderings, so it is the manager's business rather than a
  per-call argument.
- **A `ShardIdentifier`** — `ShardIdentifier(0, 0)` when you are not sharding. It labels the
  OpenTelemetry span and is what `DatabaseRegistry` routes by.
- **A `ContextVar`** holding the in-flight transaction's connection for the duration of a
  `tm.transaction()` block. A `ContextVar` rather than a thread local, so the binding follows an
  `await` and a `ThreadPoolExecutor` does not inherit one by accident.

In async mode the registry is an `AsyncDatabaseRegistry` and each manager an
`AsyncTransactionManager`, from `ekbatan.aio`: the same four things, with `AsyncEngine` pools,
and every block below is `async with`. A cancelled task rolls its transaction back like any
other failure.

## The `tm.transaction()` family

<ModeTabs>
<div slot="sync">

```python
with tm.transaction() as tx:
    orphans = tx.execute(
        select(WALLETS.c.id).where(WALLETS.c.currency.is_(None)).with_for_update()
    ).scalars().all()

    if orphans:
        tx.execute(update(WALLETS).where(WALLETS.c.id.in_(orphans)).values(currency="EUR"))
        tx.execute(insert(AUDIT_LOG).values(at=clock.now(), note="currency backfill",
                                            affected=len(orphans)))
```

</div>
<div slot="async">

```python
async with tm.transaction() as tx:
    found = await tx.execute(
        select(WALLETS.c.id).where(WALLETS.c.currency.is_(None)).with_for_update()
    )
    orphans = found.scalars().all()

    if orphans:
        await tx.execute(update(WALLETS).where(WALLETS.c.id.in_(orphans)).values(currency="EUR"))
        await tx.execute(insert(AUDIT_LOG).values(at=clock.now(), note="currency backfill",
                                                  affected=len(orphans)))
```

</div>
</ModeTabs>

`clock.now()` is written exactly as it is - UTC with no zone attached, which is what the
zone-less `at` column holds. Nothing converts it on the way in or out
([What you give is what is stored](/reference/multi-database/#what-you-give-is-what-is-stored)).

Both writes commit together or neither does - the same atomicity an action gives you, without any
of the action machinery: no plan, no outbox row, no retry on a lost version race.

`tx.rows(statement)` is forwarded too, for a statement whose rows become objects - the same
`fetch(mapper)` family a repository uses, described in [Repositories](/reference/repository/#write-the-mapping).
`tx.connection` is the `Db` underneath, for everything else SQLAlchemy offers.

**One `with` block covers every case.** The block can compute and keep any value you want, and
an exception of any kind leaves it, rolling the transaction back on the way.

## Do not nest

**Do not nest.** The framework does not simulate nested transactions or savepoints. A
`tm.transaction()` inside another one on the same `tm` does not fail loudly: it opens a *second*
transaction on a *second* pooled connection, with its own commit boundary. That is almost never what you want. Structure your code to do all the work
inside one outer block.

What the inner block gets:

- it does not see the outer block's uncommitted rows;
- its commit stands even if the outer block then fails, and its failure rolls back only its own
  writes;
- inside it, `tx_db` and `tx_db_else_db` find the inner transaction; after it, the outer one
  again;
- a write to a row the outer block has locked waits for a lock the same thread holds - until the
  database's lock timeout, or for ever where there is none. On SQLite, any inner write after an
  outer one waits for the file lock and fails with "database is locked".

An action run inside a transaction you opened is the same case: the executor opens its own
transaction, so the action commits on its own and stays committed if your block then rolls back.

## Direct usage — a worked example

1. Borrow a connection from the **primary** pool.
2. Bind it into the ambient context for this manager.
3. `BEGIN`, then run your block.
4. Normal return: `COMMIT`, release the connection.
5. Exception: `ROLLBACK`, release, re-raise.

The transaction is begun, committed and rolled back by hand rather than through SQLAlchemy's own
`with conn.begin()`. That context manager rolls back for you, but it has nowhere to report that
**the rollback itself** failed - and SQLAlchemy then returns the connection to the pool and hands
it to the next caller, still carrying whatever the rollback did not undo. This framework refuses
to do that: a failed rollback marks the transaction dirty and the connection is evicted rather
than released.

The reasoning behind the eviction is worth knowing because it is counter-intuitive: restoring
autocommit on a connection whose transaction may still be open **is itself a commit**. psycopg
issues an explicit `COMMIT`; MySQL and MariaDB send `SET autocommit=1`, which they document as an
implicit commit. Restoring it after a failed rollback would commit the very transaction that just
failed to roll back. Physically closing the connection makes the server discard what was pending.

**A failed commit is not on its own grounds for eviction.** The `COMMIT` is issued inside the
`try`, so a commit that raises falls into the same `except` as any other failure and gets a
`ROLLBACK` like any other transaction. If that rollback succeeds, the connection is clean and
goes back to the pool normally. Only a rollback that *also* fails leaves the state unknown, and
only then is the connection thrown away.

## Repository writes join automatically

Because the connection is bound into the ambient context rather than passed around, a repository
write inside the block uses it:

<ModeTabs>
<div slot="sync">

```python
with tm.transaction():
    wallet = wallets.get(wallet_id)          # a primary read, by design
    wallets.update(wallet.close())           # joins this transaction
```

</div>
<div slot="async">

```python
async with tm.transaction():
    wallet = await wallets.get(wallet_id)    # a primary read, by design
    await wallets.update(wallet.close())     # joins this transaction
```

</div>
</ModeTabs>

Reads are a choice. Inherited reads see committed state on the primary; if a read must see this
block's own uncommitted writes, use `tx.execute` / `tx.rows` or a repository method built on
`tx_db_else_db`. See [Repositories](/reference/repository/).

The mechanism is the ambient transaction, and it is worth being precise about it because it is
what makes a repository call read the same inside a unit of work and outside one.

Opening a transaction binds its connection to a `ContextVar`, keyed by the manager. A second
manager for the same shard (another registry, or
one built on a member's `jobsConfig`) sees no transaction there and opens its own, on its own
database. Every repository
write goes through `tx_db_else_db(...)`, which looks in that binding first: inside the block it
finds the connection and joins, outside it finds nothing and each statement commits on its own.
Nothing is threaded through arguments, and no repository takes a connection parameter.

Two consequences follow, and both are the point rather than side effects:

- **A repository method written once works in both places.** The same `wallets.update(...)` is
  part of your transaction inside the block and a standalone write outside it.
- **The binding does not propagate to a thread pool.** Work handed to a pool
  (`ThreadPoolExecutor.submit`) from inside a transaction does not inherit it, which is correct:
  another thread is another connection, and quietly sharing one would corrupt both. See
  [Concurrency](/reference/runtime/concurrency/).
- **It does propagate to a task, and to `asyncio.to_thread`.** Both copy the caller's context,
  so work started that way inside the transaction sees it open and uses its connection. In an
  async transaction, statements from tasks then take turns on that one connection. Keep such
  work inside the `with` block, and do not hand a sync transaction to `to_thread`.

What does *not* join is a read you route yourself. `db()` and `readonly_db()` open their own
connections deliberately — see [Repositories](/reference/repository/#picking-the-right-one).

## When NOT to use it directly

If the operation changes a model and emits an event, **write an action instead.** The action path
gets you the outbox row written atomically with the domain row - which is the entire point of the
framework - plus retry on a lost version race, the span hierarchy, cross-shard validation, and
fan-out into the event pipeline.

`tm.transaction()` is the escape hatch. Reach for it when the work genuinely does not fit:

- boot-time or shutdown-time work - default rows, a sanity check;
- admin and ops scripts - backfills, manual fixes, exports;
- multi-step reads that want one consistent snapshot and write nothing;
- batch maintenance where one event per row would be useless outbox volume.

If you find yourself reaching for it for ordinary business work, that is a signal the operation
wants to be an action.

## Read-only access (no transaction needed)

If you only read, you need no transaction:

<ModeTabs>
<div slot="sync">

```python
with tm.connection() as conn: ...                  # primary, freshest committed state
with tm.connection(readonly=True) as conn: ...     # the replica, tolerates lag
```

</div>
<div slot="async">

```python
async with tm.connection() as conn: ...              # primary, freshest committed state
async with tm.connection(readonly=True) as conn: ... # the replica, tolerates lag
```

</div>
</ModeTabs>

Inside a `tm.transaction()` block these hand you that transaction's connection instead, so a
read written this way joins rather than opening a second one.

Outside one, no transaction is opened and nothing is bound — the connection runs in
`AUTOCOMMIT`, so each statement stands on its own and commits itself. The framework sets this
on purpose, because SQLAlchemy will not do it by default: an `execute` outside a transaction quietly begins one, and
a connection closed without `commit` rolls it back, so a write would simply vanish.

`readonly=True` asks for the replica and falls back to the primary when a shard has none. It is
never the default, because a replica has not necessarily seen what you just wrote.

## Cross-shard

A transaction manager is **per shard**, and there is no two-phase commit. If you need writes
across shards you cannot have them atomically - that is a property of distributed systems, not of
this framework.

<ModeTabs>
<div slot="sync">

```python
with registry.manager(GLOBAL).transaction(): ...   # work A
with registry.manager(MEXICO).transaction(): ...   # work B
# if B fails, A is already committed.
```

</div>
<div slot="async">

```python
async with registry.manager(GLOBAL).transaction(): ...   # work A
async with registry.manager(MEXICO).transaction(): ...   # work B
# if B fails, A is already committed.
```

</div>
</ModeTabs>

An escape hatch, with the same partial-commit risk as `allow_cross_shard=True` on an action. If a
partial commit would need compensating, use a [saga](/learn/sagas/).

## Tracing

The block produces an `ekbatan.transaction` span with `ekbatan.shard.group` and
`ekbatan.shard.member` attributes, one per block - a nested block is a transaction of its own and
gets its own span.
