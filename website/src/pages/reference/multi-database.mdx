Most of the framework is dialect-agnostic. The differences concentrate in one place: **the column
types in your migrations.** Get those right and the rest follows, which is why three helpers do
all the work.

## Column-type cheatsheet

Three helpers cover the columns whose type differs between databases. Each is a SQLAlchemy type
that already knows how to render itself on each dialect, so you pick the helper and not the
dialect.

```python
from ekbatan.schema import json_column, timestamp_column, uuid_column
```

| helper | PostgreSQL | MySQL | MariaDB | SQLite |
| --- | --- | --- | --- | --- |
| `uuid_column()` | `UUID` | `CHAR(36)` | `CHAR(36)` | `CHAR(32)` |
| `timestamp_column()` | `TIMESTAMP WITHOUT TIME ZONE` | `DATETIME(6)` | `DATETIME(6)` | `DATETIME` |
| `json_column()` | `JSONB` | `JSON` | `JSON` | `JSON` |

Everything else is ordinary SQLAlchemy: `String(n)`, `Numeric(p, s)`, `Integer`, `BigInteger`,
`Boolean`. They already render correctly everywhere.

Use these helpers in your migrations rather than raw types. They are also what
[`schemagen`](/reference/schemagen/) forces reflected columns *back* to, which is what makes a schema
generated on one dialect usable on another.

### Why MySQL needs `CHARACTER SET ascii` on uuid columns

MariaDB has the same default and the same fix. A uuid in canonical form is pure 7-bit ASCII — 8-4-4-4-12 hex digits and four hyphens. Under
MySQL's default `utf8mb4` a `CHAR(36)` reserves **four bytes per character**: 144 bytes per index
entry where 36 would do. On a primary key that is read on every request, that is four times the
index pages and four times the cache pressure, for no information.

`uuid_column()` does not pin the charset, because a column's charset is part of your DDL rather
than part of a type. Pin it in the migration:

```sql
id CHAR(36) CHARACTER SET ascii NOT NULL
```

PostgreSQL's native `UUID` is 16 bytes and has no charset to get wrong. MariaDB 10.7+ has a
native `UUID` too, and this framework still writes `CHAR(36)` there — see below.

### Why MySQL uuid columns are `CHAR(36)`-shaped, not `BINARY(16)`

`BINARY(16)` is half the size and the obvious optimisation. It is not what this framework does,
and the reason is that the outbox is read by things that are not this framework: `psql`, a
Debezium connector, a service in another language on the same database, a support engineer
with a SQL prompt.
A `BINARY(16)` `model_id` is unreadable to every one of them, and unjoinable against any column
that is not also `BINARY(16)`.

The same argument rules out MariaDB's native `UUID` type: it is stored as 16 bytes, reflects as
a type MySQL does not have, and produces rows that a MySQL replica of the same schema cannot
receive.

SQLAlchemy's own default for a dialect with no uuid type is `CHAR(32)` — the hex with the
hyphens stripped. This framework overrides that, and the bug it avoids is worth stating plainly:
one writer storing `d5143465-787a-...` and another storing `d5143465787a...` cannot join on
`model_id`, **and neither notices**, because both queries succeed and return nothing. The
hyphenated text is also what a Java service writes into its events - see
[Running beside a Java service](/reference/beside-java/#ids).

### Why MariaDB `JSON` needs the type forced

MariaDB stores `JSON` as `LONGTEXT` with a `CHECK` constraint, and the driver reports it that
way. A `CREATE TABLE ... JSON` works; reading the schema back gives you `LONGTEXT`.

This affects **reflection only** — a column declared `json_column()` in your own `schema.py`
tells SQLAlchemy the type rather than asking the database, and is unaffected. But
[`schemagen`](/reference/schemagen/) reflects a real database, so on MariaDB it would emit
`Text` for a column you declared as JSON, and the generated module would then bind strings where
the framework expects objects.

`schemagen` therefore forces the type back rather than trusting the reflection: it reads the
column's `json_valid` check from `information_schema` and writes `json_column()`. The same pass
fixes `BIGINT(display_width=20)`, which MariaDB reports for a plain bigint and which does not
even import. MySQL reports `JSON` correctly and needs neither.

### One table for every dialect

A repository does not choose column types by dialect. `with_variant()` puts the per-dialect
rendering inside the type:

```python
Uuid().with_variant(_CanonicalUuid(), "mysql", "mariadb")
JSON().with_variant(JSONB(), "postgresql")
```

One `Table`, one repository, and the engine picks the rendering at statement-compile time. That
is why this page is a short cheatsheet and not a pattern to follow in every repository.

## Always UTC

### What you give is what is stored

**Ekbatan never converts a time.** A `datetime` goes to the database exactly as your code or
your clock gave it, and comes back exactly as the driver returns it. No zone is added, removed or
moved - not in models, repositories, the outbox, notifications, event JSON or
`timestamp_column()`. Getting time right is your job; the rest of this section is how.

```python
from ekbatan import SystemClock

now = SystemClock().instant()          # datetime(2026, 10, 19, 8, 30, 0, 123456) - UTC, no zone
wallet = wallets.add(Wallet.open(..., created_date=now))
wallets.get(wallet.id).created_date == now   # True: the same value, to the microsecond
```

The default clock gives the current **UTC time with no zone attached**. That is exactly what a
zone-less column holds, so what is written reads back equal, and compares with the next
`clock.instant()` - the framework does that comparison itself for event retries, due times and
expiry.

A value *with* a zone is passed on as it is, and then the driver decides. Measured with
`13:30+03:30` written into a zone-less column:

| driver | stored |
| --- | --- |
| psycopg (sync and async) | moved to the session's zone by the server: `10:00` with the session in UTC |
| asyncpg | refused - `DataError` |
| PyMySQL, aiomysql (MySQL, MariaDB) | `13:30`: the digits kept, the offset dropped |
| SQLite (pysqlite, aiosqlite) | `13:30`: the digits kept, the offset dropped |

So keep to naive UTC, as the default clock gives. If you do use aware values - your own `Clock`,
`TIMESTAMPTZ` columns - keep them aware everywhere: the framework compares what your clock gives
with what the database returns, and Python refuses to compare a naive `datetime` with an aware
one.

### Time kinds

Python has one `datetime` class for three different kinds of time. `ekbatan.time` names them, so
a type checker keeps them apart and the JSON says which one a reader gets:

| meaning | Python label | PostgreSQL column | JSON |
| --- | --- | --- | --- |
| a moment | `Instant` - no zone attached, UTC digits | `TIMESTAMP` | `"2026-03-01T09:30:00.120Z"` |
| a wall date and time | `LocalDateTime` - no zone attached | `TIMESTAMP` | `"2026-03-01T09:30:00.12"` |
| a moment with its offset | `OffsetDateTime` - zone attached | `TIMESTAMPTZ` | `"2026-03-01T13:00:00.12+03:30"` |
| a time of day | `time` | `TIME` | `"09:30:00"` |
| a date | `date` | `DATE` | `"2026-03-01"` |

On MySQL and MariaDB both `Instant` and `LocalDateTime` are `DATETIME(6)`; neither database has a
column that keeps an offset. `Instant` and `LocalDateTime` are the same zone-less column - only
the label differs.

```python
from dataclasses import dataclass
from datetime import datetime

from ekbatan import ModelEvent
from ekbatan.time import Instant, LocalDateTime


@dataclass(frozen=True, kw_only=True)
class ShiftPlannedEvent(ModelEvent["Shift"]):
    planned_at: Instant        # when it was planned: a moment
    opens_at: LocalDateTime    # "09:00 on 1 March", wherever the shop is


event = ShiftPlannedEvent(
    model_id=str(shift.id),
    planned_at=self.clock.instant(),                         # the clock gives an Instant
    opens_at=LocalDateTime(datetime(2026, 3, 1, 9, 0)),
)
```

- **The labels cost nothing.** They are `typing.NewType`s: a value is a plain `datetime`, and
  `Instant(x)` hands back `x` - it converts nothing and checks nothing. Arithmetic keeps the
  label: `self.clock.instant() + timedelta(days=1)` is still an `Instant`.
- **mypy keeps them apart.** An `Instant` passed where a `LocalDateTime` is expected is an error,
  and so is a plain `datetime` where an `Instant` is - write `Instant(value)` once, where the
  value comes in, and say what it is.
- **Where they come from.** `clock.instant()` (and `self.clock.instant()` in an action) gives an
  `Instant`. A model's `created_date` and `updated_date` are `Instant`s, and so is every time the
  framework writes - the outbox, notifications, retries, jobs. A generated record says which kind
  each column is ([schemagen](/reference/schemagen/#time-columns)).
- **In JSON, the label decides.** An event's or a params dataclass's `datetime` field is written
  as the kind it is declared - an `Instant` with `Z`, a `LocalDateTime` with no zone, an
  `OffsetDateTime` with its offset - and read back as the same kind. Nothing is converted: an
  `Instant`'s digits are already UTC's and are written as they are. A field declared plain
  `datetime`, or a value of the wrong sort for its kind (a zone attached in an `Instant` field),
  is refused when the action runs, and nothing is saved:

  ```text
  event ShiftPlannedEvent field planned_at is a plain datetime; declare it Instant,
  LocalDateTime or OffsetDateTime (ekbatan.time)
  ```
- **Your own JSON columns keep what you give them.** A `datetime` inside a `dict` written to a
  `json_column()` of your own is written as it is - no zone for a naive one, its offset (`Z` at
  zero) for an aware one - and never refused. The refusal above is for event payloads and action
  params, whose reader goes by the declared kind. A field declared `Instant`, `LocalDateTime` or
  `OffsetDateTime` is written as its kind there too.
- **A union of two kinds is refused.** `Instant | LocalDateTime` fits any `datetime`, so it says
  nothing about which one a value is: the message is `declared as more than one kind (Instant |
  LocalDateTime); pick one`. `Instant | None` is fine.
- **Ruff.** Ruff's `RUF009` flags `Instant(...)` in a dataclass default as a call. The labels hand
  back the value they are given, so tell it they are immutable, in `pyproject.toml`:

  ```toml
  [tool.ruff.lint.flake8-bugbear]
  extend-immutable-calls = [
    "ekbatan.time.Instant",
    "ekbatan.time.LocalDateTime",
    "ekbatan.time.OffsetDateTime",
  ]
  ```

### The recommendation

**Strongly recommended.** Not enforced - nothing refuses another zone - and leaving it is where
time bugs come from. Three parts:

1. **In your code, UTC.** Take the time from the framework's clock - `self.clock.instant()` in an action,
   `clock.instant()` elsewhere - which is UTC with no zone attached. Not `datetime.now()`, which is
   local time. Convert to a person's local time only where it is shown to them.
2. **In the columns, no zone.** `TIMESTAMP` (`WITHOUT TIME ZONE`) on PostgreSQL, `DATETIME(6)` on
   MySQL and MariaDB, holding UTC. `timestamp_column()` builds this - a column type and nothing
   more, with microsecond precision on every database.
   - **Not `TIMESTAMPTZ`.** It turns the session's zone into part of every write and read: two
     readers with different session zones disagree about when the thing happened.
   - **Not bare `DATETIME`** on MySQL and MariaDB: it truncates to whole seconds, silently, and
     the outbox's only ordering key is a timestamp.
3. **On the database, UTC.** A naive value is stored as written whatever the session's zone -
   measured on all three databases, both drivers each - but the database's **own** clock is not:
   `NOW()`, `CURRENT_TIMESTAMP`, a column `DEFAULT`. SQL that mixes those with your columns is off
   by the zone's offset. Run the server in UTC (`TZ=UTC` on the container; PostgreSQL's
   `timezone = 'UTC'`), or set it per connection in `data_source_properties`:

   ```python
   # PostgreSQL
   DataSourceConfig(url=..., data_source_properties={"options": "-c TimeZone=UTC"})
   # MySQL and MariaDB
   DataSourceConfig(url=..., data_source_properties={"init_command": "SET time_zone = '+00:00'"})
   ```

   Both measured against a server set to `Asia/Tehran`: the session then reports UTC. The same
   lines work for `ekbatan.aio`'s drivers as written: aiomysql reads `init_command` as PyMySQL
   does, and asyncpg - which has no libpq `options` - receives the `-c` settings as its own
   `server_settings`. Measured the same way, on both.

CI runs the PostgreSQL suite a second time under a non-UTC process, because that is where a driver
inferring a zoned type would show up and nowhere else. The one place the framework steps off the
rule is `scheduled_tasks`, which is db-scheduler's own schema - see
[that table's page](/reference/tables/scheduled-tasks/) for the measured consequence of getting it wrong.

## Schema vs database

The framework's two event tables have a fixed home: a schema called `eventlog`. What that is
depends on the database.

On PostgreSQL a schema is a namespace **inside** the connected database, so the tables are
`eventlog.events` and `eventlog.event_notifications`. `CREATE SCHEMA IF NOT EXISTS eventlog;` in
your first migration is all it takes, the connecting user normally has the right to do it, and
every database - every shard - has its own.

On MySQL and MariaDB "schema" and "database" are the same thing, so `eventlog` is a **separate
database** beside yours, and the tables are `eventlog.events` and `eventlog.event_notifications`
there too. Two consequences:

1. Your first migration creates it: `CREATE DATABASE IF NOT EXISTS eventlog;`, in a file of its
   own before the tables (`V0000__create_eventlog_database.sql`). It runs on your database's
   connection, so the login needs the right to create `eventlog` and to use it - root has it, and
   a login of its own gets it from root, once, with
   `GRANT ALL PRIVILEGES ON eventlog.* TO 'wallet'@'%';`.
2. There is one `eventlog` for the whole server, shared by every database on it. Two shards, or two
   applications, on one server write into the same two tables, and the fan-out job picks rows by
   event type alone - so where two applications use one event name, each one's handlers get the
   other's events. Give each shard a server of its own to keep them apart.

SQLite has no schemas, so there the two tables are plain `events` and `event_notifications` in the
file, and ekbatan maps `eventlog` onto it by itself.

Nothing passes the tables to the framework on any database: the executor's default event writer,
the fan-out job and the handling job name them themselves - see [Framework tables](/reference/tables/).

## Partial indexes (PostgreSQL only)

PostgreSQL can index a subset of a table:

```sql
CREATE INDEX events_undelivered ON events (event_type, event_date) WHERE delivered = FALSE;
```

MySQL and MariaDB cannot. The portable form puts the predicate column into the index instead:

```sql
CREATE INDEX ix_events_undelivered ON events (delivered, event_type, event_date);
```

**The framework's own tables use the portable form on every dialect**, including PostgreSQL,
because the table factory builds one index with no dialect variation. That costs real space on a
large outbox - [measured at 63x](/reference/tables/events/#the-undelivered-index-and-what-it-costs) - and
is the one place you may want to replace a generated index with your own.

## Why each dialect needs what it needs

Everything below was found by running the suite against all four, not by reading documentation.

| | |
| --- | --- |
| **`SKIP LOCKED`** | PostgreSQL, MySQL 8+ and MariaDB 10.6+ have it. SQLite does not, which is the main reason it is not a production dialect |
| **`RETURNING`** | PostgreSQL and SQLite support it on writes; MySQL and MariaDB do not, so the framework rebuilds written rows itself there |
| **`GET_LOCK` sub-second timeouts** | MySQL rounds them to whole seconds; MariaDB honours them. [Measured](/reference/keyed-locks/#mysql-rounds-the-wait-to-whole-seconds) |
| **Native UUID** | PostgreSQL always; MariaDB 10.7+; MySQL never |
| **Reflected type names** | MariaDB reports a bigint as `BIGINT(display_width=20)` and JSON as `LONGTEXT`. [`schemagen`](/reference/schemagen/) normalises both |
| **Untyped `NULL` in a multi-row `VALUES`** | PostgreSQL infers `text` and then refuses to insert it into an integer column. The framework casts every NULL explicitly |
| **Schema changes in a transaction** | PostgreSQL and SQLite roll a failed migration back as a whole; MySQL and MariaDB commit each schema change on its own, so keep one per migration file |

## Adding a new database

The framework picks its lock provider and its dialect behaviour off
`engine.dialect.name`, so a new dialect needs: a driver SQLAlchemy supports, a keyed-lock
provider, the three column helpers taught to render, and the suite run against it. The suite is
parametrised over the dialect rather than duplicated per dialect, so a new one cannot be
accidentally left out of a test.
