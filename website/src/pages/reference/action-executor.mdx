```

</div>

In async mode it is `AsyncActionExecutor` from `ekbatan.aio`, and `execute` is awaited; it runs
`AsyncAction`s only, as the sync one runs `Action`s only. Everything else on this page - the
transaction, the cross-shard rule, retries, tracing - is the same code in both.

Takes the action's **type**, and runs the instance registered for it. Callers depend on a class, not on a
constructed object with repositories hanging off it, and everything a service can do is listed in
its `ActionRegistry`.

An instance is refused, with a message saying so: it would run whether it was registered or not.
To run an action you just built in a test,
use `ActionSpec.of(action)` (`AsyncActionSpec` in async mode) — see [Test it without a database](/learn/your-first-action/#test-it-without-a-database).

        events: Table | None = None,

    ) -> None: ...
```

</div>

All keyword-only: an executor takes six collaborators, and positional order for six is a mistake
waiting to be made silently.

| | |
|---|---|
| `namespace` | written into every outbox row; required, and a naming root rather than a label |
| `registry` | the shard layout, which is how the executor finds a database to commit to |
| `repositories` | what persists each staged type. A type with none is refused when the executor goes to write it, with a message naming the type *and* listing what is registered |
| `actions` | the registry that maps a class to a constructed instance; optional if you always pass instances |
| `events` | the outbox `Table` to write to; the one from your generated `schema.py`. Left out (and no `outbox=`), the executor writes through the default persister to the framework's own `events` table |
| `clock` | defaults to the system clock. Pass a fixed one in tests and every timestamp becomes assertable |

`registry=None` and `repositories=None` are refused explicitly rather than accepted and dropped
into an attribute, because the failure otherwise arrives at the first `execute(...)` — far from
the wiring line that caused it.

## What "atomically" means

One transaction, on one shard, containing:

- every staged INSERT, with its initial version and timestamps;
- every staged UPDATE, each carrying `WHERE version = ?`;
- one outbox row per event, plus a sentinel row when an invocation emitted none.

They commit together or not at all. There is no second write to forget, and no publish step that
can fail after the commit.

## Cross-shard behaviour

By default an action that touches more than one shard is **refused** with `CrossShardError`,
naming the two shards that disagreed:

```python
if len(shards) > 1 and not config.allow_cross_shard:
    raise CrossShardError(first, second)
```

`ExecutionConfiguration(allow_cross_shard=True)` opts in to per-shard commits. Each shard
commits independently, **there is no two-phase commit**, and a failure rolls back only its own
shard — the ones that already committed stay committed. The executor logs that outcome loudly,
naming the shards, because a partial commit nobody noticed is the worst version of it.

Treat it as an escape hatch. Prefer passing it on one explicit `execute(...)` call rather than
setting it as an executor-wide default, so the risk is visible where the risk is taken. If a
partial commit would need compensating, use a [saga](/learn/sagas/) instead of one cross-shard
action.

See [Cross-shard actions](/learn/sharding-strategies/#cross-shard-actions-one-transaction-per-shard-never-atomic-across)
for the consistency model and the saga mitigation.

## Retries

`ExecutionConfiguration.retry_configs` is an ordered tuple of `RetryConfig(on=..., max_retries=..., delay=...)`.
The first whose `on` matches wins, so order is the precedence rule. The default is one retry on
`StaleRecordError` after 100 ms. `ExecutionConfiguration.no_retry()` turns it off.

## Tracing

Every invocation opens a span, with the action name, the shard, the principal and the outcome as
attributes, and a retry is an event on that span. The instrumentation is the OpenTelemetry **API
only** — with no SDK registered every call is a no-op. See
[Observability](/reference/runtime/observability/).

## Building one

<ModeTabs>
<div slot="sync">

```python
executor = ActionExecutor(
    registry=databases,
    repositories=repositories,
    actions=actions,
    namespace="com.example.finance",
    clock=clock,
)

wallet = executor.execute(DepositMoneyAction, params)
```

</div>
<div slot="async">

```python
executor = AsyncActionExecutor(
    registry=databases,                 # an AsyncDatabaseRegistry
    repositories=repositories,          # async repositories
    actions=actions,                    # AsyncActions
    namespace="com.example.finance",
    clock=clock,
)

wallet = await executor.execute(DepositMoneyAction, params)
```

</div>
</ModeTabs>

`namespace` goes on every outbox row and becomes the topic prefix downstream. It must be
dot-separated identifiers shaped like a package — a hyphen is refused up front, because the
namespace doubles as a protobuf package and `package my-service;` is a syntax error.

## Custom event persister

The default, `SingleTableJsonEventPersister` (`AsyncSingleTableJsonEventPersister` in async
mode), writes one JSON row per event into the outbox table. Supply your own to write a different shape — a second table, a different column layout,
encrypted payloads — while keeping the same transaction.

The protocol is one method, awaited in async mode:

<ModeTabs>
<div slot="sync">

```python
class EventPersister(Protocol):
    def persist_action_events(
        self,
        namespace: str,
        action_name: str,
        started_date: Instant,
        completion_date: Instant,
        action_params: Any,
        model_events: Sequence[ModelEvent],
        shard: ShardIdentifier,
        action_event_id: uuid.UUID,
    ) -> None: ...
```

</div>
<div slot="async">

```python
class AsyncEventPersister(Protocol):
    async def persist_action_events(
        self,
        namespace: str,
        action_name: str,
        started_date: Instant,
        completion_date: Instant,
        action_params: Any,
        model_events: Sequence[ModelEvent],
        shard: ShardIdentifier,
        action_event_id: uuid.UUID,
    ) -> None: ...
```

</div>
</ModeTabs>

It is called inside the transaction the domain rows are being written in, and a write through
the registry joins it: `registry.manager(shard).connection()` hands back the open transaction
rather than a new one. So whatever a replacement writes, it writes where the domain rows are
being written, or not at all. The default writes through `EventEntityRepository`, which does
exactly that.

The same persister is reachable from outside an action — a backfill job replaying historical
state can reuse the configured one rather than assembling events by hand.
