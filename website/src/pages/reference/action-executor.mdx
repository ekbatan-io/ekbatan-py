You build one executor when the service starts, and every request calls it:

```python
wallet = executor.execute(None, WalletDepositMoneyAction, params)
```

The arguments are the principal (who is acting, or `None`), the action's class, and its params.

## Type signature

<ModeTabs>
<div slot="sync">

```python
class ActionExecutor:
    def execute[P, R](
        self,
        principal: str | None,
        action: type[Action[P, R]],
        params: P,
        /,
        config: ExecutionConfiguration | None = None,
    ) -> R: ...
```

</div>
<div slot="async">

```python
class AsyncActionExecutor:
    async def execute[P, R](
        self,
        principal: str | None,
        action: type[AsyncAction[P, R]],
        params: P,
        /,
        config: ExecutionConfiguration | None = None,
    ) -> R: ...
```

</div>
</ModeTabs>

The first three arguments are positional, in this order: principal, action, params. A call in
any other order is refused with a `TypeError` that shows the right one. An optional `config`
changes the retries or allows cross-shard work for this one call (see [Retries](#retries) and
[Cross-shard behaviour](#cross-shard-behaviour)).

In async mode it is `AsyncActionExecutor`, from `ekbatan.aio`, and `execute` is awaited. Each
executor runs only its own kind: `ActionExecutor` runs `Action`s and `AsyncActionExecutor` runs
`AsyncAction`s. Everything else on this page - the transaction, the cross-shard rule, retries,
tracing - works the same in both. The sync `execute` called on an event loop's thread (inside
`async def` code) is refused with `BlockingCallError`.

`execute` takes the action's **class**, and runs the instance registered for it. So the code that
calls `execute` needs only the class, not an action object built with its repositories. And
everything a service can do is listed in one place: its `ActionRegistry`.

Passing an action instance instead of its class is refused with a `ValidationError`, because an
instance would run even if it was never registered. To run an action you just built in a test,
use `ActionSpec.of(action)` (`AsyncActionSpec` in async mode) — see [Test it without a database](/learn/your-first-action/#test-it-without-a-database).

## Building one

<ModeTabs>
<div slot="sync">

```python
executor = ActionExecutor(
    registry=databases,
    repositories=repositories,
    actions=actions,
    namespace="com.example.finance",
    clock=clock,
)

wallet = executor.execute(None, WalletDepositMoneyAction, params)
```

</div>
<div slot="async">

```python
executor = AsyncActionExecutor(
    registry=databases,                 # an AsyncDatabaseRegistry
    repositories=repositories,          # async repositories
    actions=actions,                    # AsyncActions
    namespace="com.example.finance",
    clock=clock,
)

wallet = await executor.execute(None, WalletDepositMoneyAction, params)
```

</div>
</ModeTabs>

```python
    def __init__(
        self,
        *,
        namespace: str,
        registry: AsyncDatabaseRegistry,
        repositories: RepositoryRegistry | Iterable[AsyncRepository],
        actions: ActionRegistry | Iterable[AsyncAction] = (),
        outbox: AsyncEventPersister | None = None,
        clock: Clock | None = None,
        config: ExecutionConfiguration = ExecutionConfiguration(),
    ) -> None: ...
```

</div>

Every argument is keyword-only, so two of them cannot be swapped by accident.

| | |
|---|---|
| `namespace` | written into every outbox row. Required, and it has a fixed shape (see below) |
| `registry` | the shard layout: how the executor finds the database to commit to |
| `repositories` | what saves each staged type. A type with no repository is refused when the executor goes to write it, with a message naming the type *and* listing what is registered |
| `actions` | the actions this executor can run: an `ActionRegistry`, or a list of action instances |
| `outbox` | what writes the outbox rows. Left out, the default persister writes them to the framework's own `events` table. See [Custom event persister](#custom-event-persister) |
| `clock` | defaults to the system clock. Pass a fixed one in tests, and every timestamp becomes predictable |
| `config` | the `ExecutionConfiguration` every call uses: one retry on `StaleRecordError`, and cross-shard work refused. A `config` passed to one `execute(...)` call replaces it for that call |

`registry=None` or `repositories=None` is refused straight away, with a `ValidationError`. So the
mistake shows at the line that builds the executor, not at the first `execute(...)`.

`namespace` goes on every outbox row, and becomes the start of the topic names downstream. It
must be dot-separated identifiers, like a package name: letters, digits and `_`, each part
starting with a letter or `_`. A hyphen is refused when the executor is built, because the
namespace is also used as a protobuf package name, and `package my-service;` is a syntax error
there. Write `my_service` instead.

`ActionExecutor.builder()` builds the same executor one setting at a time: `namespace(...)`,
`database_registry(...)`, `repository_registry(...)`, `action_registry(...)`,
`event_persister(...)`, `clock(...)` and `default_execution_configuration(...)`, then `build()`.

## What "atomically" means

One transaction, on one shard, containing:

- every staged INSERT, with its initial version and timestamps;
- every staged UPDATE, each carrying `WHERE version = ?`;
- one outbox row per event. An action that emitted no events still writes one row, with the
  event columns empty, so the outbox records every action that ran.

They commit together or not at all. There is no second write to forget, and no publish step that
can fail after the commit.

## Cross-shard behaviour

By default, an action that touches more than one shard is **refused** with `CrossShardError`,
before anything is written. The error names two of the shards involved.

To allow it, pass `allow_cross_shard=True` on the one call that needs it:

<ModeTabs>
<div slot="sync">

```python
executor.execute(
    None,
    TransferAction,
    params,
    config=ExecutionConfiguration(allow_cross_shard=True),
)
```

</div>
<div slot="async">

```python
await executor.execute(
    None,
    TransferAction,
    params,
    config=ExecutionConfiguration(allow_cross_shard=True),
)
```

</div>
</ModeTabs>

Each shard then commits on its own, and **there is no two-phase commit**. If one shard fails,
only that shard rolls back: the shards that already committed stay committed. The executor logs
that outcome loudly, naming the shards, because a partial commit nobody notices is the worst
kind.

Treat it as an escape hatch. Pass it on the one `execute(...)` call that needs it, not as the
executor-wide default, so the risk is visible where it is taken. If a partial commit would need
undoing, use a [saga](/learn/sagas/) instead of one cross-shard action.

[Cross-shard actions](/learn/sharding-strategies/#cross-shard-actions-one-transaction-per-shard-never-atomic-across)
explains what is and is not promised, and how a saga helps.

## Retries

By default, a call that fails with `StaleRecordError` (it lost a race with another write to the
same row) is tried once more, after 100 ms. To change that, pass your own `retry_configs`:

```python
config = ExecutionConfiguration(
    retry_configs=(
        RetryConfig(on=StaleRecordError, max_retries=3, delay=timedelta(milliseconds=50)),
    ),
)
wallet = executor.execute(None, WalletDepositMoneyAction, params, config=config)
```

- `retry_configs` is an ordered tuple of `RetryConfig(on=..., max_retries=..., delay=...)`.
- `max_retries` and `delay` are required. `max_retries` counts the tries after the first one.
  `delay` is a `timedelta`; a plain number is refused.
- The first `RetryConfig` whose `on` matches the error wins, so put a narrow rule before a broad
  one.
- `on` must name the exact class that is raised: a subclass of it does not match. An error raised
  `from` a matching one (`raise ... from error`) matches too.
- `ExecutionConfiguration.no_retry()` turns retries off.

## Tracing

Every call opens an OpenTelemetry span. It records the action name, the principal and the
outcome, and each retry is an event on it. Inside it, each shard's transaction gets a span of
its own, naming the shard. Ekbatan uses the OpenTelemetry **API only**: if your service registers no
OpenTelemetry SDK, every one of these calls does nothing. See
[Observability](/reference/runtime/observability/).

## Custom event persister

The default persister, `SingleTableJsonEventPersister` (`AsyncSingleTableJsonEventPersister` in
async mode), writes one JSON row per event into the outbox table. You can pass your own as the
executor's `outbox=` argument, to write a different shape: a second table, a different column
layout, encrypted payloads. It still writes in the same transaction.

The protocol is one method, awaited in async mode:

<ModeTabs>
<div slot="sync">

```python
class EventPersister(Protocol):
    def persist_action_events(
        self,
        namespace: str,
        action_name: str,
        started_date: Instant,
        completion_date: Instant,
        action_params: Any,
        model_events: Sequence[ModelEvent],
        shard: ShardIdentifier,
        action_event_id: uuid.UUID,
    ) -> None: ...
```

</div>
<div slot="async">

```python
class AsyncEventPersister(Protocol):
    async def persist_action_events(
        self,
        namespace: str,
        action_name: str,
        started_date: Instant,
        completion_date: Instant,
        action_params: Any,
        model_events: Sequence[ModelEvent],
        shard: ShardIdentifier,
        action_event_id: uuid.UUID,
    ) -> None: ...
```

</div>
</ModeTabs>

It is called inside the transaction that writes the domain rows. A write through the registry
joins that transaction: `registry.manager(shard).connection()` hands back the open transaction,
not a new connection. So whatever your persister writes commits with the domain rows, or not at
all. The default persister writes this way too.

The executor's persister is also there for code outside an action, as `executor.outbox`. A
backfill job replaying old state can call it, instead of building outbox rows by hand.
