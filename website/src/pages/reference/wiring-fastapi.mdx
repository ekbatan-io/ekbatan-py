[Wiring](/reference/wiring/) builds the service itself, with nothing about HTTP. This page connects that
service to FastAPI.

> From [`ekbatan-py-examples/fastapi-wallet-rest-uv-pg/src/fastapi_wallet_rest_pg/api.py`](https://github.com/ekbatan-io/ekbatan-py/tree/main/ekbatan-py-examples/fastapi-wallet-rest-uv-pg/src/fastapi_wallet_rest_pg/api.py).

## Build once, in a lifespan

<ModeTabs>
<div slot="sync">

```python
def create_app(settings: Settings | None = None) -> FastAPI:

    @asynccontextmanager
    async def lifespan(app: FastAPI) -> AsyncIterator[None]:
        # Built and started on a worker thread: `build` runs the migrations and starting
        # registers the jobs, both sync and both waiting on the database - and the sync API
        # is refused on the event loop's own thread.
        service = await asyncio.to_thread(build, settings)
        await asyncio.to_thread(service.start)
        app.state.service = service
        try:
            yield
        finally:
            await asyncio.to_thread(service.close)

    app = FastAPI(title="Wallet", lifespan=lifespan)
```

</div>
<div slot="async">

```python
def create_app(settings: Settings | None = None) -> FastAPI:

    @asynccontextmanager
    async def lifespan(app: FastAPI) -> AsyncIterator[None]:
        # `build` is sync - it runs the migrations - and so is starting the jobs: both on a
        # worker thread, since the sync API is refused on the event loop's own thread.
        service = await asyncio.to_thread(build, settings)
        await asyncio.to_thread(service.start)
        app.state.service = service
        try:
            yield
        finally:
            await service.aclose()     # the async pools close with `aclose()`

    app = FastAPI(title="Wallet", lifespan=lifespan)
```

</div>
</ModeTabs>

Connection pools, the job scheduler and the migrations belong to the whole process, not to one
request. FastAPI runs the `lifespan` once when the server starts, and finishes it when the server
stops. The `try/finally` closes the pools at shutdown, so they are not leaked.

`build()`, `WalletService`, `service.start()` and `service.close()` / `service.aclose()` are the
example's own code, not Ekbatan's API. `build()` creates Ekbatan's objects (the registry, the lock
provider, the job registry and their data sources), and the example's class holds them.
`start()` calls `jobs.start()`. `close()` calls `jobs.stop()`, then closes the lock provider,
closes the data sources and closes the registry. [Startup and shutdown](/learn/startup-and-shutdown/) writes the same lifespan with
those objects themselves.

The lifespan is an `async def`, so it runs on the event loop's thread, where the sync API is
refused with `BlockingCallError`. So building (which runs the migrations) and starting and
stopping the jobs go through `asyncio.to_thread`, as above.

Never create Ekbatan's objects at import time either, as a module-level `service = build()`
would. A server that forks its workers would copy them into each worker, and Ekbatan refuses to
work in a copy (`ForkedProcessError`). See [Startup and shutdown](/learn/startup-and-shutdown/).

`create_app` is a **factory** function, not a module-level `app = FastAPI()`. That way a test can
build its own app against a throwaway database, with settings of its own: the url and login set
with `monkeypatch.setenv`, for that test only. Every example's test does this.

## The dependency, and the trap in it

```python
def service_of(request: Request) -> WalletService:
    service: WalletService = request.app.state.service
    return service


Service = Annotated[WalletService, Depends(service_of)]
```

Then every endpoint takes `service: Service`.

**`Service` must be at module level.** This looks like a style point, and it is not. With
`from __future__ import annotations`, which the example's modules all use, FastAPI looks up each
type annotation among the names defined at **module** level. An `Annotated[...]` alias defined
inside `create_app` is not found there. So FastAPI cannot tell the parameter is a dependency, and
reads it as an unfilled *query parameter* instead.

The symptom is a 422 on every endpoint, naming a field nobody declared.

### Never open a transaction in a dependency

A sync `yield` dependency looks like the place to open one transaction per request:

```python
def in_transaction(service: Service) -> Iterator[None]:     # wrong
    with service.registry.default.transaction():
        yield
```

It does not cover the endpoint. FastAPI runs a sync dependency and a sync endpoint in separate
copies of the request's context, each on a worker thread. So the endpoint finds no transaction:
each of its statements commits on its own, and a failure rolls nothing back. When the
dependency's block ends, in yet another context, Ekbatan raises `TransactionContextError` to say
so. (Python's own error would only say that a token "was created in a different Context".)

Open the transaction where the work runs. Usually that is the action: `executor.execute(...)`
opens and commits its own. Work outside an action opens it in the endpoint:

```python
@app.post("/wallets/{wallet_id}/notes", status_code=204)
def add_note(wallet_id: str, body: NoteRequest, service: Service) -> None:
    with service.registry.default.transaction():
        ...   # every write here is in this one transaction
```

The same holds with `ekbatan.aio`: open it in the endpoint or the action, not in a dependency.
See [The transaction manager](/reference/transaction-manager/#repository-writes-join-automatically).

## With the sync API, a plain `def` endpoint is the right endpoint

<ModeTabs>
<div slot="sync">

```python
@app.post("/wallets", response_model=WalletResponse, status_code=201)
def open_wallet(body: OpenWalletRequest, service: Service) -> WalletResponse:
    return WalletResponse.of(
        service.executor.execute(
            None,
            WalletCreateAction,
            WalletCreateAction.Params(owner_id=body.owner_id, currency=body.currency,
                             initial_balance=body.initial_balance),
        )
    )
```

</div>
<div slot="async">

```python
@app.post("/wallets", response_model=WalletResponse, status_code=201)
async def open_wallet(body: OpenWalletRequest, service: Service) -> WalletResponse:
    return WalletResponse.of(
        await service.executor.execute(
            None,
            WalletCreateAction,
            WalletCreateAction.Params(owner_id=body.owner_id, currency=body.currency,
                             initial_balance=body.initial_balance),
        )
    )
```

</div>
</ModeTabs>

`def`, not `async def`, and with the sync API that is the single most important line on this
page.

The sync API blocks while it waits for the database. FastAPI runs a plain `def` endpoint **in a
thread pool**, so a blocking call there blocks one worker thread and nothing else. Each request
waits on its own thread, and the others carry on.

An `async def` endpoint runs **on the event loop**, and a blocking call there would stop the
entire loop: every other request on that worker, not just this one. Measured: a 0.5 s blocking
call inside an `async def` handler let a background heartbeat tick **5 times, where a free loop
manages about 55**. So Ekbatan refuses: the sync API called on the event loop's thread raises
`BlockingCallError`.

If you need an `async def` endpoint (because something else in it really awaits) and want to keep
the sync API, hand the framework call to a thread, or build the service on `ekbatan.aio` instead
(next section):

```python
wallet = await run_in_threadpool(service.wallet_repository.get_by_id, wallet_id)
```

The example's endpoints are plain `def` throughout, which is why they need no `to_thread`.

**None of this applies under gevent**, where a blocking call yields to other work and costs
nothing. But gevent serves **WSGI**, and FastAPI is ASGI, so a FastAPI service cannot use it. If
your front end is Flask or Django, see the gevent section of
[Concurrency](/reference/runtime/concurrency/).

## `async def` endpoints, on `ekbatan.aio`

The other way: build the request path on the async API, so every endpoint is an `async def` that
awaits. These are the async examples on this page. Nothing blocks the event loop, and under load
it does more work than a thread pool does.

`service.executor` is an `AsyncActionExecutor`, and `service.wallet_repository` an async
repository. Two things change compared with the sync service:

- **The keyed lock comes from `ekbatan.aio.locks`**: `async with locks.acquire(key, max_hold):`
  around `await executor.execute(...)`. Its holder is the task, not the thread.
- **Handlers run after the action, on dispatch's threads.** A handler may extend
  `AsyncEventHandler` and await an executor of its own, on dispatch's handler loop. Fan-out,
  dispatch and the jobs stay on threads, through a sync registry built from the same config file.

[Going async](/learn/async/) walks through it, and
[`fastapi-wallet-rest-uv-async-pg`](https://github.com/ekbatan-io/ekbatan-py/tree/main/ekbatan-py-examples/fastapi-wallet-rest-uv-async-pg) runs
it.

## Cap the load, in both modes

Two caps, the same whichever API the endpoints use:

- **A 503 for a full pool.** The connection pool limits how many requests can use the database at
  once. A request that waits longer than `poolTimeout` (`pool_timeout` in code) for a connection
  fails with SQLAlchemy's `TimeoutError`, in both modes. Map that error, once, to a 503 with a
  `Retry-After` header. Unmapped, the caller gets a 500, and with the default timeout only after
  30 seconds.
- **A cap at the door.** `uvicorn --limit-concurrency 50` answers 503 itself past 50 open
  requests, before they reach the app. Keep it a small multiple of the pool.

## Map the framework's errors once

```python
@app.exception_handler(EntityNotFoundError)
async def _missing(request: Request, error: Exception) -> JSONResponse:
    return JSONResponse(status_code=404, content={"detail": str(error)})


@app.exception_handler(ValidationError)
async def _rejected(request: Request, error: Exception) -> JSONResponse:
    return JSONResponse(status_code=400, content={"detail": str(error)})


@app.exception_handler(StaleRecordError)
async def _lost_a_race(request: Request, error: Exception) -> JSONResponse:
    # 409, not 500. The caller did nothing wrong; the right response is to try again.
    return JSONResponse(status_code=409, content={"detail": "the wallet changed; retry"})
```

The framework raises different errors so that a caller can tell a bad request from a lost race
from an unreachable database. Each calls for a different response, which is what a status code
is for. Map them once here, rather than catching them in every endpoint.

**A Starlette exception handler must `return` a response, not `raise` one.** An exception raised
from inside a handler is not caught again and becomes a 500, which is the exact opposite of what
these are for. The signature returning `JSONResponse` is the reminder.

Why 409 for `StaleRecordError`? Two deposits raced, the loser's version check failed, and the
caller did nothing wrong. (By then the executor has already retried once, its default.) A 500
would page somebody.

## Keyed locks across a request

<ModeTabs>
<div slot="sync">

```python
lease = service.locks.try_acquire(f"wallet:{wallet_id}", LOCK_WAIT, LOCK_HOLD)
if lease is None:
    raise HTTPException(status_code=503, detail="that wallet is busy; retry",
                        headers={"Retry-After": "1"})
with lease:
    return WalletResponse.of(service.executor.execute(None, WalletDepositMoneyAction, params))
```

</div>
<div slot="async">

```python
lease = await service.locks.try_acquire(f"wallet:{wallet_id}", LOCK_WAIT, LOCK_HOLD)
if lease is None:
    raise HTTPException(status_code=503, detail="that wallet is busy; retry",
                        headers={"Retry-After": "1"})
async with lease:
    return WalletResponse.of(await service.executor.execute(None, WalletDepositMoneyAction, params))
```

</div>
</ModeTabs>

Three things here.

**The lease spans `execute`, not just the read.** It has to cover `perform()` *and* the
executor's commit, or the race it exists to prevent reopens in the gap. The `with` block holds
the lease for exactly that long and lets go however the block ends. In async mode the lock is
from `ekbatan.aio.locks`, its holder is the request's task, and waiting for it does not block
the loop.

**`try_acquire`, not `acquire`.** An HTTP request must not wait forever. If the lock cannot be
taken within `LOCK_WAIT`, `try_acquire` returns `None`. That means someone else holds the lock,
not that anything failed, and the two are kept apart on purpose. A 503 with `Retry-After` tells
the client to come back later; it is not a bug report.

**Why lock at all, when optimistic locking already works?** It does work - a concurrent deposit
loses the version check and raises. But it is correct by *failing*. Taking the key first means
the second caller waits and then succeeds, which is what anyone depositing into a busy wallet
wants. Different wallets take different keys and never contend.

`LOCK_HOLD`, the `max_hold` argument, is not a timeout on your code. It is the promise that the
lock is released even if this process dies holding it. Set it above the worst case for the work
inside.

## Do not return the model

```python
class WalletResponse(BaseModel):
    id: UUID
    owner_id: UUID
    currency: str
    balance: Decimal
    state: str
```

`Wallet` carries a version, timestamps and an event list. A client needs none of them and should
not break when one changes.

One more thing: **quantize money at the boundary**, that is, give it a fixed number of decimal
places in the response. What an action *returns* is the model it staged, at whatever scale the
caller passed in. What a later read returns has the column's scale. So `POST /wallets` answers
`100.00` and `GET /wallets/{id}` answers `100.0000` for the same untouched wallet. Both are
correct and harmless, and exactly the sort of thing that becomes a bug report. How many decimal
places to show is the API's choice, so settle it once in the response model, rather than making
the write path read the row back.

## Testing

```python
with TestClient(create_app(settings)) as client:
    ...
```

The `with` matters: `TestClient` only runs the lifespan inside a `with` block. Without it,
`app.state.service` is never set, and every request fails on the dependency. This is the same in
both modes. In async mode, a test that calls the service directly, not through HTTP, must await
on the app's own loop, through `client.portal`.
