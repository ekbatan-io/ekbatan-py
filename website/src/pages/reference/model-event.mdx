## Type signature

```python
@dataclass(frozen=True, kw_only=True)
class WalletMoneyDepositedEvent(ModelEvent["Wallet"]):
    amount: Decimal
    new_balance: Decimal
```

The class line names the model the event is about; the constructor takes that model's id:

```python
WalletMoneyDepositedEvent(model_id=str(self.id), amount=amount, new_balance=new_balance)
```

The type argument fixes `model_name` once per event class, so no call site passes it. It is a
string because events are declared before the model that emits them, as in `ShardedId["Wallet"]`.

A missing or blank `model_id` is refused when the event is made, and so is an event class that
names no model.

## How events become outbox rows

```
wallet.deposit(...)            attaches the event to the new wallet
   │
plan.update(wallet)            the event rides along with the row
   │
the executor commits           one INSERT into events, per event
```

The row's columns are filled from three places: the **action** supplies `action_id`,
`action_name`, `action_params` and the timestamps; the **event** supplies `model_id`,
`model_type`, `event_type` and `payload`. The persister writes them as the event carries them -
it does not look at the model the event was attached to.

So a consumer correlates without opening the payload, and routes on `event_type` without
parsing it.

## Writing an event

Put in it what a consumer needs to act, and nothing else:

```python
@dataclass(frozen=True, kw_only=True)
class WalletCreatedEvent(ModelEvent["Wallet"]):
    owner_id: UUID
    currency: str
    initial_balance: Decimal
```

A delivery address, a request id, a feature flag — those belong to the invocation, not to the
fact. They travel in the action's parameters, and a handler reads them off the envelope.

Name them in the past tense: an event describes something that already happened.

An event is a value: two are equal when they are the same class, about the same model
(`model_id`), with the same fields. The same deposit into two different wallets is two events,
not one.

## Serialisation

The payload is JSON, read back into the same class from the dataclass's own annotations.
Nothing extra is needed for that round trip.

- **Keys are camelCase**, in declaration order, after `modelId` and `modelName`:
  `{"modelId": ..., "modelName": "Wallet", "amount": 10.00, "newBalance": 110.00}` for `amount`
  and `new_balance`.
- **Decimals are JSON numbers** (`10.50`, `1E+3`), and are read back as `Decimal` with their
  scale. MySQL's `JSON` column keeps a fraction as a double.
- **Dates and times are ISO-8601 text**, each as its field is declared (`ekbatan.time`): an
  `Instant` as `"2025-01-01T00:00:00.120Z"`, a `LocalDateTime` with no offset, an
  `OffsetDateTime` with its own; a field declared plain `datetime` is refused when the action
  runs, and nothing is saved. `bytes` as base64. See
  [Models and entities](/learn/models-and-entities/#modelevent) for the full table, and
  [time kinds](/reference/multi-database/#time-kinds).

A Java service built on Ekbatan reads and writes this same JSON - see
[Running beside a Java service](/reference/beside-java/#event-payloads).

## Attaching one

```python
return self.copy().with_event(WalletMoneyDepositedEvent(...)).balance(new_balance).build()
```

Inside the model's own method, always — that is the whole discipline. Events are produced in the
model, staged by the action, and persisted by the framework.

## Consumers

- **In process** — the dispatch job rebuilds the typed event and calls your handler. See
  [Local event handlers](/reference/events/local-event-handler/).
- **Through a broker** — Debezium tails the table. See [Streaming](/reference/events/streaming/).
- **By hand** — `ActionEvent.from_row(...)` in `ekbatan.streaming` is the consumer-side view of
  an outbox row.
