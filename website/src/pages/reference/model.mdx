The same class in both modes, sync and async: nothing on a model waits on the database.

## Type signature

```python
@dataclass(frozen=True, kw_only=True)
class Wallet(Model[ShardedId["Wallet"], WalletState, WalletBuilder]):
    owner_id: UUID
    currency: str
    balance: Decimal

    def validate(self) -> None:
        if self.balance < 0:
            raise ValidationError("balance cannot be negative")
```

Three type parameters:

| Parameter | Meaning | Typical value |
|---|---|---|
| `ID` | the identifier type | `Id[T]`, or [`ShardedId[T]`](/reference/sharding/) when the row lives on one of several databases |
| `S` | the state enum for this model's lifecycle | `WalletState` (`OPENED`, `CLOSED`, `DELETED`); `GenericState` by default |
| `B` | the typed builder `copy()` and `builder()` return | `WalletBuilder` - see [Builder API](#builder-api) |

The model class itself needs no parameter: the base's methods return `Self`, so `next_version()`
on a `Wallet` is typed as a `Wallet`.

What the base contributes:

```python
class Model[ID, S: Enum, B: ModelBuilder = ModelBuilder](Persistable[ID, S, B], ABC):
    id: ID
    state: S
    version: int                           # required, 1 or more
    created_date: Instant                  # required
    updated_date: Instant | None = None    # falls back to created_date
    events: tuple[ModelEvent, ...] = ()

    @abstractmethod
    def validate(self) -> None: ...        # required: the model's own rules
    @property
    def is_model(self) -> bool: ...        # always True on Model
    @property
    def is_deleted(self) -> bool: ...
    @classmethod
    def builder(cls) -> B: ...             # B is the third argument you pass
    def copy(self) -> B: ...
    def next_version(self) -> Self: ...
```

`created_date` is **required**: `build()` refuses a model without it. A model records
something that happened, and when it happened is part of the record rather than a column the
framework backfills afterwards. Pass `self.clock.instant()` from the action, so a test with a fixed
clock gets a fixed date:

```python
Wallet.create_wallet(shard, owner_id, currency, initial_balance, self.clock.instant())
```

`updated_date` falls back to `created_date` — a row that has never changed was last updated when
it was created. Both are kept exactly as given - no zone added, removed or moved - and stored
that way ([What you give is what is stored](/reference/multi-database/#what-you-give-is-what-is-stored)). Both are typed `Instant` ([time kinds](/reference/multi-database/#time-kinds)): from `clock.instant()` they are UTC
with no zone attached, so `wallet.created_date` compares with the
clock and equals the value read back from any database.

**Nothing moves `updated_date` but you.** Neither the plan nor the repository touches it on a
write. Move it on the changes where it means something:

```python
def deposit(self, amount: Decimal, at: Instant) -> Wallet:
    return (
        self.copy()
        .with_event(WalletMoneyDepositedEvent(model_id=str(self.id), amount=amount, new_balance=self.balance + amount))
        .balance(self.balance + amount)
        .updated_date(at)
        .build()
    )
```

The trade is worth knowing rather than discovering: a column named `updated_date` does not move
on its own, and a row you never mark still reads as last-updated-when-created. That is the cost
of a framework that will not rewrite a column your application set — which is the property that
makes the column usable for recording when *your* change happened.

The **version** is different, and does move on its own: the repository increments it inside the
write, under `WHERE version = ?`, because that is the optimistic lock rather than a convenience.

`Entity` has neither. Something that needs to know when it last changed almost
certainly has changes worth telling the rest of the system about, which makes it a `Model`.


### Required, and optional

The base refuses `None` for any field whose annotation does not admit it — **including the ones
you declare**. `owner_id: UUID` is required; `note: str | None` is not.

| field | `None` |
|---|---|
| `currency: str` | refused |
| `note: str \| None` | accepted |

The base reads the rule off the dataclass's own annotations, so there is no null check to write
in each model, and none to forget for a field added later.

The annotations have to be readable while the program runs. A type imported only under
`if TYPE_CHECKING:` is not, and creating such an object is refused with a `TypeError` that
names it, rather than leaving the class's fields unchecked.

`events` is excluded from equality. Two readers of one database row are looking at the same
wallet whether or not one of them is mid-change.

`frozen=True` makes it immutable; `kw_only=True` is what makes the inheritance legal at all —
without it a subclass field with no default would follow the base's defaulted fields and Python
would refuse the class. Both are required, and a `@dataclass` without them fails at class
definition rather than at runtime, which is the right time.

Four things are refused at construction: a null `id`, a null `state`, a null `version` and a
`version` below 1. Without them the mistake surfaces as an `IntegrityError` from inside a batched
insert, naming a column and a driver, several frames from the line that made it. `version`
matters most — it is the optimistic-locking primitive, and a row inserted at 0 quietly starts one
behind whatever reads it back.

## `validate()`: the model's own rules

Every model defines `validate(self) -> None`, the one place for its rules beyond its types. Ekbatan
runs its own checks first - the `None` checks above, `version` at least 1, `updated_date` falling
back, `events` made a tuple - and then `validate()`, every time a model is made: `build()`,
`copy()...build()`, the constructor, `evolve()`, `without_events()`, `next_version()`, and
`from_record` when a repository reads a row.

- **Required.** A model without it is refused when its class is defined: *"Wallet must define
  validate(); write `pass` if it has no rules beyond its types"*. mypy and pyright flag the
  line that makes one. No rules of its own: `pass`.
- **Raise `ValidationError`** (from `ekbatan.errors`) - the convention. Any exception reaches
  whoever made the row.
- **A base of your own** that real models inherit from lists `ABC`:
  `class AuditedModel[ID, S: Enum](Model[ID, S], ABC)`. The rule applies to the models below it.
- **An own `__post_init__` is safe.** Ekbatan wraps it when the class is defined: its checks, then
  your `__post_init__`, then `validate()` - with or without `super().__post_init__()`, and nothing
  runs twice.

See [Learn → Models and entities](/learn/models-and-entities/#validate-the-models-own-rules).

The companion shape, [`Entity`](/reference/entity/), is for state the persistence layer needs to
track but whose changes do not belong in the event stream — caches, lookup tables, audit-only
side effects.

## Construction and mutation

A change returns a **new** model:

```python
def deposit(self, amount: Decimal) -> Wallet:
    if amount <= 0:
        raise ValidationError(f"deposit amount must be positive, got {amount}")
    new_balance = self.balance + amount
    return (
        self.copy()
        .with_event(WalletMoneyDepositedEvent(model_id=str(self.id), amount=amount, new_balance=new_balance))
        .balance(new_balance)
        .build()
    )
```

- **`copy()`** returns a builder pre-populated from this instance, so domain code names only the
  fields that changed. Typed as `B`, the builder you named on the class line — see
  [Builder API](#builder-api).
- **`evolve(**changes)`** is the framework's own shorthand. Domain code should prefer `copy()`,
  so every change in an application reads the same way.

Immutability is not decoration: it is what makes two-phase execution safe. The plan collects
references to snapshots, so a partially applied change cannot exist.

## Events

`with_event(event)` attaches one. They ride along with the model into the plan and become outbox
rows in the commit. Reading a model back from the database returns it with **no** events — what
comes back is the database's view of a row, and events are not a column.

## Optimistic locking

Every model carries `version`, and every update carries `WHERE version = ?`. If another
transaction got there first, zero rows match and `StaleRecordError` unwinds the action, which
retries once by default.

**The write path takes no pessimistic row locks, ever.** That is correct by *failing*: when
losing the race is the wrong outcome, take a [keyed lock](/reference/keyed-locks/) first so the
second caller waits and then succeeds.

## Soft deletion

`delete()` on the model flips `state` to `DELETED` and emits an event like any other change.
Every inherited read filters those rows out; a statement you write yourself does not, so add
`state != 'DELETED'` when you drop to SQL. There is no `delete()` on the repository — a row that
silently stopped existing would leave every published event with nothing on the other side.

## Equality

Two models are equal when they are **the same row at the same version**: the same class, and the
same `id`, `state`, `version`, `created_date` and `updated_date`. The business fields take no part, and neither do events, so two wallets with one id and
version are equal even if one copy says the balance is different. The hash is the id's alone, so
any model can go in a set or be a dict key, list and dict fields included.

That is how Python compares a saved record too — Django by primary key, SQLAlchemy by one object
per row. Comparing every field is for value objects, which have no identity of their own.

It holds however the model is declared: `@dataclass(frozen=True)` would write a whole-row `==` of
its own, so the framework hands each model this one as it is defined. A model that writes its own
`__eq__` keeps it. To check what a read returned field by field, compare the fields.

## Builder API

| | model | entity |
| --- | :-: | :-: |
| `id(...)` · `state(...)` | yes | yes |
| `version(...)` · `with_initial_version()` · `increase_version()` | yes | yes |
| `copy_base(other)` · `set(**changes)` | yes | yes |
| `with_event(...)` · `events(...)` | yes | — |
| `created_date(...)` · `updated_date(...)` | yes | — |

The runtime builder resolves setters by name, so a checker sees only `__getattr__` and
`.balance("oops")` type-checks. Generate a typed one — `python -m ekbatan.codegen myapp.model
--out myapp/builders.py` — and commit it: it is derived from source you already have.

**Name the builder on the class line.** It is the third type argument, and `copy()` and
`builder()` both return it:

```python
class Wallet(Model[ShardedId["Wallet"], WalletState, WalletBuilder]):
    balance: Decimal
```

Leave it out and both refuse at the call, with a message naming the two ways to make one. There
is no compile step to catch it earlier.

The base writes `copy()` for you - a dataclass knows its own fields - so the class line is the
one place left to say which builder it returns.

Generated or hand-written makes no difference; by hand is better where a setter needs a
conditional default. `ModelBuilder(Wallet)` stays reachable by name for a model defined inside a
test; what is closed is reaching the untyped builder *through a model*. `evolve()` is
unaffected.
