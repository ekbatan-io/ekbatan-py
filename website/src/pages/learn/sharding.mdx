The claim this page makes is narrow and testable: **going from one database to two changes the
configuration and the model's id type, and nothing else.** Your actions, your repository
queries and your HTTP layer stay as they are.

[`fastapi-wallet-rest-uv-sharded-pg`](https://github.com/ekbatan-io/ekbatan-py/tree/main/ekbatan-py-examples/fastapi-wallet-rest-uv-sharded-pg)
is this page, running.

## 1. Change the model's ID type

```python
@dataclass(frozen=True, kw_only=True)
class Wallet(Model[ShardedId["Wallet"], WalletState, WalletBuilder]):
    owner_id: UUID
    currency: str
    balance: Decimal
```

`ShardedId` rather than `Id`. The `(group, member)` pair is packed into 14 bits of the UUID
itself, inside the `rand_b` field of a UUIDv7:

```
┌────────────────────────────────────────────────────────────────┐
│ MSB: [48-bit timestamp][4-bit version=7][12-bit rand_a]         │
│ LSB: [2-bit variant][8-bit GROUP][6-bit MEMBER][48-bit rand]    │
└────────────────────────────────────────────────────────────────┘
```

**The shard is recoverable from the id, with no lookup.** A request arrives with a wallet id; the
framework reads the bits, finds the database, opens the transaction. No directory service, no
sticky sessions.

The layout is fixed, so every service that reads it agrees - including a Java service built on
Ekbatan, which puts the shard in the same bits (see
[Running beside a Java service](/reference/beside-java/#ids)).

## 2. Pick the shard at creation

The shard is bonded to the row for its lifetime, so it is chosen once, at creation. The model's
factory takes a `ShardIdentifier` and hands it to `generate`:

```python
@staticmethod
def open(*, shard: ShardIdentifier, owner_id: UUID, currency: str,
         opening_balance: Decimal) -> "Wallet":
    wallet_id = ShardedId[Wallet].generate(shard)       # the shard bits live in the id forever
    return (
        WalletBuilder()
        .id(wallet_id)
        .state(WalletState.OPENED)
        .owner_id(owner_id)
        .currency(currency)
        .balance(opening_balance)
        .with_event(WalletOpenedEvent(model_id=str(wallet_id), owner_id=owner_id,
                                      currency=currency, opening_balance=opening_balance))
        .build()
    )
```

Then the action decides *which* shard, from business properties:

<ModeTabs>
<div slot="sync">

```python
class OpenWalletAction(Action[OpenWalletParams, Wallet]):
    def perform(self, principal: str | None, params: OpenWalletParams) -> Wallet:
        shard = MEXICO if params.country == "MX" else GLOBAL
        return self.plan.add(
            Wallet.open(
                shard=shard,
                owner_id=params.owner_id,
                currency=params.currency,
                opening_balance=params.opening_balance,
            )
        )
```

</div>
<div slot="async">

```python
class OpenWalletAction(AsyncAction[OpenWalletParams, Wallet]):
    async def perform(self, principal: str | None, params: OpenWalletParams) -> Wallet:

                owner_id=params.owner_id,
                currency=params.currency,
                opening_balance=params.opening_balance,

```

</div>

**That conditional is the only line in the whole application that knows there is more than one
database.** Every other action, every endpoint, and every test that does not assert on placement
is unchanged.

It is also irreversible. A row cannot move between shards, because moving it would change its
id, and its id is what everything else refers to it by. Choosing on `country` means a customer
who relocates keeps their original shard — which is usually right, since the reason the shard
existed was where the data is allowed to live at the time it was created. If it is not right for
you, that is a decision to make here rather than a migration to plan later.

## 3. Wire the second database

```python
from ekbatan.sharding import ShardIdentifier

GLOBAL = ShardIdentifier(0, 0)      # prints as "0:0"
MEXICO = ShardIdentifier(1, 0)
```

A `(group, member)` pair. Group is the **policy** axis - where data is *allowed* to live. Member
is the **capacity** axis - how many writes one database can take. See
[sharding strategies](/learn/sharding-strategies/) for why those are separate.

```python
layout = ShardingConfig(
    default_shard=GLOBAL,
    groups=(
        ShardGroupConfig(group=0, name="global", members=(
            ShardMemberConfig(member=0, configs={"primaryConfig": DataSourceConfig(url=global_url)}),
        )),
        ShardGroupConfig(group=1, name="mexico", members=(
            ShardMemberConfig(member=0, configs={"primaryConfig": DataSourceConfig(url=mexico_url)}),
        )),
    ),
)
registry = DatabaseRegistry.from_config(layout)
# async mode: the same layout, AsyncDatabaseRegistry.from_config(layout) from ekbatan.aio
```

That is the whole configuration change. `migrate(layout, MIGRATIONS)` now visits both, in
configuration order, stopping at the first failure and naming what had already succeeded.

## 4. Spin up the second database

Two databases, not two schemas in one — the point is separate capacity, and a second schema
shares the first one's connections, WAL and CPU.

```yaml
services:
  wallets-global:
    image: postgres:17
    environment: { POSTGRES_DB: wallets, POSTGRES_PASSWORD: dev }
    ports: ["5432:5432"]
  wallets-mexico:
    image: postgres:17
    environment: { POSTGRES_DB: wallets, POSTGRES_PASSWORD: dev }
    ports: ["5433:5432"]
```

Then migrate both with the one call — `migrate(layout, MIGRATIONS)` — **before anything opens a
pool**. Every shard gets the same schema, including the framework's own tables: each database
carries its own outbox, and an event is written to the database whose row it describes.


</div>
</ModeTabs>

The row is only on that database, and so is its event:

```bash
psql -p 5433 wallets -c "SELECT count(*) FROM wallets"   # 1
psql -p 5432 wallets -c "SELECT count(*) FROM wallets"   # 0
psql -p 5433 wallets -c "SELECT count(*) FROM events"    # 1
```

`wallets.get(mx.id)` finds it with no lookup table and no extra query: the shard was read out of
the id. `wallets.find_where(...)` has no id to read, so it asks both.

## 6. (Optional) Cross-shard transfer

Two wallets on two databases cannot be moved in one transaction. Nothing can do that; there is
no atomic commit across databases to have.

Asking for it anyway is refused:

<ModeTabs>
<div slot="sync">

```python
executor.execute(TransferAction, params)      # raises CrossShardError
```

</div>
<div slot="async">

```python
await executor.execute(TransferAction, params)      # raises CrossShardError
```

</div>
</ModeTabs>

You have two honest answers. Opt in per call, and accept that each shard commits on its own:

<ModeTabs>
<div slot="sync">

```python
executor.execute(
    TransferAction,
    params,
    config=ExecutionConfiguration(allow_cross_shard=True),
)
```

</div>
<div slot="async">

```python
await executor.execute(
    TransferAction,
    params,
    config=ExecutionConfiguration(allow_cross_shard=True),
)
```

</div>
</ModeTabs>

The executor then opens **one transaction per shard**. A failure rolls back only its own shard;
the ones that already committed stay committed, and the framework logs that loudly, naming them.
That is the [dual-write trap](/learn/the-dual-write-trap/) again, with two shards of your own
database standing in for the database and the broker.

Or write it as a [saga](/learn/sagas/): one action per shard, chained through the outbox, with a
compensating action if a later step fails. Slower to write, and the only version that recovers
from a partial failure without a human.

Prefer opting in **per call** rather than in a builder, so the risk is visible where the risk is
taken.

## What just happened

- `wallets.get(wallet_id)` — routes by the id's bits.
- `wallets.find_where(...)` — has no id to route by, so it **scatters** across every shard.
- Every action body. Every endpoint. Every test that does not assert on placement.

**A predicate read hits every shard.** In sync mode the shards are visited one at a time, so
latency is the sum - invisible on two shards, the first thing you would feel on eight. In async
mode they are asked at the same time, so it is the slowest shard.

**A cross-shard action is refused** unless you pass `allow_cross_shard=True`, and then each shard
commits independently. If a partial commit would need compensating, you want a
[saga](/learn/sagas/).
