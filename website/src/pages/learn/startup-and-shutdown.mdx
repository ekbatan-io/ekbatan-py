ekbatan is a library: a handful of objects your code creates. A few of them hold database
connections or threads, and one rule covers every server:

**Create ekbatan's objects in your app's startup code and close them in its shutdown code -
never at import time.**

In a FastAPI app the startup and shutdown code is the lifespan; in a plain worker, the top and
the bottom of `main()`. Normal code uses the sync API; `async def` code uses `ekbatan.aio`.

## The objects, and what to do with each

| object | what it holds | at startup | at shutdown |
| --- | --- | --- | --- |
| `DatabaseRegistry` | a connection pool per shard, and per replica | `DatabaseRegistry.from_config(layout)`, or `DatabaseRegistry.builder()...build()` | `registry.close()` - or use it as `with registry:` |
| `AsyncDatabaseRegistry` (`ekbatan.aio`) | the same, async pools | `AsyncDatabaseRegistry.from_config(layout)`, or `.builder()...build()` | `await registry.aclose()` - or `async with registry:` - on the event loop it was used on |
| an engine from `engine_for(...)` or `async_engine_for(...)` | one pool - for the jobs, the locks, or anything else beside the registry | `engine_for(member.config_for("jobsConfig"))` | `engine.dispose()`; async: `await engine.dispose()`. It is yours: nothing else disposes it, unless you hand it to a `TransactionManager` in a registry, whose `close()` does |
| `PostgresKeyedLockProvider`, `MySQLKeyedLockProvider`, `MariaDBKeyedLockProvider`; async: `AsyncPostgresKeyedLockProvider` and the rest, in `ekbatan.aio.locks` | one connection from the engine you give it for each lease held | `PostgresKeyedLockProvider.builder().engine(lock_engine).build()` | `locks.close()`, then dispose `lock_engine`. `close()` does nothing today; a lease still held stays held until released or its `max_hold` runs out |
| `RedisKeyedLockProvider` (`ekbatan.locks.redis`), `AsyncRedisKeyedLockProvider` (`ekbatan.aio.locks.redis`) | nothing of its own - it uses the Redis client you give it | `RedisKeyedLockProvider.builder().client(client).build()` | `locks.close()`, then close the client yourself: `client.close()`; async: `await client.aclose()` |
| `JobRegistry` (`ekbatan.distributedjobs`) | the scheduler's polling and worker threads, on the engine you give it | `job_registry().engine(jobs_engine).with_jobs([...]).build()`, then `jobs.start()` | `jobs.stop()` - running jobs finish first, up to `shutdown_max_wait`. `with jobs:` starts and stops it. The engine is still yours to dispose |
| `HandlerLoop` (`ekbatan.events`) - only if an event handler or a job's work is `async def` | an event loop on a thread of its own | `HandlerLoop()`, handed to `EventHandlingJob.builder().handler_loop(loop)` | after `jobs.stop()`: close what was used on it, on it - `loop.run(registry.aclose())` - then `loop.close()` |
| `EventFanoutJob`, `EventHandlingJob` (`ekbatan.events`) | thread pools, made the first time they run | their builders, then into `with_jobs([...])` | nothing: `jobs.stop()` stops them, and their threads go at exit. `job.fanout.close()` / `job.dispatch.close()` let them go sooner |
| repositories, `ActionExecutor` / `AsyncActionExecutor`, actions, `RepositoryRegistry`, `ActionRegistry`, `EventHandlerRegistry` | nothing - they use the registry | create them | nothing |

Running the migrations, `migrate(layout, MIGRATIONS)` from `ekbatan.migrations`, is a call, not
an object: run it at startup before anything opens a connection.

Two mistakes are refused with a clear error rather than left to fail later in a strange way:

| error | when | the fix |
| --- | --- | --- |
| `ForkedProcessError` | one of the objects above that holds connections or threads - a registry, a lock provider, a job registry, a handler loop - is used in a process that `fork()` copied it into | create it in the process that uses it: in the lifespan, or at the top of the worker's `main()`, never at import time |
| `BlockingCallError` | the sync API - a transaction, a connection, a repository, the executor, a migration run - is called on an event loop's thread, inside `async def` | use `ekbatan.aio`; or make the endpoint a plain `def`; or call it with `await asyncio.to_thread(...)` |

Both only refuse. Nothing is reconnected, reset or moved to a thread behind your back.

## A FastAPI app

The lifespan is `async def`, so it runs on the event loop's thread. The sync calls in it that
wait on the database - the migrations, `jobs.start()`, `jobs.stop()`, closing a sync registry -
go through `asyncio.to_thread`. `your_jobs` stands for your own function returning the jobs to
run, built on the registry.

<ModeTabs>
<div slot="sync">

```python
import asyncio
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager
from pathlib import Path

from fastapi import FastAPI

from ekbatan import DatabaseRegistry, engine_for
from ekbatan.config_files import load_ekbatan_config
from ekbatan.distributedjobs import job_registry
from ekbatan.locks import PostgresKeyedLockProvider
from ekbatan.migrations import migrate

CONFIG_FILE = Path("ekbatan.yaml")
MIGRATIONS = Path("migrations")


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    config = load_ekbatan_config(CONFIG_FILE)
    layout = config.sharding
    member = layout.groups[0].members[0]

    # Startup.
    await asyncio.to_thread(migrate, layout, MIGRATIONS)
    registry = DatabaseRegistry.from_config(layout)  # opens no connection yet
    lock_engine = engine_for(member.config_for("lockConfig"))
    locks = PostgresKeyedLockProvider.builder().engine(lock_engine).build()
    jobs_engine = engine_for(member.config_for("jobsConfig"))
    jobs = (
        job_registry()
        .engine(jobs_engine)
        .with_jobs(your_jobs(registry))
        .with_config(config.jobs)
        .build()
    )
    await asyncio.to_thread(jobs.start)
    # The repositories and the ActionExecutor are built on `registry` and hold nothing.
    app.state.registry = registry
    app.state.locks = locks
    try:
        yield
    finally:
        # Shutdown: stop taking work first, then close what the work runs on.
        await asyncio.to_thread(jobs.stop)
        locks.close()
        lock_engine.dispose()
        jobs_engine.dispose()
        await asyncio.to_thread(registry.close)
```

The endpoints use an `AsyncDatabaseRegistry` on the app's own loop. The jobs poll on threads, so
they get a sync `DatabaseRegistry` over their own pool.

```python
import asyncio
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager
from pathlib import Path

from fastapi import FastAPI

from ekbatan import DatabaseRegistry, TransactionManager, engine_for
from ekbatan.aio import AsyncDatabaseRegistry, async_engine_for
from ekbatan.aio.locks import AsyncPostgresKeyedLockProvider
from ekbatan.config_files import load_ekbatan_config
from ekbatan.distributedjobs import job_registry
from ekbatan.migrations import migrate

CONFIG_FILE = Path("ekbatan.yaml")
MIGRATIONS = Path("migrations")


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    config = load_ekbatan_config(CONFIG_FILE)
    layout = config.sharding
    member = layout.groups[0].members[0]

    # Startup.
    await asyncio.to_thread(migrate, layout, MIGRATIONS)
    registry = AsyncDatabaseRegistry.from_config(layout)  # for the endpoints
    lock_engine = async_engine_for(member.config_for("lockConfig"))
    locks = AsyncPostgresKeyedLockProvider.builder().engine(lock_engine).build()
    jobs_engine = engine_for(member.config_for("jobsConfig"))
    jobs_registry = (
        DatabaseRegistry.builder()
        .with_default_database(TransactionManager(layout.default_shard, jobs_engine))
        .build()
    )
    jobs = (
        job_registry()
        .engine(jobs_engine)
        .with_jobs(your_jobs(jobs_registry))
        .with_config(config.jobs)
        .build()
    )
    await asyncio.to_thread(jobs.start)
    app.state.registry = registry
    app.state.locks = locks
    try:
        yield
    finally:
        # Shutdown: stop taking work first, then close what the work runs on.
        await asyncio.to_thread(jobs.stop)
        locks.close()
        await lock_engine.dispose()
        await asyncio.to_thread(jobs_registry.close)  # disposes jobs_engine too
        await registry.aclose()
```

**If an event handler is `async def`**, it runs on a `HandlerLoop`, and what it awaits - its own
`AsyncDatabaseRegistry` and executor - belongs to that loop. Add to the lifespan above:

```python
    # Startup, before building the jobs:
    handler_loop = HandlerLoop()  # from ekbatan.events
    handler_registry = AsyncDatabaseRegistry.from_config(layout)  # used only on handler_loop
    # ... the handlers' executor on handler_registry, and
    # EventHandlingJob.builder()...handler_loop(handler_loop)...build() among your jobs

    # Shutdown, right after jobs.stop():
    await asyncio.to_thread(handler_loop.run, handler_registry.aclose())
    await asyncio.to_thread(handler_loop.close)
```

## A plain worker

A job worker, a consumer, a script. Everything is created at the top of `main()`, not at import
time, and closed at the bottom:

<ModeTabs>
<div slot="sync">

```python
import signal
import threading
from pathlib import Path

from ekbatan import DatabaseRegistry, engine_for
from ekbatan.config_files import load_ekbatan_config
from ekbatan.distributedjobs import job_registry
from ekbatan.migrations import migrate

CONFIG_FILE = Path("ekbatan.yaml")
MIGRATIONS = Path("migrations")


def main() -> None:
    config = load_ekbatan_config(CONFIG_FILE)
    layout = config.sharding
    migrate(layout, MIGRATIONS)
    registry = DatabaseRegistry.from_config(layout)
    jobs_engine = engine_for(layout.groups[0].members[0].config_for("jobsConfig"))
    jobs = (
        job_registry()
        .engine(jobs_engine)
        .with_jobs(your_jobs(registry))
        .with_config(config.jobs)
        .build()
    )

    stopping = threading.Event()
    signal.signal(signal.SIGTERM, lambda *_: stopping.set())  # a container stop
    jobs.start()
    try:
        stopping.wait()  # until SIGTERM, or Ctrl-C
    finally:
        jobs.stop()  # running jobs finish first, up to shutdown_max_wait
        jobs_engine.dispose()
        registry.close()
```

</div>

The worker's own work is `async def` and runs on a `HandlerLoop`, with an `AsyncDatabaseRegistry`
used only there. The jobs still poll on threads, over a sync registry:

```python
import signal
import threading
from pathlib import Path

from ekbatan import DatabaseRegistry, TransactionManager, engine_for
from ekbatan.aio import AsyncDatabaseRegistry
from ekbatan.config_files import load_ekbatan_config
from ekbatan.distributedjobs import job_registry
from ekbatan.events import HandlerLoop
from ekbatan.migrations import migrate

CONFIG_FILE = Path("ekbatan.yaml")
MIGRATIONS = Path("migrations")


def main() -> None:
    config = load_ekbatan_config(CONFIG_FILE)
    layout = config.sharding
    migrate(layout, MIGRATIONS)
    loop = HandlerLoop(name="worker-loop")
    registry = AsyncDatabaseRegistry.from_config(layout)  # used only on `loop`
    jobs_engine = engine_for(layout.groups[0].members[0].config_for("jobsConfig"))
    jobs_registry = (
        DatabaseRegistry.builder()
        .with_default_database(TransactionManager(layout.default_shard, jobs_engine))
        .build()
    )
    jobs = (
        job_registry()
        .engine(jobs_engine)
        .with_jobs(your_jobs(jobs_registry, registry, loop))
        .with_config(config.jobs)
        .build()
    )

    stopping = threading.Event()
    signal.signal(signal.SIGTERM, lambda *_: stopping.set())  # a container stop
    jobs.start()
    try:
        stopping.wait()  # until SIGTERM, or Ctrl-C
    finally:
        jobs.stop()  # waits for the jobs' work, which is waiting on the loop
        loop.run(registry.aclose())  # closed on the loop it was used on
        loop.close()
        jobs_registry.close()  # disposes jobs_engine too
```

</div>
</ModeTabs>

Instead of handling SIGTERM yourself, you can call `.register_shutdown_hook()` on the job
registry builder: SIGTERM and Ctrl-C then stop the jobs, and the process still exits as it would
have.

[`job-worker-uv-pg`](https://github.com/ekbatan-io/ekbatan-py/tree/main/ekbatan-py-examples/job-worker-uv-pg) is that shape, and
[`job-worker-uv-async-pg`](https://github.com/ekbatan-io/ekbatan-py/tree/main/ekbatan-py-examples/job-worker-uv-async-pg) the async one - again
with the objects bundled into the example's own `Worker` class and `build()` function.

## Three things true on every server

**Pools are per process.** Four worker processes hold four of every pool, so the database sees
`4 x (pool_size + job pool + lock pool)` connections. Size per process, then multiply by
processes and by replicas before comparing with `max_connections`. Every process also runs a
job registry; that is fine, since a job runs on exactly one of them.

**SIGTERM.** A container stop sends SIGTERM. An ASGI server - uvicorn, hypercorn, granian,
gunicorn's UvicornWorker - turns it into a lifespan shutdown, where your code calls
`jobs.stop()`; gunicorn's other workers run `worker_exit`. A plain worker has no server to do
that: handle SIGTERM in `main()` as above, or call `register_shutdown_hook()` on the job registry
builder. A job registry started where nothing handles SIGTERM logs one warning saying so - see
[Draining at exit](/reference/jobs/distributed-jobs/#draining-at-exit-on-by-default-and-the-sigterm-half-opt-in).

**Migrations** run once per deploy, ideally as their own step - see
[Migrations](/reference/migrations/). Run at startup instead, `migrate(...)` goes before the
registry is created, and on a worker thread inside a lifespan.

## Under each server

### uvicorn, and `fastapi run`

The lifespan above, as it is. `--workers N` starts N processes, each running the lifespan, so
each creates its own registry, lock provider and job registry, with their own pools. uvicorn
starts its workers fresh rather than by copying the parent, so nothing is shared. Sync endpoints
as plain `def`, async ones on `ekbatan.aio`. `fastapi run` is uvicorn.

### gunicorn with `uvicorn.workers.UvicornWorker`

An ASGI app, so the lifespan runs in every worker - create the registry, lock provider and job
registry there and nothing is copied. gunicorn starts workers with `fork()`, and **`--preload`**
imports your app in the parent before forking: any of them created at import time is then copied
into every worker, and refused there with `ForkedProcessError`. Created in the lifespan,
`--preload` is fine.

### gunicorn with `gthread` or `gevent` workers (Flask, Django, any WSGI app)

WSGI has no lifespan. Create the registry and the job registry in gunicorn's `post_fork` hook,
which runs in each worker after the fork, and stop and close them in `worker_exit`:

```python
# gunicorn.conf.py
from ekbatan import DatabaseRegistry, engine_for
from ekbatan.distributedjobs import job_registry


def post_fork(server, worker):
    import myapp

    member = myapp.LAYOUT.groups[0].members[0]
    myapp.registry = DatabaseRegistry.from_config(myapp.LAYOUT)
    myapp.jobs_engine = engine_for(member.config_for("jobsConfig"))
    myapp.jobs = (
        job_registry()
        .engine(myapp.jobs_engine)
        .with_jobs(myapp.your_jobs(myapp.registry))
        .build()
    )
    myapp.jobs.start()


def worker_exit(server, worker):
    import myapp

    myapp.jobs.stop()
    myapp.jobs_engine.dispose()
    myapp.registry.close()
```

Use the sync API. Under `-k gevent` every blocking call yields, with nothing to change; the
event-loop refusal stays silent because no asyncio loop runs there. `ekbatan.aio` does not run
under gevent's patching. `--preload` is fine as long as none of these objects is created at
import time.

### uwsgi

uwsgi loads the app once and then forks its workers, so a registry or job registry created at
import time is copied. Either set `lazy-apps = true`, so each worker loads the app itself, or
create them in a `uwsgidecorators.postfork` function. Sync API, as for gunicorn's WSGI workers.

### hypercorn (asyncio workers)

An ASGI server with a lifespan: the same as uvicorn. `ekbatan.aio` in `async def` endpoints, a
plain `def` endpoint for the sync API.

### granian

With `--interface asgi` it runs the lifespan in each worker: the same as uvicorn.

### waitress

One process, a pool of threads, WSGI. Create the registry and the job registry at the top of your
`main()`, before `serve(app, ...)`, and stop and close them after. Sync API.

### Celery

The default **prefork** pool forks its child processes from the worker. Create the registry in
each child with the `worker_process_init` signal and close it with `worker_process_shutdown`:

```python
from celery.signals import worker_process_init, worker_process_shutdown

from ekbatan import DatabaseRegistry


@worker_process_init.connect
def create_registry(**_):
    tasks.registry = DatabaseRegistry.from_config(tasks.LAYOUT)


@worker_process_shutdown.connect
def close_registry(**_):
    tasks.registry.close()
```

The repositories and the executor the tasks use are built on that registry, in the same place.
With `--pool threads` or `--pool gevent` there is one process: create it in `worker_init` and
close it in `worker_shutdown`. Tasks use the sync API.

### RQ

`rq worker` forks a new process for every job, so a registry created in the worker is copied into
each job and refused. Run a `SimpleWorker`, which runs jobs in its own process, from your own
`main()` that creates the registry first; or create it inside the job, at the price of new pools
per job.

### Kubernetes replicas

Each pod runs one of the setups above, so everything per process holds per pod: multiply the
pools by replicas too. Jobs need no change - the scheduler picks one runner across all pods. Give
`terminationGracePeriodSeconds` more time than the job registry's `shutdown_max_wait`, so a
stop can let running jobs finish, and run migrations as their own step (a Job or an init
container) rather than in every pod at once.
