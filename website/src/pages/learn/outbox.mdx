Every action's commit is one database transaction that touches as many domain tables as the
action needs **plus** the outbox. They land together, or none of them do.

```
┌──────────────────  ONE DATABASE TRANSACTION  ──────────────────────┐
│   wallets (UPDATE)     orders (INSERT)      events (INSERT)        │
└────────────────────────────────────────────────────────────────────┘
                                │
       commit (every row persists)  —or—  rollback (none of them do)
```

There is no second write to a broker inside the request, and no retry loop trying to keep two
systems in step. After the commit, the rows in the outbox are the record of what happened.
Anything that publishes or handles events does it later, by reading them.

## How rows get there

Every row arrives the same way, and no other way exists:

```text
Model method
  -> returns a new immutable model
  -> with one or more ModelEvents attached

Action.perform()
  -> reads the current state
  -> calls the model method
  -> stages the new model on self.plan

the executor
  -> opens one database transaction
  -> writes the domain row
  -> writes the attached event rows to `events`
  -> commits, or rolls back all of it
```

For a wallet deposit, that first step is:

```python
def deposit(self, amount: Decimal) -> Wallet:
    new_balance = self.balance + amount
    return (
        self.copy()
        .with_event(WalletMoneyDepositedEvent(model_id=str(self.id), amount=amount, new_balance=new_balance))
        .balance(new_balance)
        .build()
    )
```

The event is attached **before** anything is saved, and written **after**. In between it waits
in the action's staged changes, touching nothing. Only the executor writes it, and only in the
same transaction as the wallet row.

**That is the important part:** your code creates domain facts; the framework saves those facts
in the same transaction as the state they describe. Neither half can happen without the other,
because neither half is a separate call you could make.

## What the outbox row means

An outbox row is not "a Kafka message stored in SQL". It is a committed event, with enough around
it for a consumer to know where it came from:

- which action committed it, when, and with what parameters;
- which model the event is about;
- the event's type - its class name;
- the event itself, as JSON.

An action that emits no events still writes **one row**, with the model and event columns empty.
The action happened, and that is a fact worth keeping. A consumer skips those rows by checking
`event_type IS NULL`.

The table is `eventlog.events`, and you never write to it yourself. You do not need its exact
columns to use it; [`events`](/reference/tables/events/) has them, for every database.

## What happens after commit

The outbox is **just a table**. Anything that can read it can consume it.

**In process** — two jobs inside your service read it and call your handlers, with retries and
expiry. No broker, no extra infrastructure. Right for a monolith or an internal service.

**CDC to Kafka** — a change-data-capture tool, Debezium, follows the table and publishes its rows
to Kafka. It runs inside Kafka Connect, a Java program, whatever language wrote the row; you use
ready-made transform JARs and build nothing in Python - see
[Streaming the events](/reference/beside-java/#streaming-the-events).

Both can run against the same outbox at once. The in-process path marks each row `delivered`
once it has handled it; the Kafka path ignores those updates, so they never become Kafka messages.

## One trap worth knowing

Rows are ordered by `event_date` and nothing else. With a real clock that is fine. A test that
freezes its clock gives every row of a run the same time, so their order is effectively random:
pick a row by its `action_name` or `action_id`, not by its position.
