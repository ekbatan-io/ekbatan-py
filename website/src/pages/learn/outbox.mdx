Every action's commit is one database transaction that touches as many domain tables as the
action needs **plus** the outbox. They land together, or none of them do.

```
┌──────────────────  ONE DATABASE TRANSACTION  ──────────────────────┐
│   wallets (UPDATE)     orders (INSERT)      events (INSERT)        │
└────────────────────────────────────────────────────────────────────┘
                                │
       commit (every row persists)  —or—  rollback (none of them do)
```

## How rows get there

Every row arrives the same way, and no other way exists:

```text
Model method
  -> returns a new immutable model
  -> with one or more ModelEvents attached

Action.perform()
  -> reads the current state
  -> calls the model method
  -> stages the new model on self.plan

the executor
  -> opens one database transaction
  -> writes the domain row
  -> writes the attached event rows to `events`
  -> commits, or rolls back all of it
```

For a wallet deposit, that first step is:

```python
def deposit(self, amount: Decimal) -> Wallet:
    new_balance = self.balance + amount
    return (
        self.copy()
        .with_event(MoneyDepositedEvent(model_id=str(self.id), amount=amount, new_balance=new_balance))
        .balance(new_balance)
        .build()
    )
```

The event is attached **before** persistence and written **after** it. In between it waits in the
action's staged changes, touching nothing. Only the executor writes it, and only in the same
transaction as the wallet row.

**That is the important part:** your code creates domain facts; the framework persists those
facts atomically with the state they describe. Neither half can happen without the other,
because neither half is a separate call you could make.

And this is the table they land in. Pick your dialect above; the DDL follows.

<div data-db="pg">

```sql
CREATE SCHEMA IF NOT EXISTS eventlog;

CREATE TABLE eventlog.events (
    id              UUID         NOT NULL,
    namespace       VARCHAR(255) NOT NULL,
    action_id       UUID         NOT NULL,
    action_name     VARCHAR(255) NOT NULL,
    action_params   JSONB        NOT NULL,
    started_date    TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    completion_date TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    model_id        VARCHAR(255),
    model_type      VARCHAR(255),
    event_type      VARCHAR(255),
    payload         JSONB,
    event_date      TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    delivered       BOOLEAN      NOT NULL,
    PRIMARY KEY (id)
);
```

`JSONB` rather than `JSON`: the binary form is indexable and compares by value, where `JSON` is
stored text and compares by bytes, so two payloads differing only in key order would be unequal.

</div>

<div data-db="mysql">

```sql
CREATE DATABASE IF NOT EXISTS eventlog;

CREATE TABLE eventlog.events (
    id              CHAR(36)     NOT NULL,
    namespace       VARCHAR(255) NOT NULL,
    action_id       CHAR(36)     NOT NULL,
    action_name     VARCHAR(255) NOT NULL,
    action_params   JSON         NOT NULL,
    started_date    DATETIME(6)  NOT NULL,
    completion_date DATETIME(6)  NOT NULL,
    model_id        VARCHAR(255),
    model_type      VARCHAR(255),
    event_type      VARCHAR(255),
    payload         JSON,
    event_date      DATETIME(6)  NOT NULL,
    delivered       BOOL         NOT NULL,
    PRIMARY KEY (id)
);
```

`DATETIME(6)`, never bare `DATETIME` — the bare form truncates to whole seconds, silently, and
`event_date` is the outbox's only ordering key. MySQL has no UUID type, so ids are `CHAR(36)`:
the hyphenated text form, chosen so they stay grep-able and so they match what the other
dialects store.

</div>

```sql
CREATE DATABASE IF NOT EXISTS eventlog;

CREATE TABLE eventlog.events (

    action_id       CHAR(36)     NOT NULL,
    action_name     VARCHAR(255) NOT NULL,
    action_params   JSON         NOT NULL,
    started_date    DATETIME(6)  NOT NULL,
    completion_date DATETIME(6)  NOT NULL,
    model_id        VARCHAR(255),
    model_type      VARCHAR(255),
    event_type      VARCHAR(255),
    payload         JSON,
    event_date      DATETIME(6)  NOT NULL,
    delivered       BOOL         NOT NULL,
    PRIMARY KEY (id)
);
```

MariaDB 10.7+ has a native 16-byte `UUID` type. This framework writes `CHAR(36)`, because
SQLAlchemy does not render the native one. **A table that uses the native type works too, and
that was checked**: the framework writes a uuid into it and reads back the same value.

Note also that MariaDB stores `JSON` as `LONGTEXT` with a check constraint. Invisible when you
declare the column; very visible when something *reflects* it, which is why
[schemagen](/reference/schemagen/) forces it back.

</div>

```sql
CREATE TABLE events (
    id              CHAR(32)     NOT NULL,
    namespace       VARCHAR(255) NOT NULL,
    action_id       CHAR(32)     NOT NULL,
    action_name     VARCHAR(255) NOT NULL,
    action_params   JSON         NOT NULL,

    delivered       BOOLEAN      NOT NULL,
    PRIMARY KEY (id)
);
```

`CHAR(32)` — hex with the hyphens stripped, because SQLite has no native uuid. The values round
trip correctly but do not look like what PostgreSQL shows, so a hand-written query comparing
against a hyphenated literal finds nothing.

**SQLite is not a production dialect.** It has no `SKIP LOCKED`, so the scheduler and the SQL
keyed lock degrade to single-process behaviour.

</div>

## What the outbox row means

An action that emits no events still writes **one row**, with `model_id`, `model_type`,
`event_type` and `payload` all null. The action happened, and that is a fact worth keeping.

A consumer skips them with `event_type IS NULL`. The Debezium transforms already do.

Otherwise `event_type` is the event's class name - the name handlers subscribe to. An event
class cannot override it: mypy flags an override, and the class is refused when it is defined.

## What happens after commit

The outbox is **just a table**. Anything that can read it can consume it.

**In process** — two jobs drain it and invoke typed handlers, with retry and expiry. No broker,
no CDC. Right for a monolith or an internal service.

**CDC to Kafka** — point Debezium at `events`. The transform that routes rows runs **inside
Kafka Connect**, which is a Java program whatever language wrote the row, so you use the
ready-made transform JARs and build nothing in Python - see
[Streaming the events](/reference/beside-java/#streaming-the-events).

Both can run against the same outbox at once. Fan-out flips `delivered` from false to true,
producing `UPDATE` rows; the transforms drop non-insert operations, so those flips never become
Kafka messages.

## One trap worth knowing

`event_date` is the only ordering key — there is no ordinal column. Under a real
clock that is fine. Under a **frozen** clock every row of a run ties and the order falls back to
a random uuid. The test suite fell into this more than once.
