Both are immutable, both version-tracked, both with a `state` column that supports soft
deletion. The difference is whether their changes are news.

| | `Model` | `Entity` |
| --- | :---: | :---: |
| `id`, `state`, `version` | yes | yes |
| `created_date` / `updated_date` | **required**, and typed on the base | neither |
| Changes emit events | yes | no |

Choose **`Model`** when a change should be recorded as an event. Choose **`Entity`** when the
current state is enough: lookup tables, configuration, auxiliary records that take part in an
action without needing a trail of their own.

## A model

<CodeBlock filename="model.py" language="python" shadow="yellow" code={`@dataclass(frozen=True, kw_only=True)
class Wallet(Model[ShardedId["Wallet"], WalletState, WalletBuilder]):
    owner_id: UUID
    currency: str
    balance: Decimal

    @classmethod
    def open(cls, *, owner_id: UUID, currency: str, balance: Decimal) -> Wallet:
        wallet_id = ShardedId[Wallet].random()
        return (
            WalletBuilder()
            .id(wallet_id)
            .state(WalletState.OPENED)
            .owner_id(owner_id)
            .currency(currency)
            .balance(balance)
            .with_initial_version()
            .with_event(WalletOpenedEvent(model_id=str(wallet_id), owner_id=owner_id,
                                          currency=currency, opening_balance=balance))
            .build()
        )

    def deposit(self, amount: Decimal) -> Wallet:
        if amount <= 0:
            raise ValidationError(f"deposit amount must be positive, got {amount}")
        new_balance = self.balance + amount
        return (
            self.copy()
            .with_event(MoneyDepositedEvent(model_id=str(self.id), amount=amount, new_balance=new_balance))
            .balance(new_balance)
            .build()
        )

    def close(self) -> Wallet:
        if self.state is WalletState.CLOSED:
            return self
        return self.copy().with_event(WalletClosedEvent(model_id=str(self.id))).state(WalletState.CLOSED).build()`} />

Two patterns worth naming. **A factory** (`open`) builds a *new* aggregate, calls
`with_initial_version()` and attaches the creation event. **`copy()`** returns a builder
pre-populated with the current state; mutators build on it, change what changed, attach an event
and `build()`.

`close()` returning `self` when already closed is the shape to copy: nothing staged means
nothing emitted, and the action's invocation is still recorded as a sentinel row.

## Why frozen

`@dataclass(frozen=True, kw_only=True)` is ordinary Python — the standard library has had
dataclasses since 3.7, and pydantic, pytest, FastAPI and SQLAlchemy all use frozen ones. What is
unusual is *what* is frozen here. The ecosystem freezes **value objects**: cache keys, config
values, durations. This framework freezes the **aggregate**.

That is deliberate, and the reason is [two-phase execution](/learn/actions/). The plan holds a
*reference* to what you staged, and the executor writes it later. With a mutable model, anything
touching that object between staging and commit would silently change what got written — a
deposit of 100 committing as 0.

`kw_only` does two jobs. It stops transposition, because `owner_id` sits next to `currency` and
`started_date` next to `completion_date`. It also makes the inheritance **legal at all**: the
base carries `version` and the timestamps, all with defaults, and a subclass field without one
would otherwise be *"non-default argument follows default argument"*.

If you are arriving from Django or the SQLAlchemy ORM: what you give up is dirty tracking. There
is no `session.commit()` working out what changed; you say what changed, through the plan.

## ModelEvent

```python
@dataclass(frozen=True, kw_only=True)
class MoneyDepositedEvent(ModelEvent["Wallet"]):
    amount: Decimal
    new_balance: Decimal
```

The class line names the model the event is about, and the constructor takes that model's id —
`MoneyDepositedEvent(model_id=str(self.id), amount=..., new_balance=...)`. Those two fill the
outbox's `model_id` and `model_type` columns, exactly as Java's `super(id, Wallet.class)` does.
A blank id is refused when the event is made, not when it is written.

### Deserialization (for in-process handlers)

Events are stored as JSON in `events.payload` and read back into the same class when an
in-process handler is invoked. **Nothing extra is needed for that round trip** — no annotation,
no registered constructor, no per-handler mapping layer. The payload is rebuilt from the
dataclass's own annotations, which is the one place the field types are already written down.

That is the whole of the Python side of a problem Java spends a `@JsonCreator` constructor on.
Java's Jackson cannot reconstruct an event with constructor parameters unless you write a second
constructor annotating every parameter with its JSON name; forget it and the dispatch job fails
to invoke the handler at all. Here the dataclass's `__init__` already takes keyword arguments
named after its fields, so there is nothing to declare.

What the decoder does with each field, driven by its annotation:

| Annotation | Written as (what Java writes) | Read back as |
|---|---|---|
| `Decimal` | a JSON **number**, as `BigDecimal.toString()`: `10.50`, `1E+3` | the same `Decimal`, scale kept |
| `float` | a number, as `Double.toString()`: `0.1`, `1.0E20` | `float` |
| `datetime` with UTC | an `Instant`: `"2025-01-01T00:00:00.120Z"` | aware, UTC |
| `datetime` with another offset | an `OffsetDateTime`: `"...T02:00:00+02:00"` | aware, that offset |
| `datetime` with no zone | a `LocalDateTime`: `"2025-01-01T10:00:00"` | no zone, as written |
| `date`, `time`, `timedelta` | `LocalDate`, `LocalTime`, `Duration` (`"PT1.5S"`) | the same type |
| `bytes` | base64: `"AQL/"` | `bytes` |
| `UUID` | its text | `UUID` |
| an `Enum` | its **member name**, never its ordinal | the member |
| `Id`, `ShardedId` | `{"id": "...", "value": "..."}`, as Jackson writes Java's | the typed id |
| another `TypedValue` | `{"value": ...}` | the typed value |
| a nested frozen dataclass | an object, keys as below | recursively, the same way |
| `list` / `tuple` / `set` / `frozenset` / `dict` of any of the above | array / object | element by element |
| `T \| None` | | the non-`None` arm, when there is exactly one |

**Keys are Java's field names**: `new_balance` is written `newBalance`, in the order the fields
are declared - what Jackson writes for a Java event with Ekbatan's usual `@JsonCreator`. A
`dict` keeps its own keys, in insertion order; nothing is sorted. The text is the same, byte for
byte, as Java's default Jackson 3 mapper writes for the same object - checked over 50,000
values in `parity-probes/G-domain-model/`.

**Every JSON number is read as a `Decimal`**, so nothing is lost on the way in, from either
port. One database is the exception: MySQL's `JSON` type stores a number with a fraction as a
double, so `50.00` comes back `50.0` there - for a Java service too, which sends the same text.
Enums travel by name - an ordinal changes meaning the moment somebody inserts a member in the
middle, and nothing about that change looks dangerous at the time.

Two limits worth knowing:

- **A key the dataclass does not declare is dropped**, not an error. An additive change on the
  producer cannot break a consumer that has not caught up — which is the same tolerance the
  streaming path has, and for the same reason. **A key the JSON lacks leaves the field `None`**
  (or its declared default), as Jackson leaves a Java field null.
- **A union with more than one non-`None` arm is left as raw JSON.** There is no discriminator in
  the payload to pick an arm with, so the decoder does not guess. Model that as a nested
  dataclass with a `kind` field rather than as a union if a handler needs it typed.

`model_id` and `model_name` come first, as `modelId` and `modelName`, because Java's local event
handler deserialises the payload straight into the event class and refuses one without them.
`modelName` is not read back: it comes off the class line, as Java's comes off `Wallet.class`.

Streaming-only consumers do not go through any of this: they read the JSON off the broker.

## Optimistic locking, always

Every update carries `WHERE version = ?`. If another transaction got there first, zero rows
match and `StaleRecordError` unwinds the action, which then retries once by default.

**The write path takes no pessimistic row locks, ever.** Conflicts surface as an exception rather
than as blocked threads. But note that is correct by *failing* — two deposits race and the loser
raises. When losing is the wrong outcome, take a keyed lock first so the second caller waits and
then succeeds.

## Generated builders

`wallet.copy().balance(...)` works with nothing generated. What it cannot do is tell a *type
checker* that `.balance(...)` takes a `Decimal` — setters resolve by name at runtime, so a
`.balance("25.50")` is a string in a `NUMERIC` column that nothing complains about until the
database does.

That is the one thing Python cannot work out for itself, and the one thing the generator exists
for:

```
uv run python -m ekbatan.codegen myapp.model --out myapp/builders.py
```

It imports the modules you name, finds every `Model` and `Entity` in them, and writes a builder
per class. For a `Wallet` with `owner_id: UUID`, `currency: str` and `balance: Decimal`:

```python
class WalletBuilder(ModelBuilder[Wallet, ShardedId[Wallet], WalletState]):
    """Builds a Wallet, with the field types a checker can see."""

    builds = Wallet

    def owner_id(self, value: UUID) -> Self:
        return self.set(owner_id=value)

    def currency(self, value: str) -> Self:
        return self.set(currency=value)

    def balance(self, value: Decimal) -> Self:
        return self.set(balance=value)


def wallet(source: Wallet | None = None) -> WalletBuilder:
    """A fresh WalletBuilder, optionally pre-loaded from an existing Wallet."""
    made = WalletBuilder()
    return made.copy_base(source) if source is not None else made
```

**What is generated:**

- A class named `<ModelName>Builder`, subclassing `ModelBuilder` (or `EntityBuilder`) with the
  right type parameters.
- A `builds` attribute naming the class it constructs — which is what `build()` calls, so there
  is no `build()` override to generate.
- One fluent setter per field the model **declared**, returning `Self` so the chain keeps its
  type. `id`, `state`, `version`, `created_date` and `updated_date` are typed on the base and are
  not repeated.
- A module-level factory named after the model in snake case — `wallet()` for `Wallet`,
  `wallet_account()` for `WalletAccount` — optionally pre-loaded from an existing instance.
- The imports the file needs, emitted relative when `--out` lands inside your package.

**What is not generated** — these stay on the model, where you can see them:

- The dataclass itself and its field declarations.
- Validation. `deposit()` raising on a non-positive amount is business logic, not boilerplate.
- Business methods, and the events they attach.
- Factory methods like `Wallet.open(...)` that set up a fresh aggregate and its first event.
- The one place your model names it — its own class line. The generator writes a separate file
  and never edits your model:

  ```python
  class Wallet(Model[ShardedId["Wallet"], WalletState, WalletBuilder]):
      balance: Decimal
  ```
- Any conditional default or computed field. If a builder needs one, write that builder by hand;
  the generator will not fight you for the name.

**Commit the output**, and **regenerate it when a model changes.** It is derived from source
you already have, unlike the schema module, which is derived from a database you have to start.

Regenerating is not optional discipline, and it is worth knowing exactly what a stale builder
costs, because it is less than you would hope: a setter the builder does not declare is **not**
caught by a type checker — the base resolves setters through `__getattr__`, which accepts any
name — and `build()` fails at runtime only if the new field is *required*, taking the default
silently if it is not.

Java has no equivalent exposure: its annotation processor runs on every compile, so its builder
cannot be stale or missing. `scripts/check-builders.py` restores that guarantee here — it
regenerates into memory, compares, and fails `make lint` on a builder that is missing or behind
its model. A builder without the generator's header is taken as hand-written, and only its
existence is checked.

**A model must name a typed builder**, on its class line:

```python
class Wallet(Model[ShardedId["Wallet"], WalletState, WalletBuilder]):
    balance: Decimal
```

That third argument is the return type of `copy()` and `builder()`, so a checker reads the real
setters. Leave it out and both refuse:

```
Wallet.copy() needs a typed builder, and Wallet has not named one.
  generated   python -m ekbatan.codegen myapp.model --out <pkg>/builders.py
  by hand     class WalletBuilder(ModelBuilder["Wallet", ...]): ...
then name it on Wallet's class line, which is the whole of the wiring.
```

Java's `copy()` returns a generated builder or the class does not compile. There is no compile
step here, so the refusal is **per route and at the call** — a model that only ever calls
`copy()` needs only that override, and an entity built solely through a factory like
`Alert.create(...)` and never copied needs neither.

**Generated or hand-written makes no difference** — what is required is a builder a checker can
read, and writing one by hand is better where a setter needs a conditional default or a computed
field. `ModelBuilder(X)` is still reachable by name, for a model defined inside a test with
nowhere to put a builder. What is closed is reaching the untyped builder *through a model*.

`evolve()` is unaffected, and is still the right call for a one-field change.

## Soft deletion

Nothing is physically removed. `delete()` on the model flips `state` to `DELETED` and emits an
event like any other change, and every inherited read filters those rows out:

```python
def delete(self) -> Wallet:
    if self.state is WalletState.DELETED:
        return self
    return self.copy().with_event(WalletDeletedEvent(model_id=str(self.id))).state(WalletState.DELETED).build()
```

then `repo.update(wallet.delete())`, or `plan.update(wallet.delete())` inside an action.

There is no `delete()` on the repository, in either port, and that is deliberate: a row that
silently stopped existing would leave every event already published about it with nothing on the
other side. What leaves is the wallet, not the history.

Two things follow. **Deleting is a domain decision**, so the model says what it means — some
models refuse to be deleted while they hold money. And **a query you write yourself does not get
the filter**: the inherited reads apply it, a statement you build carries what you put in it, so
add `WALLETS.c.state != WalletState.DELETED.name` when you drop to SQL.

When a physical delete is genuinely required — an erasure request, purging expired rows — write
it against your own rule. [`WalletRepository.erase`](/reference/repository/) in the
example does exactly that, and refuses a wallet that still holds money.

## Inherited builder methods

Both builders carry a shared set on the base, typed `Self` so the return stays your builder:

| | model | entity |
| --- | :-: | :-: |
| `id(...)` | yes | yes |
| `state(...)` | yes | yes |
| `version(...)` / `with_initial_version()` / `increase_version()` | yes | yes |
| `copy_base(other)` | yes | yes |
| `set(**changes)` | yes | yes |
| `with_event(...)` / `events(...)` | yes | — |
| `created_date(...)` / `updated_date(...)` | yes | — |

`copy_base(other)` is what `model.copy()` returns first: the id, state, version, and for a model
the events and timestamps, pre-populated — so domain code only names the fields that changed.

The split is the whole difference between the two kinds. An entity has no events to attach and
no timestamps to hold, so those methods are not on it to be called by mistake.

## Naming conventions

The same in both ports, so a reader moving between them recognises what they are looking at.

- **Model** — a singular noun: `Wallet`, `Order`, `Subscription`.
- **State enum** — `<Model>State`, values in `UPPER_SNAKE`: `WalletState.OPENED`,
  `OrderState.SHIPPED`. `GenericState` (`ACTIVE` / `DELETED`) is fine for an entity, or a model
  with no real state machine.
- **Event** — `<Model><Verb>ed` + `Event`: `WalletOpenedEvent`, `MoneyDepositedEvent`,
  `OrderShippedEvent`. Past tense: an event describes something that already happened.
- **Action** — `<Verb><Model>Action`: `OpenWalletAction`, `DepositMoneyAction`,
  `ShipOrderAction`. Imperative: an action describes intent.
- **Id** — no class of its own: `ShardedId[Wallet]` for a model whose rows are routed by id,
  `Id[Alert]` otherwise, as Java writes `ShardedId<Wallet>`. A checker keeps two models' ids
  apart; at runtime they compare by uuid, as Java's do.
