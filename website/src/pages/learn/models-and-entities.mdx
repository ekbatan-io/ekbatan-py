Both are frozen dataclasses, both carry an `id`, a `state` and a `version`, and both are saved
by a repository. The difference is whether their changes are news.

| | `Model` | `Entity` |
| --- | :---: | :---: |
| `id`, `state`, `version` | yes | yes |
| `created_date` / `updated_date` | **required** | neither |
| Changes emit events | yes | no |

Choose **`Model`** when a change should be recorded as an event. Choose **`Entity`** when the
current state is enough: lookup tables, configuration, auxiliary records that take part in an
action without needing a history of their own.

Both work the same in sync and async code: nothing on a model waits on the database.

## A model

<CodeBlock filename="model.py" language="python" shadow="yellow" code={`@dataclass(frozen=True, kw_only=True)
class Wallet(Model[ShardedId["Wallet"], WalletState, WalletBuilder]):
    owner_id: UUID
    currency: str
    balance: Decimal

    def validate(self) -> None:
        if self.balance < 0:
            raise ValidationError("balance cannot be negative")

    @staticmethod
    def create_wallet(
        shard: ShardIdentifier,
        owner_id: UUID,
        currency: str,
        initial_balance: Decimal,
        created_date: Instant,
    ) -> WalletBuilder:
        wallet_id = ShardedId[Wallet].generate(shard)
        return (
            WalletBuilder()
            .id(wallet_id)
            .state(WalletState.OPENED)
            .owner_id(owner_id)
            .currency(currency)
            .balance(initial_balance)
            .created_date(created_date)
            .with_initial_version()
            .with_event(WalletCreatedEvent(model_id=str(wallet_id), owner_id=owner_id,
                                          currency=currency, initial_balance=initial_balance))
        )

    def deposit(self, amount: Decimal) -> Wallet:
        if amount <= 0:
            raise ValidationError("Deposit amount must be positive")
        new_balance = self.balance + amount
        return (
            self.copy()
            .with_event(WalletMoneyDepositedEvent(model_id=str(self.id), amount=amount, new_balance=new_balance))
            .balance(new_balance)
            .build()
        )

    def close(self) -> Wallet:
        if self.state is WalletState.CLOSED:
            return self
        return self.copy().with_event(WalletClosedEvent(model_id=str(self.id))).state(WalletState.CLOSED).build()`} />

Three patterns are worth naming:

- **`validate()`** holds the wallet's own rules, and runs on every wallet made - see
  [below](#validate-the-models-own-rules).
- **A factory**, `create_wallet`, builds a *new* wallet: it sets the first version with
  `with_initial_version()` and attaches the creation event.
- **`copy()`** returns a builder filled in from the current wallet. A method such as `deposit()`
  changes what changed, attaches an event and calls `build()`. The old wallet is untouched.

`close()` returns `self` when the wallet is already closed. That is the shape to copy: nothing
changed means no event, and the action is still recorded in the outbox.

## `validate()`: the model's own rules

Every model and every entity defines `validate()`: the one place for rules its field types cannot
express, such as "the balance is never negative".

It runs **every time a wallet is made** - by `build()`, by the constructor, and when a repository
reads a row - so no path hands you a wallet that breaks its rules. Raise `ValidationError` (from
`ekbatan.errors`) when one is broken.

It is required. A model with no rules of its own says so:

```python
    def validate(self) -> None:
        pass  # no rules beyond its types
```

A model without it is refused as soon as its class is defined. The finer points - base classes of
your own, a model with its own `__post_init__` - are in the
[reference](/reference/model/#validate-the-models-own-rules).

## Why frozen

`@dataclass(frozen=True, kw_only=True)` is ordinary Python. What is unusual is *what* is frozen
here: not small value objects, but the whole aggregate - the wallet itself.

The reason is [two-phase execution](/learn/actions/). The plan holds a *reference* to what you
staged, and the executor writes it later. If the model could change, anything touching it between
staging and commit would silently change what got written - a deposit of 100 committing as 0.

`kw_only` means every field is passed by name, so two fields of the same type, such as
`started_date` and `completion_date`, can never be swapped by accident.

If you come from Django or the SQLAlchemy ORM, what you give up is dirty tracking: nothing works
out what changed for you. You say what changed, through the plan.

## ModelEvent

```python
@dataclass(frozen=True, kw_only=True)
class WalletMoneyDepositedEvent(ModelEvent["Wallet"]):
    amount: Decimal
    new_balance: Decimal
```

The class line names the model the event is about, and the constructor takes that model's id:
`WalletMoneyDepositedEvent(model_id=str(self.id), amount=..., new_balance=...)`. Together they
fill the outbox row's `model_id` and `model_type`.

### Deserialization (for in-process handlers)

An event is saved as JSON in the outbox row's `payload`, and read back into the same class when an
in-process handler runs. **Nothing extra is needed** for that round trip: the dataclass's own
field types say how each field is written and read.

Field names are written in camelCase (`new_balance` becomes `newBalance`), decimals as JSON
numbers, and times as ISO-8601 text. A `datetime` field must say which kind of time it holds -
`Instant`, `LocalDateTime` or `OffsetDateTime`, from `ekbatan.time`; a plain `datetime` is refused
when the event is written. The full table, type by type, is on
[ModelEvent](/reference/model-event/).

Consumers that read events from Kafka do not use any of this: they read the JSON off the broker.

## Optimistic locking, always

Every update carries `WHERE version = ?`. If another transaction changed the row first, nothing
matches, and `StaleRecordError` unwinds the whole action, which then retries once by default.

The framework never takes row locks. So two deposits racing on one wallet do not wait for each
other: the loser fails and retries. When failing is the wrong outcome, take a
[keyed lock](/reference/keyed-locks/) first, so the second caller waits and then succeeds.

## Generated builders

`wallet.copy().balance(...)` works with nothing generated. What it cannot do is tell a *type
checker* that `.balance(...)` takes a `Decimal`: the setters are found by name at runtime, so
`.balance("25.50")` passes every check until the database refuses it.

Generating a builder per model fixes that:

```
uv run python -m ekbatan.codegen myapp.model --out myapp/builders.py
```

For the wallet, it writes:

```python
class WalletBuilder(ModelBuilder[Wallet, ShardedId[Wallet], WalletState]):
    """Builds a Wallet, with the field types a checker can see."""

    builds = Wallet

    def owner_id(self, value: UUID) -> Self:
        return self.set(owner_id=value)

    def currency(self, value: str) -> Self:
        return self.set(currency=value)

    def balance(self, value: Decimal) -> Self:
        return self.set(balance=value)
```

Then name the builder on the model's class line - it is the third type in the brackets, and it
is what `copy()` returns:

```python
class Wallet(Model[ShardedId["Wallet"], WalletState, WalletBuilder]):
    ...
```

**Commit the generated file, and regenerate it whenever a model changes.** A builder that has
fallen behind its model is not caught by a type checker, so run the generator in CI and fail on a
difference. What the generator writes and leaves alone, and how to write a builder by hand, is in
the [reference](/reference/model/#builder-api).

## Soft deletion

Nothing is physically removed. `delete()` on the model flips its `state` to `DELETED` and emits an
event, like any other change, and every read the repository gives you leaves deleted rows out:

```python
def delete(self) -> Wallet:
    if self.state is WalletState.DELETED:
        return self
    return self.copy().with_event(WalletDeletedEvent(model_id=str(self.id))).state(WalletState.DELETED).build()
```

There is no `delete()` on the repository: a row that silently disappeared would leave every event
already published about it pointing at nothing. Two things follow. Deleting is a domain decision,
so the model says what it means - a wallet might refuse while it holds money. And a query you
write yourself does not leave deleted rows out unless you say so.

When a row truly has to go - an erasure request, say - write that delete yourself, against your
own rules; the [repository reference](/reference/repository/) shows one.

## Inherited builder methods

Every builder has these, on top of its own setters:

| | model | entity |
| --- | :-: | :-: |
| `id(...)` | yes | yes |
| `state(...)` | yes | yes |
| `version(...)` / `with_initial_version()` / `increase_version()` | yes | yes |
| `copy_base(other)` | yes | yes |
| `set(**changes)` | yes | yes |
| `with_event(...)` / `events(...)` | yes | — |
| `created_date(...)` / `updated_date(...)` | yes | — |

`copy_base(other)` is what `copy()` starts from: the id, state, version, and for a model its
events and dates, already filled in - so your code names only the fields that changed.

## Naming conventions

Not enforced, but followed by every example, so a reader moving between services recognises what
they are looking at.

- **Model** — a singular noun: `Wallet`, `Order`, `Subscription`.
- **State enum** — `<Model>State`, values in `UPPER_SNAKE`: `WalletState.OPENED`,
  `OrderState.SHIPPED`. `GenericState` (`ACTIVE` / `DELETED`) is fine for an entity, or a model
  with no real states of its own.
- **Event** — `<Model><Verb>ed` + `Event`: `WalletCreatedEvent`, `WalletMoneyDepositedEvent`,
  `OrderShippedEvent`. Past tense: an event describes something that already happened.
- **Action** — `<Model><Verb>Action`: `WalletCreateAction`, `WalletDepositMoneyAction`,
  `WalletCloseAction`. Imperative: an action describes intent.
- **Id** — `ShardedId[Wallet]` for a model whose rows are spread across databases by id,
  `Id[Notification]` otherwise. A type checker keeps two models' ids apart.
