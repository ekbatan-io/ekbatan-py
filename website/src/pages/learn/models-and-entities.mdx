Both are immutable, both version-tracked, both with a `state` column that supports soft
deletion. The difference is whether their changes are news.

| | `Model` | `Entity` |
| --- | :---: | :---: |
| `id`, `state`, `version` | yes | yes |
| `created_date` / `updated_date`, managed for you | yes | no |
| Changes emit events | yes | no |

Choose **`Model`** when a change should be recorded as an event. Choose **`Entity`** when the
current state is enough: lookup tables, configuration, auxiliary records that take part in an
action without needing a trail of their own.

## A model

<CodeBlock filename="model.py" language="python" shadow="yellow" code={`@dataclass(frozen=True, kw_only=True)
class Wallet(Model[WalletId, WalletState]):
    owner_id: UUID
    currency: str
    balance: Decimal

    @classmethod
    def open(cls, *, owner_id: UUID, currency: str, balance: Decimal) -> Wallet:
        return (
            WalletBuilder()
            .id(WalletId.random())
            .state(WalletState.OPENED)
            .owner_id(owner_id)
            .currency(currency)
            .balance(balance)
            .with_initial_version()
            .with_event(WalletOpenedEvent(owner_id=owner_id, currency=currency,
                                          opening_balance=balance))
            .build()
        )

    def deposit(self, amount: Decimal) -> Wallet:
        if amount <= 0:
            raise ValidationError(f"deposit amount must be positive, got {amount}")
        new_balance = self.balance + amount
        return (
            self.copy()
            .with_event(MoneyDepositedEvent(amount=amount, new_balance=new_balance))
            .balance(new_balance)
            .build()
        )

    def close(self) -> Wallet:
        if self.state is WalletState.CLOSED:
            return self
        return self.copy().with_event(WalletClosedEvent()).state(WalletState.CLOSED).build()`} />

Two patterns worth naming. **A factory** (`open`) builds a *new* aggregate, calls
`with_initial_version()` and attaches the creation event. **`copy()`** returns a builder
pre-populated with the current state; mutators build on it, change what changed, attach an event
and `build()`.

`close()` returning `self` when already closed is the shape to copy: nothing staged means
nothing emitted, and the action's invocation is still recorded as a sentinel row.

## Why frozen

`@dataclass(frozen=True, kw_only=True)` is ordinary Python — the standard library has had
dataclasses since 3.7, and pydantic, pytest, FastAPI and SQLAlchemy all use frozen ones. What is
unusual is *what* is frozen here. The ecosystem freezes **value objects**: cache keys, config
values, durations. This framework freezes the **aggregate**.

That is deliberate, and the reason is [two-phase execution](/learn/actions/). The plan holds a
*reference* to what you staged, and the executor writes it later. With a mutable model, anything
touching that object between staging and commit would silently change what got written — a
deposit of 100 committing as 0.

`kw_only` does two jobs. It stops transposition, because `owner_id` sits next to `currency` and
`started_date` next to `completion_date`. It also makes the inheritance **legal at all**: the
base carries `version` and the timestamps, all with defaults, and a subclass field without one
would otherwise be *"non-default argument follows default argument"*.

If you are arriving from Django or the SQLAlchemy ORM: what you give up is dirty tracking. There
is no `session.commit()` working out what changed; you say what changed, through the plan.

## ModelEvent

```python
@dataclass(frozen=True, kw_only=True)
class MoneyDepositedEvent(ModelEvent):
    amount: Decimal
    new_balance: Decimal
```

That is the whole declaration. The event carries **no identity** — you do not pass it the
model's id. It was attached to a model, so the framework knows, and fills the outbox's
`model_id` and `model_type` columns itself.

### Deserialization (for in-process handlers)

Events are stored as JSON in `events.payload`, and read back into the same class when an
in-process handler is invoked. Nothing extra is needed for that round trip: the payload is
rebuilt from the dataclass's own annotations. Decimals travel as strings, deliberately — a JSON
number is a double, and a balance that round-trips through one is no longer the balance.

## Optimistic locking, always

Every update carries `WHERE version = ?`. If another transaction got there first, zero rows
match and `StaleRecordError` unwinds the action, which then retries once by default.

**The write path takes no pessimistic row locks, ever.** Conflicts surface as an exception rather
than as blocked threads. But note that is correct by *failing* — two deposits race and the loser
raises. When losing is the wrong outcome, take a keyed lock first so the second caller waits and
then succeeds.

## Generated builders

`wallet.copy().balance(...)` works with nothing generated. What it cannot do is tell a *type
checker* that `.balance(...)` takes a `Decimal` — setters resolve by name at runtime.

```
uv run python -m ekbatan.codegen myapp.model --out myapp/builders.py
```

A generated builder declares **only the fields its model added**; `id`, `state`, `version` and
the timestamps are typed on the base. **Commit the output** — it is derived from source you
already have, unlike the schema module, which is derived from a database you have to start.

## Soft deletion

Nothing is physically removed. `delete()` on the model flips `state` to `DELETED` and emits an
event like any other change, and every inherited read filters those rows out:

```python
def delete(self) -> Wallet:
    if self.state is WalletState.DELETED:
        return self
    return self.copy().with_event(WalletDeletedEvent()).state(WalletState.DELETED).build()
```

then `repo.update(wallet.delete())`, or `plan.update(wallet.delete())` inside an action.

There is no `delete()` on the repository, in either port, and that is deliberate: a row that
silently stopped existing would leave every event already published about it with nothing on the
other side. What leaves is the wallet, not the history.

Two things follow. **Deleting is a domain decision**, so the model says what it means — some
models refuse to be deleted while they hold money. And **a query you write yourself does not get
the filter**: the inherited reads apply it, a statement you build carries what you put in it, so
add `WALLETS.c.state != WalletState.DELETED.name` when you drop to SQL.

When a physical delete is genuinely required — an erasure request, purging expired rows — write
it against your own rule. [`WalletRepository.erase`](/reference/repository/) in the
example does exactly that, and refuses a wallet that still holds money.

## Inherited builder methods

Both builders carry a shared set on the base, typed `Self` so the return stays your builder:

| | model | entity |
| --- | :-: | :-: |
| `id(...)` | yes | yes |
| `state(...)` | yes | yes |
| `version(...)` / `with_initial_version()` / `increase_version()` | yes | yes |
| `copy_base(other)` | yes | yes |
| `set(**changes)` | yes | yes |
| `with_event(...)` / `events(...)` | yes | — |
| `created_date(...)` / `updated_date(...)` | yes | — |

`copy_base(other)` is what `model.copy()` returns first: the id, state, version, and for a model
the events and timestamps, pre-populated — so domain code only names the fields that changed.

The split is the whole difference between the two kinds. An entity has no events to attach and
no timestamps to hold, so those methods are not on it to be called by mistake.

## Naming conventions

The same in both ports, so a reader moving between them recognises what they are looking at.

- **Model** — a singular noun: `Wallet`, `Order`, `Subscription`.
- **State enum** — `<Model>State`, values in `UPPER_SNAKE`: `WalletState.OPENED`,
  `OrderState.SHIPPED`. `GenericState` (`ACTIVE` / `DELETED`) is fine for an entity, or a model
  with no real state machine.
- **Event** — `<Model><Verb>ed` + `Event`: `WalletOpenedEvent`, `MoneyDepositedEvent`,
  `OrderShippedEvent`. Past tense: an event describes something that already happened.
- **Action** — `<Verb><Model>Action`: `OpenWalletAction`, `DepositMoneyAction`,
  `ShipOrderAction`. Imperative: an action describes intent.
- **Id** — `<Model>Id`, a named subclass rather than `Id[Wallet]`, so
  `WalletId(u) == AlertId(u)` is false at runtime and not only to a checker.
