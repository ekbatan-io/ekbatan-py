Every business change produces two things at once — a new state, and a record of how it got
there. Persisting them as two separate writes is where systems start to drift apart.

## The shape of the bug

You write an order to the database. Then you publish `OrderPlaced` to Kafka so the warehouse,
billing and the email worker all hear about it. Two writes, two systems, two round trips.

<GuidedFlow variant="broken" />

The bug is the gap between them. The database write succeeds; the process is OOM-killed, the
broker connection drops, the pod is rescheduled — any of them, between the two lines — and the
database now holds an order nothing downstream will ever hear about. Or the reverse: the publish
succeeds, the database write rolls back, and three systems start working on an order that does
not exist.

**Retries do not fix it.** Retrying the publish after a successful commit can succeed *or*
duplicate. Retrying the commit after a successful publish can succeed *or* publish twice. There
is no atomic "do both" across two systems short of a distributed transaction, and distributed
transactions between a database and a broker are not a thing anyone runs.

## The shape of the fix

Write the event to *the same database, in the same transaction* as the domain row. Let something
else carry it to the broker afterwards, by reading the database.

<GuidedFlow variant="outbox" />

The outbox is an ordinary table in your application database. The framework inserts its row in
the same transaction as the state change, so the two land together or not at all. A separate
process — Debezium reading the write-ahead log, or an in-process worker polling the table —
ships them onward.

The dual write is gone. The only system that has to be transactionally consistent is the
database, which is what databases are for.

## Why it’s a framework concern

The pattern is well known, and most teams bolt it on: add an `events` table, remember to write
to it in every transaction, build a poller. It works, and you carry the discipline forever.
Every new action has to remember. Every review has to check. The day somebody forgets, you have
a silent dual write, and it will not be noticed until a downstream system is measurably wrong.

This framework makes forgetting impossible. The executor writes the outbox row for every action,
at every commit. Concretely: your code stages a `WalletDepositMoneyAction`; the executor opens the
transaction, writes the `wallets` row, writes the matching `WalletMoneyDepositedEvent` to `events`, and
commits. **There is no second table to remember, because you never write to it.**

That is the whole pitch, and the rest of this section is how the pieces make the guarantee
*structural* rather than a convention somebody has to police. An action that forgot the outbox
is not a bug you can write — there is no API for writing a domain row without one.

## The one place it reappears

A **cross-shard** action is conceptually a dual write again — two databases, two commits, no
atomicity between them. That is why it is refused by default rather than merely discouraged. See
[sharding strategies](/learn/sharding-strategies/) and [sagas](/learn/sagas/).
