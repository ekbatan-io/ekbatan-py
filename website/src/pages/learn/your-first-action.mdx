This lesson builds on [Getting started](/learn/getting-started/). We write actual domain code: a
`Wallet` that emits a `MoneyDepositedEvent`, and a `DepositMoneyAction` that moves the balance.

The model and action code are the same whatever serves your HTTP. The endpoint below uses
FastAPI only to show where an application calls the executor. For a complete runnable project,
see [Complete project setup](/learn/complete-project-setup/).

The shape of the surface, before we type a line:

```
           POST /wallets/{id}/deposits
                        ▼
              deposit(wallet_id, body)
                        ▼
            executor.execute(
                DepositMoneyAction,
                DepositParams(wallet_id, amount, recipient))
                        ▼
        ┌─── Phase 1 — perform() ──────────────────┐
        │  self.wallets.get(wallet_id)             │
        │  wallet.deposit(amount)                  │
        │      ↳ attaches MoneyDepositedEvent      │
        │  self.plan.update(updated)               │
        └──────────────────────────────────────────┘
                        ▼
        ┌─── Phase 2 — the executor commits ───────┐
        │  one transaction, one shard:             │
        │     UPDATE wallets  WHERE id=? AND v=?   │
        │     INSERT events   (1 row)              │
        │  commit                                  │
        └──────────────────────────────────────────┘
```

## 1. Define the event

Domain events are pure data carriers — frozen dataclasses with the fields a consumer needs and
nothing else:

```python
@dataclass(frozen=True, kw_only=True)
class MoneyDepositedEvent(ModelEvent["Wallet"]):
    amount: Decimal
    new_balance: Decimal
```

The event says which model it is about. `ModelEvent["Wallet"]` on the class line fixes the
model's name once for every event of this class, and the wallet's id is passed when the event is
made - `MoneyDepositedEvent(model_id=str(self.id), ...)`. Those two go into the outbox's `model_id` and `model_type`
columns, so a consumer correlates without opening the payload.

Notice what is *not* in it. The deposit endpoint also takes a `recipient`, and it is absent
here: a delivery address has no business inside a money-deposited event. It travels as an action
parameter instead, and a handler reads it off the envelope. See
[ModelEvent](/reference/model/).

## 2. Define the model

A model is immutable, version-tracked, and emits events through `with_event(...)`:

```python
@dataclass(frozen=True, kw_only=True)
class Wallet(Model[ShardedId["Wallet"], WalletState, WalletBuilder]):
    owner_id: UUID
    currency: str
    balance: Decimal

    def deposit(self, amount: Decimal) -> Wallet:
        if amount <= 0:
            raise ValidationError(f"deposit amount must be positive, got {amount}")
        new_balance = self.balance + amount
        return (
            self.copy()
            .with_event(MoneyDepositedEvent(model_id=str(self.id), amount=amount, new_balance=new_balance))
            .balance(new_balance)
            .build()
        )
```

Frozen, so a deposit returns a *new* wallet rather than mutating one. That is not decoration: it
is what makes two-phase execution safe. An action reads and constructs freely, the plan collects
references to immutable snapshots, and a partial write is not expressible.

**Time is UTC.** A model's dates come from the framework's clock (`self.now()` in an action),
an aware UTC `datetime`, and are stored in zone-less columns. That is the strong recommendation
everywhere - in your code and on the database - see [Always UTC](/reference/multi-database/#always-utc).

`deposit(amount)` is the only place this event is ever attached. That is the whole discipline —
events are produced inside the model, staged inside the action's `perform()`, and persisted by
the framework.

`copy()` returns a builder. Generate a typed one with `python -m ekbatan.codegen` so a checker
sees the field types, which is the one thing Python cannot work out for itself — see
[Models and entities](/learn/models-and-entities/).

## 3. A repository

```python
class WalletRepository(ModelRepository[Wallet, ShardedId[Wallet]]):
    def __init__(self, registry: DatabaseRegistry) -> None:
        super().__init__(Wallet, WALLETS, registry)

    def to_row(self, wallet: Wallet) -> dict[str, Any]:
        return self.columns_by_field_name(wallet)

    def from_row(self, row: Row[Any] | Mapping[str, Any]) -> Wallet:
        return self.model_by_field_name(row)
```

That is the whole repository. `get`, `find_where`, `add`, `update`, counting and existence are
inherited. The mapping between a row and the model is yours to write, and when the names line up
it is the two methods above: every field to the column of the same name. A repository without
them is refused when it is created, so a renamed column can never quietly stop matching. Where a
name or a shape differs, write the mapping out instead.

What you add are the questions your business actually asks:

```python
    def find_all_by_owner(self, owner_id: UUID) -> list[Wallet]:
        return self.find_where(WALLETS.c.owner_id == owner_id)
```

See [Repositories](/reference/repository/) for the inherited surface, and for what to
reach for when it runs out.

## 4. Write the action

The action does three things in `perform()`: read, mutate, stage. **No database writes happen
here** — the executor opens the transaction *after* `perform()` returns.

```python
@dataclass(frozen=True, kw_only=True)
class DepositParams:
    wallet_id: ShardedId[Wallet]
    amount: Decimal
    recipient: str


class DepositMoneyAction(Action[DepositParams, Wallet]):
    def __init__(self, wallets: WalletRepository, clock: Clock) -> None:
        super().__init__(clock)
        self.wallets = wallets

    def perform(self, principal: str | None, params: DepositParams) -> Wallet:
        wallet = self.wallets.get(params.wallet_id)
        return self.plan.update(wallet.deposit(params.amount))
```

`self.plan.update` **writes nothing.** It stages. Nothing discovers this class either: you put
it in a registry in your wiring, where you can see it. See [Actions](/learn/actions/) and
[Wiring](/reference/wiring/).

## 5. Call the action from application code

The caller can be an HTTP endpoint, a message handler, a scheduled job or a CLI command. What
matters is that it goes through `executor.execute(...)`.

```python
class DepositRequest(BaseModel):
    amount: Decimal = Field(gt=0)
    recipient: str


@app.post("/wallets/{wallet_id}/deposits", response_model=WalletResponse)
def deposit(wallet_id: UUID, body: DepositRequest, service: Service) -> WalletResponse:
    return WalletResponse.of(
        service.executor.execute(
            DepositMoneyAction,
            DepositParams(
                wallet_id=ShardedId[Wallet](wallet_id),
                amount=body.amount,
                recipient=body.recipient,
            ),
        )
    )
```

`service` is the one built at startup, handed over by a FastAPI dependency — not built per
request, which would open a connection pool per request.
[Wiring with FastAPI](/reference/wiring-fastapi/) is that seam, and names the other sharp
mistake: calling this sync API from an `async def` endpoint blocks the event loop. (An async
service uses `ekbatan.aio` instead - [Going async](/learn/async/).)

Who is acting is a separate concern. The executor takes a principal; in a real service it comes
from your authentication layer.

## 6. Run a deposit

Start your application, then:

```bash
curl -X POST http://localhost:8000/wallets/<wallet_id>/deposits \
     -H 'Content-Type: application/json' \
     -d '{"amount": 10.00, "recipient": "ada@example.com"}'
```

## 7. Look at the outbox

```sql
SELECT action_name, model_type, event_type, payload
FROM events
ORDER BY event_date DESC
LIMIT 5;
```

One row, with `event_type = 'MoneyDepositedEvent'`, `model_type = 'Wallet'` and a payload of
`{"modelId": "...", "modelName": "Wallet", "amount": 10.00, "newBalance": ...}`. The `wallets` row shows the new balance and
`version + 1`. Both changed inside **one** transaction — see
[`events`](/reference/tables/events/) for what every column means.

The keys are camelCase and decimals are JSON numbers. Every number is read back as a `Decimal`,
so the scale survives. (A Java service built on Ekbatan writes the same text for the same event -
see [Running beside a Java service](/reference/beside-java/#event-payloads).)

## What just happened

- **One** database transaction touched two tables (`wallets` UPDATE + `events` INSERT). The
  outbox guarantee is structural — there is no second commit you could forget.
- Your code never opened a transaction. The executor did, after `perform()` returned.
- The event payload carries no infrastructure concern — no topic, no broker, no delivery flag.
  It is pure domain.
- The next deposit on this wallet uses the new version in its `WHERE version = ?`. A concurrent
  stale write matches zero rows, raises `StaleRecordError`, and the framework re-runs phase one.
  See [Actions](/learn/actions/).

Look at what you did not write: no `BEGIN`, no `COMMIT`, no flush, no publish, and no mention of
an outbox anywhere. There is no second table to remember, because you never write to it.

## Test it without a database

An action's logic needs none. `ActionSpec` runs the action and checks what it staged and emitted:

```python
(ActionSpec.of(DepositMoneyAction(wallets, clock))
    .with_principal("alice")
    .execute(DepositParams(wallet_id=..., amount=Decimal("50.00"), recipient="ada@example.com"))
    .assert_updated(Wallet, lambda w: w.balance == Decimal("150.00"))
    .assert_emitted(MoneyDepositedEvent, lambda e: e.amount == Decimal("50.00"))
    .assert_no_additions())
```

A verifier can be a `lambda` returning its verdict or a function that asserts inside itself. A
falsy verdict fails, so a `lambda` cannot pass by accident. When plain `assert` reads better,
`run_action` hands back the same information as data:

```python
staged = run_action(
    DepositMoneyAction(wallets, clock),
    DepositParams(wallet_id=..., amount=Decimal("50.00"), recipient="ada@example.com"),
)

assert staged.result.balance == Decimal("150.00")
assert staged.emitted(MoneyDepositedEvent)[0].amount == Decimal("50.00")
```

Both bind the plan through the same mechanism the executor uses, so `self.plan`,
`self.clock` and the `principal` argument behave exactly as in production. Nothing is written.

That is also the limit of it. **That state and events land *together* is a claim about a
transaction**, and only a test against a real database checks it.
