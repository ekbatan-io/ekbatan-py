An **action** is one unit of business work. It does **not** write to the database. It stages new
and updated domain objects on its plan. Only after `perform()` returns does the executor open a
single transaction, flush every staged change, write the outbox rows and commit.

## The two-phase lifecycle

```
   executor.execute(principal, WalletDepositMoneyAction, params)
                              │
   ┌─── Phase 1 - perform()   (no transaction yet) ─────────────┐
   │   read from repositories                                   │
   │   build new immutable models                               │
   │   attach events to them                                    │
   │   stage:  self.plan.add(order) / self.plan.update(wallet)  │
   │   return a result                                          │
   └────────────────────────────────────────────────────────────┘
                              │
   ┌─── Phase 2 - persist     (one transaction per shard) ──────┐
   │   group staged changes by shard                            │
   │   repositories write the domain rows                       │
   │   the persister writes the outbox rows                     │
   │   commit  -or-  roll back                                  │
   │   on StaleRecordError, retry the whole action              │
   └────────────────────────────────────────────────────────────┘
```

Phase 1 is pure construction. Phase 2 is the only place a transaction is opened, and it always
wraps every staged change together with the matching event rows.

Three consequences follow from the split, and they are most of why it exists.

**`perform()` cannot write, so it cannot half-write.** There is no flush, no `save()`, no
connection to reach for. The worst an action can do is stage something the executor then refuses,
and refusing costs nothing because nothing has been written.

**A retry is cheap and correct.** When a version check fails, phase 2 rolls back and the executor
re-runs phase 1 from the top with a **fresh plan** — re-reading the row it lost the race on, so
the second attempt is computed from the winner's state rather than patched onto the loser's.
An action that only reads, computes and stages is safe to re-run by construction; one that
posted to an external API in `perform()` is not, which is the real reason for the rule.

**Sharding stays out of the action.** The grouping step is in phase 2, so `perform()` stages
objects without knowing which database each one lands on. The same action body works on one
database and on eight.

The cost is the one thing you have to hold in your head: **`self.plan.update(x)` has not written
`x`.** It returns the row as it *will be* written — stamped, version already moved — so later
code in the same `perform()` reads the new state. But the database has not seen it, and will not
until `perform()` returns.

## Writing an action

<ModeTabs>
<div slot="sync">

```python
class WalletDepositMoneyAction(Action["WalletDepositMoneyAction.Params", Wallet]):
    @dataclass(frozen=True, kw_only=True)
    class Params:
        wallet_id: ShardedId[Wallet]
        amount: Decimal

    def __init__(self, clock: Clock, wallet_repository: WalletRepository) -> None:
        super().__init__(clock)
        self.wallet_repository = wallet_repository

    def perform(self, principal: str | None, params: Params) -> Wallet:
        wallet = self.wallet_repository.get_by_id(params.wallet_id.value)
        return self.plan.update(wallet.deposit(params.amount))
```

</div>
<div slot="async">

```python
class WalletDepositMoneyAction(AsyncAction["WalletDepositMoneyAction.Params", Wallet]):
    @dataclass(frozen=True, kw_only=True)
    class Params:
        wallet_id: ShardedId[Wallet]
        amount: Decimal

    def __init__(self, clock: Clock, wallet_repository: WalletRepository) -> None:
        super().__init__(clock)
        self.wallet_repository = wallet_repository

    async def perform(self, principal: str | None, params: Params) -> Wallet:
        wallet = await self.wallet_repository.get_by_id(params.wallet_id.value)
        return self.plan.update(wallet.deposit(params.amount))
```

</div>
</ModeTabs>

In async mode the action is an `AsyncAction`, `perform` is `async def`, and each read is
awaited. What it stages is the same, and so is everything else on this page.

Typed parameters in, a domain object out. The action reads through a repository, builds a new
immutable wallet with an event already attached — that happened inside `wallet.deposit(...)` —
and stages it. **No database write happens in `perform()`.**

The generic parameters are what a checker holds you to: `Action[WalletDepositMoneyAction.Params, Wallet]` means
`execute` on this action takes those params and returns a wallet, at the call site, without a
cast.

Calling it:

<ModeTabs>
<div slot="sync">

```python
wallet = executor.execute(
    None,
    WalletDepositMoneyAction,
    WalletDepositMoneyAction.Params(wallet_id=wallet_id, amount=Decimal("25.50")),
)
```

</div>
<div slot="async">

```python
wallet = await executor.execute(
    None,
    WalletDepositMoneyAction,
    WalletDepositMoneyAction.Params(wallet_id=wallet_id, amount=Decimal("25.50")),
)
```

</div>
</ModeTabs>

The executor opens one transaction, writes the wallet row with its incremented version, writes
the `WalletMoneyDepositedEvent` row into `events`, and commits. If anything raises, both roll back
together.

An action with no parameters passes `None`. What it may not pass is a bare scalar — a string or
an int in the params column is unreadable six months later, so it is refused.

## ActionPlan

```python
self.plan.add(entity)         # staged for INSERT
self.plan.update(entity)      # staged for UPDATE; returns the object at its next version
self.plan.add_all(items)
self.plan.update_all(items)
```

Three rules:

- **One id may be staged at most once per action.** Re-staging raises. Two changes to one row in
  one action is almost always a bug you would rather find here.
- **`update()` returns the object at its next version**, so later reads in the same `perform()`
  see the increment.
- **The plan is single-writer.** It is a plain dict; concurrent mutation is a data race.

## Singletons + per-call state via a ContextVar

One instance per class, shared by every concurrent invocation. Its only state is what the
constructor set. Per-execution state — the plan, the clock, the principal — is bound into a
**`ContextVar`** for the duration of `perform()`.

So an action must not have mutable instance state, and `self.plan` must be reached from the
thread or task running `perform()`.

## Plan is single-writer; spawning threads is fine

Spawning parallel work inside `perform()` is **allowed** — the *plan* is single-writer, not the
action. Two hard rules:

1. **Only the thread that invoked `perform()` may call `self.plan.add(...)` or
   `self.plan.update(...)`.** The plan is a plain dict; concurrent mutation from a pool thread
   is a data race with a correct-looking traceback. Even *reading* it from a pool thread is
   unsupported, because the `ContextVar` binding does not propagate — `self.plan` raises there
   rather than returning the wrong plan, which is the better of the two failures.
2. **Do not share the action's transactional connection across threads.** It is bound to the
   invoking thread, and a DBAPI connection is not thread-safe regardless.

That second rule is why the non-propagation is correct rather than a limitation: a pool thread
outliving the unit of work while holding its connection is exactly the bug it prevents.

The supported pattern is fan out, **join**, and only then stage — from the invoking thread, or,
in async mode, from `perform()` itself after the gather:

<ModeTabs>
<div slot="sync">

```python
def perform(self, principal: str | None, params: Params) -> Order:
    with ThreadPoolExecutor() as pool:
        customer, quote = pool.map(...)     # neither touches the plan
    return self.plan.add(build_order(customer, quote))   # back on this thread
```

</div>
<div slot="async">

```python
async def perform(self, principal: str | None, params: Params) -> Order:
    customer, quote = await asyncio.gather(
        self.customer_repository.get_by_id(params.customer_id.value),   # each read on a connection of its own
        self.quote_repository.get_by_id(params.quote_id.value),         # neither touches the plan
    )
    return self.plan.add(build_order(customer, quote))   # staged here, after both
```

</div>
</ModeTabs>

For *reads*, prefer doing the fan-out **before** `executor.execute(...)` — at the caller — so
the parallel work uses ordinary pool connections rather than anything belonging to the action.
Inside `perform()`, keep parallelism to work that needs none of the action's state: external
calls, replica reads on their own connections, pure computation.

Under asyncio the rule is the same, for a different reason. A task started inside `perform()` -
`asyncio.gather` makes one per read - gets a copy of the context, so `self.plan` does resolve
there. Stage from `perform()` anyway, after the gather: the order of what is staged then does not
depend on which read finished first. See [Concurrency](/reference/runtime/concurrency/).

## Retries on optimistic-lock conflicts

The default is one retry after 100 ms — enough to absorb ordinary contention, not enough to hide
a real problem.

<ModeTabs>
<div slot="sync">

```python
config = ExecutionConfiguration(
    retry_configs=(RetryConfig(on=StaleRecordError, max_retries=3, delay=0.05),)
)
executor.execute(None, WalletDepositMoneyAction, params, config=config)
```

</div>
<div slot="async">

```python
config = ExecutionConfiguration(
    retry_configs=(RetryConfig(on=StaleRecordError, max_retries=3, delay=0.05),)
)
await executor.execute(None, WalletDepositMoneyAction, params, config=config)
```

</div>
</ModeTabs>

Three details worth knowing:

**`max_retries` counts retries, not attempts.** `max_retries=1` runs the action twice. It is
named for what it counts because `attempts=1` running twice is the sort of thing nobody catches
in review and everybody hits in production.

**Matching looks through the cause chain**, so a driver wrapping a conflict is still recognised.

**Matching is by exact class, so a subclass does not match.** A policy for `EkbatanError` does
not catch a `StaleRecordError` — name the class that is actually thrown. Which failures retry is
then written down in one place, rather than widened by whatever subclasses exist. Order is the
only precedence rule, so put narrow policies first.

**A retry replays the whole action from phase 1, with a fresh plan.** Side effects outside the
plan — logging, counters, an HTTP call — replay too. Keep `perform()` pure.

## No nested actions inside `perform()`

An action must not execute another action inside `perform()`. The framework **intentionally does
not support nesting or composition**: an action is a self-contained unit of business work that
produces one atomic transaction, and nesting blurs that boundary, creates hidden coupling, and
makes the execution flow hard to reason about.

There are three right answers, depending on what you actually meant:

- **They must happen together** → they belong in a single action. One `perform()` can read three
  repositories and stage four objects; that is not a reason to reach for a second action.
- **They are independent** → execute them separately from the caller, which is the layer that
  already knows they are independent.
- **One must follow the other** → chain them *after* the commit.

That last one is the only exception, and it is a real one: an in-process handler, a broker
consumer or a worker reacts once the source action has **committed**, and starts the next step in
its own transaction. A [saga](/learn/sagas/) is exactly this shape, repeated — one committed
action emits an event, a post-commit consumer starts the next.

The reason the exception is safe and nesting is not comes down to one thing: after the commit
there is no outer transaction left to corrupt. Inside `perform()` there is not even one yet.

## Cross-shard actions

Refused unless you ask. An action whose staged changes span shards raises `CrossShardError`,
naming the two that disagreed — the check is on what was staged, so it fires at the boundary
between `perform()` and the commit rather than half way through writing.

<ModeTabs>
<div slot="sync">

```python
executor.execute(
    None,
    TransferAction,
    params,
    config=ExecutionConfiguration(allow_cross_shard=True),
)
```

</div>
<div slot="async">

```python
await executor.execute(
    None,
    TransferAction,
    params,
    config=ExecutionConfiguration(allow_cross_shard=True),
)
```

</div>
</ModeTabs>

With that, each shard gets its own transaction and commits independently. **There is no
two-phase commit**, and there is no way to add one: the shards are separate databases, and an
atomic commit across them does not exist to be opted into. A failure rolls back only its own
shard; the ones that already committed stay committed, and the executor logs that loudly.

So a partial commit here is the [dual-write trap](/learn/the-dual-write-trap/) wearing a
different hat — two systems that can disagree, where the two systems happen to both be yours.
Prefer opting in per call rather than as an executor default, so the risk is visible at the
call site. If a partial commit would need compensating, the honest answer is a
[saga](/learn/sagas/).
