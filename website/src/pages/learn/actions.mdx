An **action** is one unit of business work. It does **not** write to the database. It stages new
and updated domain objects on its plan. Only after `perform()` returns does the executor open a
single transaction, flush every staged change, write the outbox rows and commit.

## The two phases

```
        executor.execute(DepositMoneyAction, params)
                              │
   ┌─── Phase 1 - perform()   (no transaction yet) ─────────────┐
   │   read from repositories                                   │
   │   build new immutable models                               │
   │   attach events to them                                    │
   │   stage:  self.plan.add(order) / self.plan.update(wallet)  │
   │   return a result                                          │
   └────────────────────────────────────────────────────────────┘
                              │
   ┌─── Phase 2 - persist     (one transaction per shard) ──────┐
   │   group staged changes by shard                            │
   │   repositories write the domain rows                       │
   │   the persister writes the outbox rows                     │
   │   commit  -or-  roll back                                  │
   │   on StaleRecordError, retry the whole action              │
   └────────────────────────────────────────────────────────────┘
```

Phase 1 is pure construction. Phase 2 is the only place a transaction is opened, and it always
wraps every staged change together with the matching event rows.

## The plan

```python
self.plan.add(entity)         # staged for INSERT
self.plan.update(entity)      # staged for UPDATE; returns the object at its next version
self.plan.add_all(items)
self.plan.update_all(items)
```

Three rules:

- **One id may be staged at most once per action.** Re-staging raises. Two changes to one row in
  one action is almost always a bug you would rather find here.
- **`update()` returns the object at its next version**, so later reads in the same `perform()`
  see the increment.
- **The plan is single-writer.** It is a plain dict; concurrent mutation is a data race.

## Actions are singletons

One instance per class, shared by every concurrent invocation. Its only state is what the
constructor set. Per-execution state — the plan, the clock, the principal — is bound into a
**`ContextVar`** for the duration of `perform()`. The Java port binds the same thing to a
`ScopedValue`.

So an action must not have mutable instance state, and `self.plan` must be reached from the
thread or task running `perform()`. Work handed to a pool does **not** inherit the binding —
which is correct, not a limitation: a pool thread outliving the unit of work while holding its
connection is exactly the bug this prevents.

```python
def perform(self, params: Params) -> Order:
    with ThreadPoolExecutor() as pool:
        customer, quote = pool.map(...)     # neither touches the plan
    return self.plan.add(build_order(customer, quote))   # back on this thread
```

Fan out, **join**, and only then stage.

## Retries

The default is one retry after 100 ms — enough to absorb ordinary contention, not enough to hide
a real problem.

```python
config = ExecutionConfiguration(
    retry_configs=(RetryConfig(on=StaleRecordError, max_retries=3, delay=0.05),)
)
executor.execute(DepositMoneyAction, params, config=config)
```

Three details worth knowing:

**`max_retries` counts retries, not attempts.** `max_retries=1` runs the action twice. It is
named for what it counts because `attempts=1` running twice is the sort of thing nobody catches
in review and everybody hits in production.

**Matching looks through the cause chain**, so a driver wrapping a conflict is still recognised.

**Matching is by `isinstance`, so a subclass matches.** This is a real divergence from the Java
port, which matches the exception class *exactly* — a policy for `RuntimeException` there does
not catch an `IllegalStateException`. Here a policy for `EkbatanError` catches every framework
error. Order is the only precedence rule, so put narrow policies first.

**A retry replays the whole action from phase 1, with a fresh plan.** Side effects outside the
plan — logging, counters, an HTTP call — replay too. Keep `perform()` pure.

## Two refusals

**No nesting.** An action must not execute another action inside `perform()`. Nesting blurs the
transaction boundary, hides coupling and makes the flow hard to follow. If two operations must
happen together, they are one action. If one must follow the other, chain them *after* the
commit — which is what a [saga](/learn/sagas/) is.

**No cross-shard, unless you ask.** An action whose changes span shards raises `CrossShardError`.
With `allow_cross_shard=True` each shard gets its own transaction and commits independently —
there is no two-phase commit — and a partial commit is the dual-write trap wearing a different
hat.
