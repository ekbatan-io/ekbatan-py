## Threads, and the one way to use this wrongly

CPython has no lightweight threads: every thread is an operating-system thread, and only one runs
Python code at a time. So how the framework uses threads, and how your server calls it, are worth
a few minutes. If you read one thing on this page, read this.

**The sync API blocks.** Under a threaded server that is exactly right: a blocking call holds one
worker thread, and Python lets the other threads run while it waits on the database.

Under **asyncio** it is not, because a blocking call there stops the entire event loop rather
than one thread.

```python
# refused inside an async def: BlockingCallError
wallet = wallet_repository.get_by_id(wallet_id)

# right, with the sync API
wallet = await run_in_threadpool(wallet_repository.get_by_id, wallet_id)

# right, with ekbatan.aio: an async repository, awaited
wallet = await wallet_repository.get_by_id(wallet_id)
```

A plain `def` endpoint in FastAPI is already run in a threadpool, so the ordinary way of writing
one is safe with none of this. Or build the request path on the async API, `ekbatan.aio`, and
`await` every call — see [Going async](/learn/async/). There, the connection pool is the cap on
requests waiting on the database: size it, set `pool_timeout`, map its timeout to a 503, and cap
open requests at the server too (`uvicorn --limit-concurrency`).

### What runs in parallel

Three parts of the framework use threads of their own:

- **fan-out across shards** — each round reads every shard at once, one thread per shard;
- **dispatch** — the handlers of a batch run at once, one thread each. **So your handlers run at
  the same time as each other**: write them to be safe alongside each other;
- **the keyed-lock watchdog** — a single thread watches every held lock, however many there are.

**And one place the gap closes entirely.** Under `gevent.monkey.patch_all()` a blocking call costs
nothing: every one of them lets other work run while it waits. The framework needs no code for
it, and CI runs the whole test suite under gevent to keep it that way. The catch is that gevent
serves **WSGI** apps, so Flask and Django can use it and FastAPI cannot - and every example here
is FastAPI. See
[Concurrency](/reference/runtime/concurrency/).

## Pools live in processes

Under `uvicorn --workers 4` there are four of every pool, so the database sees
`4 × (pool_size + job_pool_size + lock_pool_size)` connections. **Size per process, then multiply
before comparing with `max_connections`** — this is the usual way a Python deployment runs out.

Every worker process also runs the scheduler. That is fine and is the point: the scheduler is
cluster-exclusive, so four processes contend for the same rows and exactly one wins each
execution. It is the same code path as four machines.

**Build them in each process, after it starts** - in the FastAPI lifespan, or at the top of
the worker's `main()`. A server that forks its workers copies whatever the parent built, and
ekbatan refuses to work in such a copy (`ForkedProcessError`).
[Startup and shutdown](/learn/startup-and-shutdown/) lists those objects - the registries, the
job registry, the lock providers - with their startup and shutdown calls, and the recipe per
server.

If you would rather not have every web worker also be a job worker, run the jobs in their own
process.

## Migrations

Run them as their own deploy step rather than at startup once you are past the toy stage — which
is what making it a setting is for.

`migrate` visits shards in **configuration order**, stops at the first failure, and names the
shard *and what had already succeeded*, because half a migrated cluster is a state an operator
has to reason about.

It also records a checksum of every applied migration in `ekbatan_schema_history` and refuses to
run when an applied file has been edited, renamed or deleted, so the files and the database never
disagree with nothing to say so. Each database is locked while it is migrated - a lock the database
drops if the migrating process dies - so replicas starting together cannot run a migration twice,
and a replica or read-only server is refused rather than migrated. Migrate over a direct connection to each primary: PgBouncer, a connection pooler, drops the
session lock a migration relies on when it runs in transaction mode.

## What to alert on

Two rules rather than dashboard panels.

**`ekbatan.events.delivery.lag` rising steadily.** A shard falling behind still reports perfectly
healthy success counts, so **no counter can reveal a growing backlog** — only the lag can.

**`ekbatan.events.handled{outcome="expired_postfailure"}` above zero means events were
discarded.** A notification reaches that state only after failing for the whole retention window
— seven days by default — so any occurrence is a delivery permanently given up on.

A steady stream of `failed_retry` concentrated on a single handler usually means that handler
cannot succeed at all — the classic case being an `ImportError` from a missing optional
dependency. Alerting on that catches it in minutes; the discard alert only fires a week later,
once the events are gone.

## Two things to know before you deploy

**Running jobs finish on SIGTERM - by default.** A started `JobRegistry` lets its running jobs
finish on any normal exit, on Ctrl-C, and on SIGTERM - what a container stop sends. Under
uvicorn or gunicorn the server has SIGTERM: it turns it into a lifespan shutdown, and the
lifespan calls `jobs.stop()`, as the examples do. A **standalone worker** has no server, so the
registry catches SIGTERM itself. Where it cannot - the hook turned off, or the registry started
off the main thread - it logs one warning when it starts: its running jobs would be cut off, and
their rows would wait out the dead-execution window, 60 seconds on framework defaults, before
another instance picks them up. [Details](/reference/jobs/distributed-jobs/).

**No connection-pool leak detection.** Nothing warns you about a connection that is taken from a
pool and never given back. A detector that raised when the connection came back would lose the
connection itself, so there is none.

**And one thing that is not a gap in the code:** this framework has never run in production.
The suite passes on four dialects — but a passing suite is not *proven under load*.
