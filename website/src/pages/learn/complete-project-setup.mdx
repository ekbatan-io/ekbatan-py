Everything below follows the picker. Choose your database, your installer and the mode - the
sync API, or `ekbatan.aio` with every database call awaited - and the whole page rewrites
itself; the choice persists across pages. Not sure which mode? [Sync or
async?](/learn/sync-or-async/) takes two minutes.

**Every file on this page is a real file**, read when this site is built, so it cannot drift
from what was checked: copy each file to the path in its header and the project runs. The steps
are checked by doing exactly that, in an empty folder, for every database, installer and mode -
the service starts, a deposit's notification arrives, and the outbox holds the rows step 15
lists.

<div data-db="pg mysql mariadb">

This is a **complete** service: migrations, generated schema, domain, actions, repository, an
event handler, a distributed job, wiring, a small HTTP layer and a Makefile.

You need Python 3.13 or later, and Docker: the database in step 2 and the schema generator each
run a container.

</div>

<div data-db="sqlite">

On SQLite the service is smaller, and runs with nothing installed but Python 3.13 or later: no
web layer, no migrations, no container. One module set, a hand-written schema, and a script that
drives it.

</div>

## 1. Scaffold a project

<div data-install="uv">

```bash
uv init wallet && cd wallet
```

</div>

<div data-install="pip">

```bash
mkdir -p wallet/src/wallet && cd wallet
touch src/wallet/__init__.py
python3 -m venv .venv && source .venv/bin/activate
```

pip has no scaffold of its own, so the project file is yours to write - setuptools finds the `src/` layout by itself:

<div data-db="pg mysql mariadb">

```toml
# pyproject.toml

name = "wallet"
version = "0.1.0"
requires-python = ">=3.13"

[build-system]
requires = ["setuptools>=69"]
build-backend = "setuptools.build_meta"

# setuptools packs only .py files unless told: the migrations and the config file ride along here
[tool.setuptools.package-data]
wallet = ["ekbatan.yaml", "migrations/*.sql"]
```

## 2. Start a database

<div data-db="pg mysql mariadb">

The service connects to it in step 15; the schema generator starts a throwaway container of its
own.

</div>

<div data-db="pg">

```bash
docker run --rm -d --name wallet-pg \
  -e POSTGRES_DB=wallet -e POSTGRES_USER=ekbatan -e POSTGRES_PASSWORD=ekbatan \
  -p 5432:5432 postgres:17
```

</div>

<div data-db="mysql">

```bash
docker run --rm -d --name wallet-mysql \
  -e MYSQL_ROOT_PASSWORD=ekbatan -e MYSQL_DATABASE=wallet \
  -p 3306:3306 mysql:8.4
```

</div>

<div data-db="mariadb">

```bash
docker run --rm -d --name wallet-mariadb \
  -e MARIADB_ROOT_PASSWORD=ekbatan -e MARIADB_DATABASE=wallet \
  -p 3306:3306 mariadb:11.4
```

</div>

<div data-db="pg mysql mariadb">

The login matches the defaults in `ekbatan.yaml` (step 4), so the service runs against this
container with nothing set. Elsewhere, set the variables the file names.

</div>

<div data-db="mysql mariadb">

The login is root because the first migration (step 5) creates a second database, `eventlog`, for
the framework's event tables. Any login allowed to create that database and to use it will do.

</div>

<div data-db="sqlite">

Nothing to start: a SQLite database is a file, made on first use. The script points the service
at one in a temporary folder.

</div>

`${NAME:default}` is an environment variable with a default, and a missing one with no default
stops startup naming it. YAML, TOML, JSON and INI all work - see
[Config files](/reference/config-files/).

<div data-db="pg mysql mariadb">

**The url names the database and where it is - never the login.** `username` and `password` are
fields of their own, because a url is logged and repeated, and one carrying a password is
refused.

</div>

<div data-db="pg mysql mariadb" data-mode="sync">

**Two pools on one member.** `primaryConfig` is for requests. `jobsConfig` is the scheduler's,
sized at least twice its worker count, because the scheduler heartbeats from a housekeeping
thread and a job body holding the last connection starves it. `app.py` (step 13) builds it with
`DataSource.from_config` and closes it.

</div>

<div data-db="pg mysql mariadb" data-mode="async">

**Three pools on one member, one url.** The url names the sync driver; the async side reads it as
"this database" and connects through its async default - asyncpg for PostgreSQL, aiomysql for
MySQL and MariaDB.

- `primaryConfig` - requests, async. It is also the cap on requests waiting on the database:
  past `poolSize` they queue, for at most `poolTimeout` seconds, then fail.
- `handlersConfig` - the event handler's and the stipend job's units of work, async, used only
  on the loop the handler runs on.
- `jobsConfig` - sync: the scheduler, and the fan-out and dispatch jobs. At least the job
  workers plus three, because the scheduler heartbeats and a job body holding the last
  connection starves it.

</div>

<div data-db="pg mysql mariadb">

**Every session in UTC, on every pool.** `options: -c TimeZone=UTC` on PostgreSQL,
`time_zone = '+00:00'` in `init_command` on MySQL and MariaDB. The columns hold UTC wall-clock
time; this puts the database's own clock - `NOW()`, a column default - on UTC too, whatever the
server's default zone is. See [Always UTC](/reference/multi-database/#always-utc).

</div>

<div data-db="pg mysql mariadb" data-mode="async">

The same setting reaches the async drivers unchanged: asyncpg receives libpq's `options` as its
own `server_settings`, and aiomysql runs `init_command` as PyMySQL does.

</div>

<div data-db="sqlite">

**One url, no login.** SQLite has neither a server nor users. Handling is switched on under
`local-event-handler`, so the in-process handler runs.

</div>

<div data-db="sqlite" data-mode="async">

The url names no driver: the sync side connects with sqlite3, the async side with aiosqlite,
SQLite's async default.

</div>

**The namespace** is written into every outbox row, which is what lets two applications share
one database without reading each other's events. Change it after the fact and the rows already
written are, correctly, no longer yours.

from sqlalchemy import MetaData

from ekbatan.migrations import emit_ddl
from ekbatan.schema import notifications_table, outbox_table

metadata = MetaData()
outbox_table(metadata)
notifications_table(metadata)

The handler takes the **executor**, not a connection: it does its work as its own unit of work,
after the one that produced the event has committed. **Delivery is at-least-once** - make the body
idempotent - and the handler's `name` is stored on every notification row, so keep it stable.

<div data-mode="async">

inside it: fan-out and dispatch are jobs on their own threads, and dispatch runs an async handler
on its **handler loop** - one event loop on a thread of its own. What the handler awaits belongs
to that loop, so `app.py` (step 13) builds the handler its own registry and executor, and closes
them on that loop.

Every two seconds, each open wallet below 100.00 gets 10.00, through the same
`WalletDepositMoneyAction` a request runs - so its deposits are events like any other, and reach
