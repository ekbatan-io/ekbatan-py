This is a **complete** service: migrations, generated schema, domain, actions, repository,
handler, job, wiring, HTTP layer, tests and a Makefile. The example named in the picker is this
page as a runnable project.

## 1. The project

```
wallet/
├─ Makefile
├─ pyproject.toml
├─ migrations/
│  ├─ env.py
│  └─ versions/0001_initial.py
├─ wallet/
│  ├─ __init__.py
│  ├─ model.py          the domain
│  ├─ builders.py       GENERATED, committed
│  ├─ schema.py         GENERATED, gitignored
│  ├─ actions.py        the units of work
│  ├─ repository.py     the queries this app asks
│  ├─ handlers.py       in-process event handlers
│  ├─ jobs.py           cluster-exclusive background work
│  ├─ app.py            the wiring, all of it
│  └─ api.py            the HTTP layer, and nothing else
└─ tests/
```

Two generated files, and the difference between them matters: **`builders.py` is committed**
because it is derived from source you already have; **`schema.py` is gitignored** because it is
derived from a database you have to start.

## 3. The connection url

<div data-db="pg">

```
postgresql+psycopg://user:pass@localhost:5432/wallet
```

`psycopg`, not `psycopg2` — the `postgres` extra brings psycopg 3.

</div>
<div data-db="mysql">

```
mysql+pymysql://user:pass@localhost:3306/wallet
```

</div>
<div data-db="mariadb">

```
mariadb+pymysql://user:pass@localhost:3306/wallet
```

**The scheme has to say `mariadb`.** A MariaDB container hands back a `mysql://` url, and
SQLAlchemy picks its DDL, its version reporting and its `SKIP LOCKED` support off the scheme —
while this framework picks its keyed-lock provider off `engine.dialect.name`. Leave it as `mysql`
and everything works, while running MySQL's code path against a MariaDB server.

</div>
<div data-db="sqlite">

```
sqlite:///wallet.db
```

Fine for one process. Not a production dialect: no `SKIP LOCKED`, so the scheduler and the SQL
keyed lock degrade to single-process behaviour.

</div>

## 4. The first migration

The framework's own tables have to exist. Do not hand-write their DDL — generate it once and
commit the result:

```python
from sqlalchemy import MetaData
from ekbatan.migrations import emit_ddl
from ekbatan.schema import notifications_table, outbox_table, scheduled_tasks_table

metadata = MetaData()
outbox_table(metadata)
notifications_table(metadata)
scheduled_tasks_table(metadata)

print(emit_ddl(metadata, "postgresql"))    # or "mysql", "sqlite"
```

Paste it into `migrations/versions/0001_initial.py` alongside your own tables, **one statement
per `op.execute()`** — PyMySQL rejects a multi-statement script, so a revision that works on
PostgreSQL fails elsewhere with an error naming the syntax rather than the cause.

## 5. Generate the schema

<div data-db="sqlite">

Skip this step. There is no container to reflect from, so write `schema.py` by hand with the
column helpers and commit it:

```python
from sqlalchemy import Column, MetaData, Numeric, String, Table
from ekbatan.schema import timestamp_column, uuid_column

metadata = MetaData()
WALLETS = Table(
    "wallets", metadata,
    Column("id", uuid_column(), primary_key=True),
    Column("version", Integer, nullable=False),
    Column("state", String(32), nullable=False),
    Column("owner_id", uuid_column(), nullable=False),
    Column("currency", String(3), nullable=False),
    Column("balance", Numeric(19, 4), nullable=False),
    Column("created_date", timestamp_column(), nullable=False),
    Column("updated_date", timestamp_column(), nullable=False),
)
```

</div>

<div data-db="pg">

```bash
uv run python -m ekbatan.schemagen --migrations migrations --out wallet/schema.py \
  --image postgres:17-alpine
```

</div>
<div data-db="mysql">

```bash
uv run python -m ekbatan.schemagen --migrations migrations --out wallet/schema.py \
  --image mysql:8.4
```

</div>
<div data-db="mariadb">

```bash
uv run python -m ekbatan.schemagen --migrations migrations --out wallet/schema.py \
  --image mariadb:11.4
```

</div>

<div data-db="pg">
It starts a throwaway container, runs **your** migrations into it, reflects the result and
writes a module of `Table` definitions — the counterpart to the Java port's jOOQ step.
</div>
<div data-db="mysql">
It starts a throwaway container, runs **your** migrations into it and reflects the result. The
type forcing matters here: a uuid on MySQL is `CHAR(36)` and nothing in the database says it is a
uuid, so a plain reflection would give you a text column that no other dialect can join against.
</div>
<div data-db="mariadb">
It starts a throwaway container, runs **your** migrations into it and reflects the result. Two
MariaDB quirks make the forcing essential: `JSON` is reported as `LONGTEXT`, and a bigint comes
back as `BIGINT(display_width=20)` — which, emitted verbatim, does not even import.
</div>

## 7. The wiring

<CodeBlock filename="wallet/app.py" language="python" shadow="orange" code={`@dataclass(frozen=True, slots=True)
class WalletService:
    registry: DatabaseRegistry
    wallets: WalletRepository
    executor: ActionExecutor
    locks: KeyedLockProvider
    jobs: JobRegistry

    def start(self) -> None:
        self.jobs.start()

    def close(self) -> None:
        # Order matters: stop taking work before closing what the work runs on.
        self.jobs.stop()
        self.locks.close()
        self.registry.close()


def build(config: Settings) -> WalletService:
    layout = ShardingConfig(
        shards=(ShardConfig(shard=DEFAULT_SHARD,
                            primary=DataSourceConfig(url=config.url,
                                                     pool_size=config.pool_size)),),
        default_shard=DEFAULT_SHARD,
    )

    if config.run_migrations:
        migrate(layout, MIGRATIONS)          # before anything opens a pool

    registry = DatabaseRegistry.from_config(layout)
    wallets = WalletRepository(registry)

    executor = ActionExecutor(
        namespace="com.example.wallet",
        registry=registry,
        repositories=RepositoryRegistry.builder().with_model_repository(wallets).build(),
        actions=(ActionRegistry.builder()
                 .with_action(OpenWalletAction())
                 .with_action(DepositMoneyAction(wallets))
                 .build()),
        events=EVENTS,
    )

    handlers = EventHandlerRegistry([MoneyDepositedEventHandler(executor)])
    events_config = LocalEventHandlerConfig(handling=HandlingConfig(enabled=True))

    return WalletService(
        registry=registry,
        wallets=wallets,
        executor=executor,
        locks=PostgresKeyedLockProvider(
            create_engine(config.url, pool_size=config.lock_pool_size, max_overflow=0)),
        jobs=(job_registry()
              .engine(create_engine(config.url, pool_size=config.job_pool_size, max_overflow=0))
              .with_jobs([
                  EventFanoutJob(registry, handlers, events=EVENTS,
                                 notifications=EVENT_NOTIFICATIONS, config=events_config),
                  EventHandlingJob(registry, handlers,
                                   notifications=EVENT_NOTIFICATIONS, config=events_config),
                  PayStipendJob(executor, wallets),
              ])
              .workers(3)
              .build()),
    )`} />

**Three pools.** Requests get the main engine. Jobs get their own, sized at **at least twice the
worker count**, because the scheduler heartbeats from a housekeeping thread and a job body
holding the last connection starves it — and an execution whose heartbeat stops is declared dead
and run again somewhere else. Locks get a third, because a keyed lock holds its connection for
the life of the lease.

<div data-db="mysql">
Use `MySQLKeyedLockProvider` rather than the PostgreSQL one — and note that a sub-second
`try_acquire` wait is a **poll** on MySQL, which truncates the fraction to zero.
</div>
<div data-db="mariadb">
Use `MariaDBKeyedLockProvider`. It issues the same statements as the MySQL one and exists
separately because MariaDB honours sub-second `GET_LOCK` timeouts where MySQL truncates them.
</div>
<div data-db="sqlite">
Use `InProcessKeyedLockProvider`. It is a `threading.Lock`, not a distributed lock, and will not
tell you so at runtime — two instances each get their own.
</div>

## 8. The HTTP layer

<CodeBlock filename="wallet/api.py" language="python" shadow="yellow" code={`def service_of(request: Request) -> WalletService:
    service: WalletService = request.app.state.service
    return service


# MODULE LEVEL. With \`from __future__ import annotations\`, FastAPI resolves string
# annotations against the *module* namespace - an alias defined inside create_app is
# invisible, and the parameter is read as an unfilled query parameter instead. The
# symptom is a 422 on every endpoint, naming a field nobody declared.
Service = Annotated[WalletService, Depends(service_of)]


def create_app(settings: Settings | None = None) -> FastAPI:
    @asynccontextmanager
    async def lifespan(app: FastAPI) -> AsyncIterator[None]:
        service = build(settings or Settings())
        service.start()
        app.state.service = service
        try:
            yield
        finally:
            service.close()

    app = FastAPI(title="Wallet", lifespan=lifespan)

    # A handler must RETURN a response. Raising from inside one is not caught again and
    # becomes a 500 - the opposite of what these exist for.
    @app.exception_handler(StaleRecordError)
    async def _lost_a_race(request: Request, error: Exception) -> JSONResponse:
        return JSONResponse(status_code=409, content={"detail": "the wallet changed; retry"})

    # \`def\`, not \`async def\`. FastAPI runs a plain def in a threadpool, so a blocking
    # database call blocks one worker thread. An async def endpoint runs on the event
    # loop, where the same call stops every request on that worker.
    @app.post("/wallets/{wallet_id}/deposits", response_model=WalletResponse)
    def deposit(wallet_id: UUID, body: DepositRequest, service: Service) -> WalletResponse:
        return WalletResponse.of(
            service.executor.execute(
                DepositMoneyAction,
                DepositParams(wallet_id=WalletId(wallet_id), amount=body.amount),
            )
        )

    return app`} />

## 9. Example actions

Three shapes, which between them cover almost everything you will write.

```python
class OpenWalletAction(Action[OpenWalletParams, Wallet]):
    """Creates. `plan.add` stages an INSERT and returns the stamped row."""

    def __init__(self, wallets: WalletRepository) -> None:
        self.wallets = wallets

    def perform(self, params: OpenWalletParams) -> Wallet:
        return self.plan.add(
            Wallet.open(
                owner_id=params.owner_id,
                currency=params.currency,
                balance=params.opening_balance,
            )
        )


class DepositMoneyAction(Action[DepositParams, Wallet]):
    """Changes. Read, mutate, stage - and the event goes along with the row."""

    def __init__(self, wallets: WalletRepository) -> None:
        self.wallets = wallets

    def perform(self, params: DepositParams) -> Wallet:
        wallet = self.wallets.get(params.wallet_id)
        return self.plan.update(wallet.deposit(params.amount))


class CloseWalletAction(Action[WalletIdParams, Wallet]):
    """Changes, sometimes. Closing a closed wallet stages nothing and emits nothing -
    and the invocation is still recorded, as one sentinel row."""

    def __init__(self, wallets: WalletRepository) -> None:
        self.wallets = wallets

    def perform(self, params: WalletIdParams) -> Wallet:
        wallet = self.wallets.get(params.wallet_id)
        closed = wallet.close()
        return self.plan.update(closed) if closed is not wallet else wallet
```

That last one is worth pausing on. An action that changes nothing still writes a row to the
outbox, with `event_type` null — so *"this ran and decided there was nothing to do"* is a fact
in the log rather than a silence you cannot distinguish from a crash.

## 10. An example event handler

Two attributes and a method. Register it in `build()` alongside everything else:

```python
class MoneyDepositedEventHandler:
    name = "money-deposited"
    event_type = MoneyDepositedEvent

    def __init__(self, executor: ActionExecutor) -> None:
        self.executor = executor

    def handle(self, envelope: EventEnvelope[MoneyDepositedEvent]) -> None:
        # The recipient is not on the event - a delivery address has no business inside a
        # money-deposited event - so it comes off the action's parameters instead.
        self.executor.execute(
            RaiseAlertAction,
            RaiseAlertParams(
                wallet_id=WalletId(UUID(envelope.model_id)),
                recipient=envelope.action_params["recipient"],
                message=f"deposited {envelope.event.amount}",
            ),
        )
```

The handler takes the **executor**, not a connection: it does its own work as its own unit of
work, with its own transaction and its own outbox rows. The transaction that produced the event
committed and went away before this ran.

## 11. An example distributed job

Periodic work that must run on exactly one instance of the cluster, however many are deployed:

```python
class PayStipendJob(DistributedJob):
    name = "pay-stipend"
    schedule = Schedule.fixed_delay(timedelta(hours=24))

    def __init__(self, wallets: WalletRepository, executor: ActionExecutor) -> None:
        self.wallets = wallets
        self.executor = executor

    def run(self, context: ExecutionContext) -> None:
        for wallet in self.wallets.find_open_below(Decimal("10.00")):
            self.executor.execute(
                DepositMoneyAction,
                DepositParams(wallet_id=wallet.id, amount=Decimal("5.00"), recipient="stipend"),
            )
```

Exclusivity comes from the `scheduled_tasks` row, not from configuration: whichever instance
claims it runs, the rest do not. **The body must still tolerate running twice** — a claim can be
lost to a dead-execution timeout, and then another instance picks the task up.

## 12. A test

```python
with TestClient(create_app(settings)) as client:
    created = client.post("/wallets", json={...}).json()
    client.post(f"/wallets/{created['id']}/deposits", json={"amount": "25.50"})
```

**The `with` matters.** `TestClient` only runs the lifespan inside a context manager, so without
it `app.state.service` is never set and every request fails on the dependency.
