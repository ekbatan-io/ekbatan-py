<SetupPicker />

Everything below follows the picker. Choose your database, your installer and the mode - the
sync API, or `ekbatan.aio` with every database call awaited - and the whole page rewrites
itself; the choice persists across pages. Not sure which mode? [Sync or
async?](/learn/sync-or-async/) takes two minutes.

**Every file on this page is the real file** of an example project that is tested on every
commit, read from it when this site is built, so it cannot drift. Each example exists once per
database, once per installer and once per mode - the picker's *Example* row names the one for
your choices, `fastapi-wallet-rest-uv-pg` to `wallet-service-poetry-async-sqlite` - and each of
those builds its wheel and tests it installed. Copy each file to the path in its header and the
project runs; the steps were checked by doing exactly that, in an empty folder, for every
database, installer and mode.

<div data-db="pg mysql mariadb">

This is a **complete** service: migrations, generated schema, domain, actions, repository,
handler, keyed lock, wiring, HTTP layer, a test and a Makefile.

You need Python 3.13 or later, and Docker: the database in step 2, the schema generator and the
test each run a container.

</div>

<div data-db="sqlite">

On SQLite the service is smaller, and runs with nothing installed but Python 3.13 or later: no
web layer, no migrations, no container. One module set, a hand-written schema, a script that
drives it, and a test.

</div>

## 1. Scaffold a project

<div data-install="uv">

```bash
uv init wallet && cd wallet
```

</div>

<div data-install="pip">

```bash
mkdir -p wallet/src/wallet && cd wallet
touch src/wallet/__init__.py
python3 -m venv .venv && source .venv/bin/activate
```

pip has no scaffold of its own, so the project file is yours to write - setuptools finds the `src/` layout by itself:

<div data-db="pg mysql mariadb">

```toml
# pyproject.toml
[project]
name = "wallet"
version = "0.1.0"
requires-python = ">=3.13"

[build-system]
requires = ["setuptools>=69"]
build-backend = "setuptools.build_meta"

# setuptools packs only .py files unless told: the migrations and the config file ride along here
[tool.setuptools.package-data]
wallet = ["ekbatan.yaml", "migrations/*.sql"]
```

</div>

<div data-db="pg mysql mariadb">

Poetry leaves a gitignored file out of the package, and `schema.py` will be one (below), so name it:

```bash
cat >> pyproject.toml <<'EOF'

[[tool.poetry.include]]
path = "src/wallet/schema.py"
format = ["sdist", "wheel"]
EOF
```

You end with this - the package under `src/`, and everything the service reads at runtime inside
it, so a wheel carries it along with the code:

Two generated files, and the difference between them matters: **`builders.py` is committed**
because it is derived from source you already have; **`schema.py` is gitignored** because it is
derived from a database you have to start. The Makefile in step 7 makes both.

```bash
echo "src/wallet/schema.py" >> .gitignore
```

## 2. Start a database

<div data-db="pg mysql mariadb">

The service connects to it in step 16; the schema generator and the test start throwaway
containers of their own.

</div>

<div data-db="pg">

```bash
docker run --rm -d --name wallet-pg \
  -e POSTGRES_DB=wallet -e POSTGRES_USER=ekbatan -e POSTGRES_PASSWORD=ekbatan \
  -p 5432:5432 postgres:17
```

</div>

<div data-db="mysql">

```bash
docker run --rm -d --name wallet-mysql \
  -e MYSQL_ROOT_PASSWORD=ekbatan -e MYSQL_DATABASE=wallet \
  -p 3306:3306 mysql:8.4
```

</div>

<div data-db="mariadb">

```bash
docker run --rm -d --name wallet-mariadb \
  -e MARIADB_ROOT_PASSWORD=ekbatan -e MARIADB_DATABASE=wallet \
  -p 3306:3306 mariadb:11.4
```

</div>

<div data-db="pg mysql mariadb">

The login matches the defaults in `ekbatan.yaml` (step 4), so the service runs against this
container with nothing set. Elsewhere, set the variables the file names.

</div>

<div data-db="sqlite">

Nothing to start: a SQLite database is a file, made on first use. The script and the test each
point the service at one in a temporary folder.

</div>

`${NAME:default}` is an environment variable with a default, and a missing one with no default
stops startup naming it. YAML, TOML, JSON and INI all work - see
[Config files](/reference/config-files/).

<div data-db="pg mysql mariadb">

**The url names the database and where it is - never the login.** `username` and `password` are
fields of their own, because a url is logged and repeated, and one carrying a password is
refused.

</div>

<div data-db="pg mysql mariadb" data-mode="sync">

**Three pools on one member.** `primaryConfig` is for requests. `jobsConfig` is the scheduler's,
sized at least twice its worker count, because the scheduler heartbeats from a housekeeping
thread and a job body holding the last connection starves it. `lockConfig` holds keyed-lock
leases, one connection each for as long as the lease is held. `app.py` (step 13) builds the last
two with `engine_for` and disposes them.

</div>

<div data-db="pg mysql mariadb" data-mode="async">

**Four pools on one member, one url.** The url names the sync driver; the async side reads it as
"this database" and connects through its async default - asyncpg for PostgreSQL, aiomysql for
MySQL and MariaDB.

- `primaryConfig` - requests, async. It is also the cap on requests waiting on the database:
  past `poolSize` they queue, for at most `poolTimeout` seconds, then fail with a 503.
- `handlersConfig` - the event handler's units of work, async, used only on the loop the handler
  runs on.
- `lockConfig` - keyed-lock leases, async: one connection each for as long as a lease is held.
- `jobsConfig` - sync: the scheduler, and the fan-out and dispatch jobs. At least the job
  workers plus three, because the scheduler heartbeats and a job body holding the last
  connection starves it.

</div>

<div data-db="pg mysql mariadb">

**Every session in UTC, on every pool.** `options: -c TimeZone=UTC` on PostgreSQL,
`time_zone = '+00:00'` in `init_command` on MySQL and MariaDB. The columns hold UTC wall-clock
time; this puts the database's own clock - `NOW()`, a column default - on UTC too, whatever the
server's default zone is. See [Always UTC](/reference/multi-database/#always-utc).

</div>

<div data-db="pg mysql mariadb" data-mode="async">

The same setting reaches the async drivers unchanged: asyncpg receives libpq's `options` as its
own `server_settings`, and aiomysql runs `init_command` as PyMySQL does.

</div>

<div data-db="sqlite">

**One url, no login.** SQLite has neither a server nor users. Handling is switched on under
`local-event-handler`, so the in-process handler runs.

</div>

<div data-db="sqlite" data-mode="async">

The url names no driver: the sync side connects with sqlite3, the async side with aiosqlite,
SQLite's async default.

</div>

**The namespace** is written into every outbox row, which is what lets two applications share
one database without reading each other's events. Change it after the fact and the rows already
written are, correctly, no longer yours.

## 5. Add the migrations

<div data-db="pg mysql mariadb">

Plain SQL files, named `V<version>__<description>.sql` and run in version order - one file per
concern, so each can be read and reviewed on its own. **The framework does not ship its tables as
a bundled migration**: they are your tables, reviewed like every other, and the framework only
says what shape they must have. They are the same in both modes.

|---|---|
| `V0001__eventlog.sql` | the framework's outbox - `events`, and `event_notifications` for the in-process handlers |
| `V0002__scheduled_tasks.sql` | the job scheduler's table; the event handlers run on the scheduler |
| `V0003__wallets.sql` | your domain table |
| `V0004__alerts.sql` | what the deposit handler (step 11) writes |

They were generated once with `emit_ddl` and pasted, rather than built from `schema.py` at
migration time - a migration has to mean the same thing forever:

```python
from sqlalchemy import MetaData

from ekbatan.migrations import emit_ddl
from ekbatan.schema import notifications_table, outbox_table

metadata = MetaData()
outbox_table(metadata)
notifications_table(metadata)
print(emit_ddl(metadata, "postgresql"))  # or "mysql", "mariadb"
```

An applied file is never edited: the migrator records a checksum of each one and refuses to start
when an applied file has changed, been renamed or gone missing. A change goes in the next file.
`app.py` runs them at startup with `migrate(layout, MIGRATIONS)`, before anything opens a pool -
sync in both modes - and the test checks their names without a database through
`validate_scripts`.

</div>

<div data-db="sqlite">

No migrations in this project: the next step's `schema.py` is the whole schema, and `app.py`
builds the tables from it with `create_all` at startup. That is for development only - a real
deployment migrates from files, because `create_all` has no answer for a column that changed. The
server-database setups on this page show how.

</div>

blocks it. The deposit takes an async keyed lock with `try_acquire` - its holder is the request's

here - the sync executor, a sync repository - would block every request at once.

Every row was written in the same transaction as the change it describes. Only the first deposit
is delivered by the time the outbox is printed: a handler subscribes to `MoneyDepositedEvent`, and
nothing subscribes to the opened or closed wallet - an event nobody handles stays undelivered
rather than being thrown away, so a handler added later still finds it. The alert's row and the
second close carry no event at all: they changed nothing that is news, and the unit of work is
recorded anyway.

</div>
