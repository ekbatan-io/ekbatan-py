This is a **complete** service: migrations, generated schema, domain, actions, repository,
handler, job, wiring, HTTP layer, tests and a Makefile. The example named in the picker is this
page as a runnable project.

## 1. Scaffold a project

```
wallet/
├─ Makefile
├─ pyproject.toml
├─ migrations/
│  ├─ env.py
│  └─ versions/0001_initial.py
├─ wallet/
│  ├─ __init__.py
│  ├─ model.py          the domain
│  ├─ builders.py       GENERATED, committed
│  ├─ schema.py         GENERATED, gitignored
│  ├─ actions.py        the units of work
│  ├─ repository.py     the queries this app asks
│  ├─ handlers.py       in-process event handlers
│  ├─ jobs.py           cluster-exclusive background work
│  ├─ app.py            the wiring, all of it
│  └─ api.py            the HTTP layer, and nothing else
└─ tests/
```

Two generated files, and the difference between them matters: **`builders.py` is committed**
because it is derived from source you already have; **`schema.py` is gitignored** because it is
derived from a database you have to start.

## 2. Start a database

Nothing below needs a database until step 5, but the schema generator starts its own throwaway
container and the tests need a real one — so it is worth having PostgreSQL up before you begin.

```bash
docker run --rm -d --name wallet-pg \
  -e POSTGRES_DB=wallet -e POSTGRES_PASSWORD=dev \
  -p 5432:5432 postgres:17
```

MySQL or MariaDB work the same way; only the url in step 3 and the driver extra in step 2
change. SQLite needs no container at all, which is why
[`wallet_service_sqlite`](https://github.com/ekbatan-io/ekbatan-py/tree/main/ekbatan-py-examples/wallet_service_sqlite)
is the example to read first if you only want to see the framework work.

## 4. Configure the DB connection

The framework reads its coordinates from a `ShardingConfig`, built in code rather than bound from
a property file. One shard is still a sharding layout — the single-database case is the
one-member case, which is why going to two databases later changes configuration and nothing
else.

```python
from ekbatan.config import DataSourceConfig, ShardGroupConfig, ShardingConfig, ShardMemberConfig
from ekbatan.persistence import DatabaseRegistry
from ekbatan.sharding import ShardIdentifier

DEFAULT = ShardIdentifier(0, 0)

layout = ShardingConfig(
    default_shard=DEFAULT,
    groups=(
        ShardGroupConfig(group=0, name="global", members=(
            ShardMemberConfig(member=0, name="global", configs={
                "primaryConfig": DataSourceConfig(url=os.environ["DATABASE_URL"], pool_size=20),
            }),
        )),
    ),
)
registry = DatabaseRegistry.from_config(layout)
```

`default_shard` is required: the framework routes there when no sharding strategy commits, and a
layout that cannot answer "where does this go" is rejected at construction rather than at the
first write.

### The url

<div data-db="pg">

```
postgresql+psycopg://user:pass@localhost:5432/wallet
```

`psycopg`, not `psycopg2` — the `postgres` extra brings psycopg 3.

</div>
<div data-db="mysql">

```
mysql+pymysql://user:pass@localhost:3306/wallet
```

</div>
<div data-db="mariadb">

```
mariadb+pymysql://user:pass@localhost:3306/wallet
```

**The scheme has to say `mariadb`.** A MariaDB container hands back a `mysql://` url, and
SQLAlchemy picks its DDL, its version reporting and its `SKIP LOCKED` support off the scheme —
while this framework picks its keyed-lock provider off `engine.dialect.name`. Leave it as `mysql`
and everything works, while running MySQL's code path against a MariaDB server.

</div>
<div data-db="sqlite">

```
sqlite:///wallet.db
```

Fine for one process. Not a production dialect: no `SKIP LOCKED`, so the scheduler and the SQL
keyed lock degrade to single-process behaviour.

</div>

A url naming something unsupported is refused at construction, and the two refusals are
deliberately separate: a url nothing can be read out of is a typo, and a url naming Oracle is a
decision about what this framework supports. They want different fixes.

### The namespace

```python
executor = ActionExecutor(
    namespace="example.wallet",
    registry=registry,
    repositories=repositories,
    actions=actions,
    events=EVENTS,
)
```

Required, and it is a naming root rather than a label. It is written into every `events` and
`event_notifications` row, which is what lets two applications share one database without reading
each other's outbox. Change it after the fact and the rows already written are, correctly, no
longer yours.

### Sizing the pool

| Knob | Default | What it is |
|---|---|---|
| `pool_size` | 10 | connections kept open |
| `max_overflow` | 0 | extra connections allowed under burst, closed when returned |
| `pool_timeout` | 30.0 | seconds a checkout waits before raising |
| `pool_recycle` | 1800 | seconds before a connection is replaced |
| `pool_pre_ping` | True | validate on checkout, to survive a database restart |

`pool_size` and `max_overflow` together are what a Java reader knows as one maximum pool size.
The split is SQLAlchemy's and is left visible rather than papered over, because an operator
tuning a pool needs to see the knobs their own tooling reports on. Start at `pool_size` = your
worker count, and `max_overflow=0` so an overloaded process queues rather than opening
connections a database has not budgeted for.

Every knob refuses rather than clamping. `pool_size=0`, a negative overflow or a non-positive
timeout raise `ValidationError` naming the value, because a knob that silently disables itself is
a knob an operator believes is set.

### One pool, not three

Each shard member carries a **map of named pools**, exactly as Java's does. `"primaryConfig"` is
required and `"secondaryConfig"` optional; any other name is yours. Java's DI modules use it to
hand the job scheduler and the keyed-lock provider pools of their own, so a job storm cannot starve
HTTP requests. Here you do the handing:

```python
ShardMemberConfig(member=0, name="global", configs={
    "primaryConfig": DataSourceConfig(url=url, pool_size=20),
    "jobsConfig":    DataSourceConfig(url=url, pool_size=5),
})
...
jobs_engine = engine_for(layout.groups[0].members[0].config_for("jobsConfig"))
job_registry().engine(jobs_engine)
```

`engine_for` is Java's `ConnectionProvider.hikariConnectionProvider`: the same checks and settings
the registry's own pools get. The registry builds only the primary and secondary, so this one is
yours to dispose. If your jobs are heavy, do this — with no pool of their own, the scheduler's
polling competes with your requests.

`"secondaryConfig"` is the read path: `readonly_db()` uses it and falls back to the primary when a shard
has none. It does not join an open transaction, because a replica has not seen what that
transaction wrote.

## 5. Add a migration

Alembic runs every revision in `migrations/versions/`, in `down_revision` order, and the schema
generator (step 6) replays the same revisions against a throwaway container to discover the
schema. **The framework does not ship its tables as a bundled migration** — you write them, or
copy one verbatim out of any
[`ekbatan-py-examples/*`](https://github.com/ekbatan-io/ekbatan-py/tree/main/ekbatan-py-examples).

That is a deliberate refusal, not an omission. A library that creates its own tables on first
connection decides your schema, your naming and your deploy order for you, and takes them out of
the review that every other table goes through. These are your tables; the framework only tells
you what shape they have to be.

Revisions this guide ends up with:

| Revision | What it is |
|---|---|
| `0001_eventlog` | the framework's outbox tables — `events` and `event_notifications` |
| `0002_scheduled_tasks` | the scheduler's table; the in-process event handlers depend on it |
| `0003_wallets` | your domain tables |

Three revisions rather than one because they change for different reasons and at different
times: the first two move when you upgrade the framework, the third moves whenever your domain
does. Squashing them into one file works, and the first framework upgrade is where you find out
why it was a bad idea.

### 5a. Where the framework's tables live

Nothing forces them into a schema of their own. `outbox_table(metadata)` writes `events` into the
database you are already connected to, next to `wallets`, and the examples all do exactly that.

If you want them separated, say so once, in your own `schema.py`:

```python
EVENTS = outbox_table(metadata, schema="eventlog")
EVENT_NOTIFICATIONS = notifications_table(metadata, schema="eventlog")
```

### 5b. `0001_eventlog` — the framework's outbox tables

Two tables. `events` is the outbox itself; `event_notifications` holds one row per
(event, handler) and is what the in-process dispatcher marks off as it goes. Generate both rather
than typing them:

```python
from sqlalchemy import MetaData
from ekbatan.migrations import emit_ddl
from ekbatan.schema import notifications_table, outbox_table

metadata = MetaData()
outbox_table(metadata)
notifications_table(metadata)

print(emit_ddl(metadata, "postgresql"))    # or "mysql", "mariadb", "sqlite"
```

Two details in that DDL are load-bearing, whichever dialect you are on. `action_params` is **not
null** — every row carries the full input of the unit of work that produced it, so one row is a
complete audit record without a join, and so a consumer can read a value the domain event
deliberately does not carry. And `delivered` is the outbox's only mutable column: it belongs to
the consumer, and a producer that flips it loses the event for every consumer that had not read
it yet. See [`events`](/reference/tables/events/) for every column.

### One statement per `op.execute`

Not for tidiness. PyMySQL executes a single statement per call and rejects a script; psycopg
accepts one. A revision written as one multi-statement block therefore works on PostgreSQL and
fails on MySQL and MariaDB with a syntax error pointing at the second `CREATE TABLE` — which is
the kind of difference that makes these separate example projects rather than one project with a
different url.

Generate, paste, commit. Then edit `schema.py`, regenerate, and paste the *difference* into a new
revision — never make a revision read today's `schema.py`, or it quietly changes meaning every
time a column is added.

### Running them

One call, from the layout you already configured:

```python
from ekbatan.migrations import migrate

migrate(layout, MIGRATIONS)          # before anything opens a pool
```

`migrate` takes the `ShardingConfig` itself rather than a url, so the coordinates are not copied
into a second migration-specific block that can drift from the one the application reads. **This
is the same shape for one database or many.** Here there is one shard, so it runs once; in a
sharded application the same call runs the same revisions against every member's primary, one at
a time and fail-fast — carrying on past a failure turns one broken database into several. It
returns the revision each shard ended on.

Rolling out to a subset is the deliberate act:

```python
migrate(layout, MIGRATIONS, shards=[MEXICO])
```

A coordinate the layout does not contain is refused rather than skipped, because a typo there
would otherwise read as "nothing to do" and migrate nothing at all.

**Before anything opens a pool**, and before the job registry starts — the scheduler writes to
`scheduled_tasks` on its first tick, and a tick that beats the migration fails on a table that
does not exist yet. In `build()` that ordering is just line order; in a stack with lazy
initialisation it is something you have to say out loud.

For development and tests there is a shortcut that skips the files:

```python
migrate_registry(registry, metadata)     # create_all, on every shard
```

Use it in tests. Not in a deployment: `create_all` has no answer for a column that changed.

## 8. Sneak peek — a model and a repository

Four pieces, in the order they depend on each other: the state enum, the events the wallet emits,
the model itself, and the repository.

`WalletState` first, because the model's type signature names it:

```python
class WalletState(StrEnum):
    OPENED = "OPENED"
    CLOSED = "CLOSED"
    DELETED = "DELETED"
```

`DELETED` is not decoration. It is how a soft-deleted row stays readable — `delete()` moves the
state, it does not issue a `DELETE`, so the event that explains the deletion still has a row to
point at.

The events are pure data carriers that say which model they are about: the class line names the
model (`ModelEvent["Wallet"]`), and each is constructed with that model's id. Those fill the
outbox's `model_id` and `model_type` columns.

```python
@dataclass(frozen=True, kw_only=True)
class WalletOpenedEvent(ModelEvent["Wallet"]):
    owner_id: UUID
    currency: str
    opening_balance: Decimal


@dataclass(frozen=True, kw_only=True)
class MoneyDepositedEvent(ModelEvent["Wallet"]):
    amount: Decimal
    new_balance: Decimal
```

Then the model. Frozen, version-tracked, and every state change returns a *new* wallet with its
event already attached:

<CodeBlock filename="wallet/model.py" language="python" shadow="yellow" code={`@dataclass(frozen=True, kw_only=True)
class Wallet(Model[ShardedId["Wallet"], WalletState, WalletBuilder]):
    owner_id: UUID
    currency: str
    balance: Decimal

    @staticmethod
    def open(*, owner_id: UUID, currency: str, opening_balance: Decimal) -> "Wallet":
        wallet_id = ShardedId[Wallet].random()      # the default shard
        return (
            WalletBuilder()
            .id(wallet_id)
            .state(WalletState.OPENED)
            .owner_id(owner_id)
            .currency(currency)
            .balance(opening_balance)
            .with_event(WalletOpenedEvent(model_id=str(wallet_id), owner_id=owner_id,
                                          currency=currency, opening_balance=opening_balance))
            .build()
        )

    def deposit(self, amount: Decimal) -> "Wallet":
        if amount <= 0:
            raise ValidationError(f"deposit amount must be positive, got {amount}")
        new_balance = self.balance + amount
        return (
            self.copy()
            .with_event(MoneyDepositedEvent(model_id=str(self.id), amount=amount, new_balance=new_balance))
            .balance(new_balance)
            .build()
        )`} />

`deposit()` is the only place `MoneyDepositedEvent` is ever attached. That is the whole
discipline: events are produced inside the model, staged inside an action's `perform()`, and
persisted by the framework. A balance cannot exist without the event that explains it, because
there is no other way to change one.

`copy()` returns a builder. Which builder is the third argument on `Wallet`'s class line —
`Model[ShardedId["Wallet"], WalletState, WalletBuilder]` — so a checker sees the real field types,
the one thing Python cannot work out for itself. Leave it out and `copy()` **refuses**, so a missing
builder is an error at the call rather than a checker quietly seeing `__getattr__`.
`python -m ekbatan.codegen` writes the builder; writing one by hand satisfies it just as well.

`balance` is `Decimal`, never `float`. It lands in a `NUMERIC` column, and a float that
round-trips through JSON is no longer the balance.

There is no id class to write. The id is `ShardedId[Wallet]`, spelled as Java spells
`ShardedId<Wallet>`: the model is the type argument, so a checker refuses a `ShardedId[Wallet]`
where an `Id[Order]` belongs. On `Wallet`'s own class line the name is quoted —
`ShardedId["Wallet"]` — because the class does not exist yet at that point.

At runtime the model is erased, as it is in Java: two models' ids holding one uuid compare
equal. The checker is what keeps them apart, so run it. `ShardedId` carries the shard in the
uuid itself, which is what lets you add a second database later — see
[Adding a shard](/learn/sharding/).

And the repository:

```python
class WalletRepository(ModelRepository[Wallet, ShardedId[Wallet]]):
    def __init__(self, registry: DatabaseRegistry) -> None:
        super().__init__(Wallet, WALLETS, registry)

    def find_all_by_owner(self, owner_id: UUID) -> list[Wallet]:
        return self.find_where(WALLETS.c.owner_id == owner_id)
```

That is the whole thing. `get`, `find_where`, `add`, `update`, counting and existence are
inherited, and the mapping between table and dataclass is **by field name** — no `from_row`, no
`to_row`, nothing to keep in step with the model. What you add are the questions your business
actually asks.

`WALLETS` comes from the `schema.py` step 6 generated. That is the chain the whole setup exists
to close: migration → generated schema → repository, with the database as the single source of
truth for all three.

## 9. Wire the service

<CodeBlock filename="wallet/app.py" language="python" shadow="orange" code={`@dataclass(frozen=True, slots=True)
class WalletService:
    registry: DatabaseRegistry
    wallets: WalletRepository
    executor: ActionExecutor
    locks: KeyedLockProvider
    jobs: JobRegistry
    lock_engine: Engine    # built from "lockConfig" - yours to dispose
    jobs_engine: Engine    # built from "jobsConfig" - likewise

    def start(self) -> None:
        self.jobs.start()

    def close(self) -> None:
        # Order matters: stop taking work before closing what the work runs on.
        self.jobs.stop()
        self.locks.close()
        self.lock_engine.dispose()
        self.jobs_engine.dispose()
        self.registry.close()


def build(config: Settings) -> WalletService:
    layout = ShardingConfig(
        default_shard=DEFAULT_SHARD,
        groups=(ShardGroupConfig(group=0, name="global", members=(
            ShardMemberConfig(member=0, name="global", configs={
                "primaryConfig": DataSourceConfig(url=config.url, pool_size=config.pool_size),
                "jobsConfig":    DataSourceConfig(url=config.url, pool_size=config.job_pool_size),
                "lockConfig":    DataSourceConfig(url=config.url, pool_size=config.lock_pool_size),
            }),
        )),),
    )

    if config.run_migrations:
        migrate(layout, MIGRATIONS)          # before anything opens a pool

    registry = DatabaseRegistry.from_config(layout)
    wallets = WalletRepository(registry)

    executor = ActionExecutor(
        namespace="com.example.wallet",
        registry=registry,
        repositories=RepositoryRegistry.builder().with_model_repository(wallets).build(),
        actions=(ActionRegistry.builder()
                 .with_action(OpenWalletAction(clock))
                 .with_action(DepositMoneyAction(wallets, clock))
                 .build()),
        events=EVENTS,
    )

    member = layout.groups[0].members[0]
    lock_engine = engine_for(member.config_for("lockConfig"))
    jobs_engine = engine_for(member.config_for("jobsConfig"))

    handlers = EventHandlerRegistry([MoneyDepositedEventHandler(executor)])
    events_config = LocalEventHandlerConfig(handling=HandlingConfig(enabled=True))

    return WalletService(
        registry=registry,
        wallets=wallets,
        executor=executor,
        locks=PostgresKeyedLockProvider(lock_engine),
        lock_engine=lock_engine,
        jobs_engine=jobs_engine,
        jobs=(job_registry()
              .engine(jobs_engine)
              .with_jobs([
                  EventFanoutJob(registry, handlers, events=EVENTS,
                                 notifications=EVENT_NOTIFICATIONS, config=events_config),
                  EventHandlingJob(registry, handlers,
                                   notifications=EVENT_NOTIFICATIONS, config=events_config),
                  PayStipendJob(executor, wallets),
              ])
              .workers(3)
              .build()),
    )`} />

**Three pools.** Requests get the main engine. Jobs get their own, sized at **at least twice the
worker count**, because the scheduler heartbeats from a housekeeping thread and a job body
holding the last connection starves it — and an execution whose heartbeat stops is declared dead
and run again somewhere else. Locks get a third, because a keyed lock holds its connection for
the life of the lease.

<div data-db="mysql">
Use `MySQLKeyedLockProvider` rather than the PostgreSQL one — and note that a sub-second
`try_acquire` wait is a **poll** on MySQL, which truncates the fraction to zero.
</div>
<div data-db="mariadb">
Use `MariaDBKeyedLockProvider`. It issues the same statements as the MySQL one and exists
separately because MariaDB honours sub-second `GET_LOCK` timeouts where MySQL truncates them.
</div>
<div data-db="sqlite">
SQLite has no advisory locks, so there is no SQLite provider — and no in-process one, as there is
none in Java: a lock in one process's memory excludes nothing in the next worker. If a SQLite
service needs keyed locks, use `RedisKeyedLockProvider`. Optimistic locking on every write needs
nothing and is on regardless.
</div>

## 10. The HTTP layer

<CodeBlock filename="wallet/api.py" language="python" shadow="yellow" code={`def service_of(request: Request) -> WalletService:
    service: WalletService = request.app.state.service
    return service


# MODULE LEVEL. With \`from __future__ import annotations\`, FastAPI resolves string
# annotations against the *module* namespace - an alias defined inside create_app is
# invisible, and the parameter is read as an unfilled query parameter instead. The
# symptom is a 422 on every endpoint, naming a field nobody declared.
Service = Annotated[WalletService, Depends(service_of)]


def create_app(settings: Settings | None = None) -> FastAPI:
    @asynccontextmanager
    async def lifespan(app: FastAPI) -> AsyncIterator[None]:
        service = build(settings or Settings())
        service.start()
        app.state.service = service
        try:
            yield
        finally:
            service.close()

    app = FastAPI(title="Wallet", lifespan=lifespan)

    # A handler must RETURN a response. Raising from inside one is not caught again and
    # becomes a 500 - the opposite of what these exist for.
    @app.exception_handler(StaleRecordError)
    async def _lost_a_race(request: Request, error: Exception) -> JSONResponse:
        return JSONResponse(status_code=409, content={"detail": "the wallet changed; retry"})

    # \`def\`, not \`async def\`. FastAPI runs a plain def in a threadpool, so a blocking
    # database call blocks one worker thread. An async def endpoint runs on the event
    # loop, where the same call stops every request on that worker.
    @app.post("/wallets/{wallet_id}/deposits", response_model=WalletResponse)
    def deposit(wallet_id: UUID, body: DepositRequest, service: Service) -> WalletResponse:
        return WalletResponse.of(
            service.executor.execute(
                DepositMoneyAction,
                DepositParams(wallet_id=ShardedId[Wallet](wallet_id), amount=body.amount),
            )
        )

    return app`} />

## 11. Example actions

Three shapes, which between them cover almost everything you will write.

```python
class OpenWalletAction(Action[OpenWalletParams, Wallet]):
    """Creates. `plan.add` stages an INSERT and hands back the row you gave it."""

    def __init__(self, wallets: WalletRepository, clock: Clock) -> None:
        super().__init__(clock)
        self.wallets = wallets

    def perform(self, principal: str | None, params: OpenWalletParams) -> Wallet:
        return self.plan.add(
            Wallet.open(
                owner_id=params.owner_id,
                currency=params.currency,
                balance=params.opening_balance,
            )
        )


class DepositMoneyAction(Action[DepositParams, Wallet]):
    """Changes. Read, mutate, stage - and the event goes along with the row."""

    def __init__(self, wallets: WalletRepository, clock: Clock) -> None:
        super().__init__(clock)
        self.wallets = wallets

    def perform(self, principal: str | None, params: DepositParams) -> Wallet:
        wallet = self.wallets.get(params.wallet_id)
        return self.plan.update(wallet.deposit(params.amount))


class CloseWalletAction(Action[WalletIdParams, Wallet]):
    """Changes, sometimes. Closing a closed wallet stages nothing and emits nothing -
    and the invocation is still recorded, as one sentinel row."""

    def __init__(self, wallets: WalletRepository, clock: Clock) -> None:
        super().__init__(clock)
        self.wallets = wallets

    def perform(self, principal: str | None, params: WalletIdParams) -> Wallet:
        wallet = self.wallets.get(params.wallet_id)
        closed = wallet.close()
        return self.plan.update(closed) if closed is not wallet else wallet
```

That last one is worth pausing on. An action that changes nothing still writes a row to the
outbox, with `event_type` null — so *"this ran and decided there was nothing to do"* is a fact
in the log rather than a silence you cannot distinguish from a crash.

## 12. An example event handler

With `EventFanoutJob` and `EventHandlingJob` registered — step 9 does both — the framework polls
the outbox, materialises one `event_notifications` row per (event, handler), and invokes your
handlers on a cluster-exclusive worker. Two jobs rather than one because fan-out and delivery
fail for different reasons: a handler that keeps raising retries its own row without re-reading
the outbox.

Two attributes and a method. Register it in `build()` alongside everything else:

```python
class MoneyDepositedEventHandler:
    # Cluster-stable identifier; stored in event_notifications.handler_name.
    name = "money-deposited"
    event_type = MoneyDepositedEvent

    def __init__(self, executor: ActionExecutor) -> None:
        self.executor = executor

    def handle(self, envelope: EventEnvelope[MoneyDepositedEvent]) -> None:
        # The recipient is not on the event - a delivery address has no business inside a
        # money-deposited event - so it comes off the action's parameters instead.
        self.executor.execute(
            RaiseAlertAction,
            RaiseAlertParams(
                wallet_id=ShardedId[Wallet](UUID(envelope.model_id)),
                recipient=envelope.action_params["recipient"],
                message=f"deposited {envelope.event.amount}",
            ),
        )
```

The handler takes the **executor**, not a connection: it does its own work as its own unit of
work, with its own transaction and its own outbox rows. The transaction that produced the event
committed and went away before this ran.

**Delivery is at-least-once.** A handler can run twice — a crash between the work and the row
update leaves the notification unmarked, and it is picked up again. Make the body idempotent:
a unique constraint, an idempotency key, or the event id itself. Rename `name` and every
notification written under the old one is orphaned, so treat it as cluster-stable.

## 13. An example distributed job

Periodic work that must run on exactly one instance of the cluster, however many are deployed:

```python
class PayStipendJob(DistributedJob):
    name = "pay-stipend"
    schedule = Schedule.fixed_delay(timedelta(hours=24))

    def __init__(self, wallets: WalletRepository, executor: ActionExecutor) -> None:
        self.wallets = wallets
        self.executor = executor

    def run(self, context: ExecutionContext) -> None:
        for wallet in self.wallets.find_open_below(Decimal("10.00")):
            self.executor.execute(
                DepositMoneyAction,
                DepositParams(wallet_id=wallet.id, amount=Decimal("5.00"), recipient="stipend"),
            )
```

Exclusivity comes from the `scheduled_tasks` row, not from configuration: whichever instance
claims it runs, the rest do not. **The body must still tolerate running twice** — a claim can be
lost to a dead-execution timeout, and then another instance picks the task up.
