Everything below follows the picker. Choose your database and your installer once and the whole
page rewrites itself; the choice persists across pages.

This is a **complete** service: migrations, generated schema, domain, actions, repository,
handler, job, wiring, HTTP layer, a test and a Makefile. **Every file on this page is the real
file** of an example project that is tested on every commit, read from it when this site is
built, so it cannot drift. Each example exists once per database and once per installer - the
picker's *Example* row names the one for your choices, `fastapi-wallet-rest-uv-pg` to
`fastapi-wallet-rest-poetry-mariadb` - and each of those builds its wheel and tests it installed.
Copy each file to the path in its header and the project runs; the steps were checked by doing
exactly that, in an empty folder, with each installer.

You need Python 3.13 or later, and Docker: the database in step 2, the schema generator and the
test each run a container.

## 1. Scaffold a project

<div data-install="uv">

```bash
uv init wallet && cd wallet
```

</div>
<div data-install="pip">

```bash
mkdir -p wallet/src/wallet && cd wallet
touch src/wallet/__init__.py
python3 -m venv .venv && source .venv/bin/activate
```

pip has no scaffold of its own, so the project file is yours to write - setuptools finds the `src/` layout by itself:

```toml
# pyproject.toml
[project]
name = "wallet"
version = "0.1.0"
requires-python = ">=3.13"

[build-system]
requires = ["setuptools>=69"]
build-backend = "setuptools.build_meta"

# setuptools packs only .py files unless told: the migrations and the config file ride along here
[tool.setuptools.package-data]
wallet = ["ekbatan.yaml", "migrations/*.sql"]
```

</div>
<div data-install="poetry">

```bash
poetry new wallet && cd wallet
```

Poetry leaves a gitignored file out of the package, and `schema.py` will be one (below), so name it:

```bash
cat >> pyproject.toml <<'EOF'

[[tool.poetry.include]]
path = "src/wallet/schema.py"
format = ["sdist", "wheel"]
EOF
```

</div>

You end with this - the package under `src/`, and everything the service reads at runtime inside
it, so a wheel carries the migrations and the config file along with the code:

```
wallet/
├─ Makefile
├─ pyproject.toml
└─ src/wallet/
   ├─ __init__.py
   ├─ ekbatan.yaml          the settings: database, pools, namespace
   ├─ migrations/           the SQL files, run in order at startup
   │  ├─ V0001__eventlog.sql
   │  ├─ V0002__scheduled_tasks.sql
   │  ├─ V0003__wallets.sql
   │  └─ V0004__alerts.sql
   ├─ model.py              the domain
   ├─ builders.py           GENERATED, committed
   ├─ schema.py             GENERATED, gitignored
   ├─ repository.py         the queries this app asks
   ├─ actions.py            the units of work
   ├─ handlers.py           in-process event handlers
   ├─ jobs.py               cluster-exclusive background work
   ├─ app.py                the wiring, all of it
   ├─ api.py                the HTTP layer, and nothing else
   └─ test_wallet.py
```

Two generated files, and the difference between them matters: **`builders.py` is committed**
because it is derived from source you already have; **`schema.py` is gitignored** because it is
derived from a database you have to start. The Makefile in step 7 makes both.

```bash
echo "src/wallet/schema.py" >> .gitignore
```

`${NAME:default}` is an environment variable with a default, and a missing one with no default
stops startup naming it. YAML, TOML, JSON and INI all work - see
[Config files](/reference/config-files/).

**The url names the database and where it is - never the login.** `username` and `password` are
fields of their own, because a url is logged and repeated, and one carrying a password is
refused.

**Three pools on one member.** `primaryConfig` is for requests. `jobsConfig` is the scheduler's,
sized at least twice its worker count, because the scheduler heartbeats from a housekeeping
thread and a job body holding the last connection starves it. `lockConfig` holds keyed-lock
leases, one connection each for as long as the lease is held. `app.py` (step 9) builds the last
two with `engine_for` and disposes them.

**The namespace** is written into every outbox row, which is what lets two applications share
one database without reading each other's events. Change it after the fact and the rows already
written are, correctly, no longer yours.

## 5. Add the migrations

Plain SQL files, named `V<version>__<description>.sql` and run in version order - one file per
concern, so each can be read and reviewed on its own. **The framework does not ship its tables as a bundled
migration**: they are your tables, reviewed like every other, and the framework only says what
shape they must have.

| File | What it is |
|---|---|
| `V0001__eventlog.sql` | the framework's outbox - `events`, and `event_notifications` for the in-process handlers |
| `V0002__scheduled_tasks.sql` | the job scheduler's table; the event handlers run on the scheduler |
| `V0003__wallets.sql` | your domain table |
| `V0004__alerts.sql` | what the deposit handler (step 11) writes |

They were generated once with `emit_ddl` and pasted, rather than built from `schema.py` at
migration time - a migration has to mean the same thing forever:

```python
from sqlalchemy import MetaData

from ekbatan.migrations import emit_ddl
from ekbatan.schema import notifications_table, outbox_table

metadata = MetaData()
outbox_table(metadata)
notifications_table(metadata)
print(emit_ddl(metadata, "postgresql"))  # or "mysql", "mariadb"
```

An applied file is never edited: the migrator records a checksum of each one and refuses to start
when an applied file has changed, been renamed or gone missing. A change goes in the next file.
`app.py` runs them at startup with `migrate(layout, MIGRATIONS)`, before anything opens a pool,
and the test checks their names without a database through `validate_scripts`.

It starts a throwaway container, runs **your** migrations into it, reflects the result and writes a
module of SQLAlchemy `Table` definitions for your repositories to query. On MySQL and MariaDB
the type forcing matters: a uuid is `CHAR(36)` there and nothing in the database says it is one.
You rarely run this by hand; the Makefile does, when a migration changes.

The flags can live in `pyproject.toml` instead, under `[tool.ekbatan.schemagen]` (`migrations`,
`out`, `image`), and the command then runs bare - which is how the example projects do it, and
where forced types, includes and excludes go. See [schemagen](/reference/schemagen/).

## 7. The Makefile

`uv` has no task runner and no dependency graph - nothing that knows `schema.py` comes from the
migrations and rebuilds it when they change. A Makefile is that, in a few lines.

<div data-install="uv">

<div data-db="pg">

```make
IMAGE := postgres:17-alpine
PKG   := src/wallet

$(PKG)/schema.py: $(wildcard $(PKG)/migrations/*.sql)
	uv run python -m ekbatan.schemagen --migrations $(PKG)/migrations --out $@ --image $(IMAGE)

$(PKG)/builders.py: $(PKG)/model.py
	uv run python -m ekbatan.codegen wallet.model --out $@

.PHONY: run test
run:  $(PKG)/schema.py $(PKG)/builders.py ; uv run uvicorn --factory wallet.api:create_app --reload
test: $(PKG)/schema.py $(PKG)/builders.py ; uv run pytest
```

## 8. The model

## 11. An event handler

`schema.py`, `ekbatan.yaml` and the four migrations must all be listed: the service imports the
first and reads the others at startup, and a wheel without them fails there, not here. Each tool
has its own rule, which is why step 1 carries a line for two of them. Checked by building a
wheel with each:

| build tool | a gitignored `schema.py` | the `.yaml` and `.sql` files |
| --- | --- | --- |
| `uv_build` (`uv init`) | packed | packed |
| setuptools (the pip setup above) | packed | only with `[tool.setuptools.package-data]` |
| poetry-core (`poetry new`) | only with `[[tool.poetry.include]]` | packed |
| hatchling | only with `artifacts = ["src/wallet/schema.py"]` under `[tool.hatch.build.targets.wheel]` | packed |
