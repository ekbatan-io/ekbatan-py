ekbatan is useful when a service needs to save a business change and also make that change
available as an event. The event might be handled inside the same service, or it might later be
published to Kafka, Pulsar, RabbitMQ, or another broker.

The examples below use a wallet. A wallet is just an account with a balance. A deposit means
adding money to that balance. The example is small on purpose, so the persistence and event flow
are easy to see.

Read the page in order. It starts with the failure case, then introduces the outbox pattern,
then shows how ekbatan represents the same idea with models, actions, and an executor.

## The golden path

Create ekbatan's objects in your app's startup code and close them in its shutdown code - never
at import time:

- **FastAPI** - in the lifespan.
- **A plain worker** - at the top and the bottom of `main()`.

The objects that hold connections or threads are the database registry (`DatabaseRegistry`, or
`AsyncDatabaseRegistry` in `ekbatan.aio`), the job registry (`JobRegistry`: `start()` and
`stop()`), the keyed lock providers and, for `async def` event handlers, a `HandlerLoop`.
Repositories, the executor and actions hold nothing and are just created. Normal code uses the
sync API; `async def` code uses `ekbatan.aio`.

That is all a deployment has to get right, and ekbatan says so when it is not: one of those
objects created in one process and used in a copy of it raises `ForkedProcessError`, and the sync
API called inside `async def` raises `BlockingCallError`. [Startup and shutdown](/learn/startup-and-shutdown/) has
each object's startup and shutdown call, the lifespan and `main()` written out, and the recipe
for each server.

## 1. The problem

Many event-driven services start with this shape:

```text
request
  -> write row to database
  -> publish event to Kafka / Pulsar / RabbitMQ / ...
```

That looks normal, but it is two writes to two systems. If the database commit succeeds and the
broker publish fails, the database says the business change happened but the event stream never
hears about it. If the broker publish succeeds and the database commit fails, consumers react to
a change that never committed.

That is the dual-write problem.

<GuidedFlow variant="broken" />

If an event must describe committed database state, the event needs to be saved with the
database change. Publishing it as a separate operation can fail independently.

For the full motivation, read [The dual-write trap](/learn/the-dual-write-trap/).

## 2. The first fix

The outbox pattern stores the event in the database first. An outbox is a table of committed
events that can be read and delivered later.

The request flow becomes:

```text
request
  -> one database transaction
       -> write state row
       -> write event row
  -> commit
  -> publish later by reading the event row
```

The database is the transactional boundary. Either the state row and event row both commit, or
neither does.

<GuidedFlow variant="outbox" />

Publishing happens after the database commit by reading the committed event row.

Most teams bolt this on by hand: add a table, remember to write to it in every transaction,
build a poller. It works, and you carry the discipline forever — every new action has to
remember, and every review has to check. The rest of this page is what it looks like when the
framework owns that instead.

For the conceptual version, read [The outbox](/learn/outbox/).

## 3. Where the event comes from

In ekbatan, a domain object that emits events is a `Model`. A domain object is an object from
your business model, such as a wallet, order, or account.

When money is deposited into a wallet, the wallet does not just change its balance. It creates a
new immutable wallet state and attaches a domain event that describes what happened.

```python
@dataclass(frozen=True, kw_only=True)
class Wallet(Model[ShardedId["Wallet"], WalletState, WalletBuilder]):
    ...

    def validate(self) -> None:
        if self.balance < 0:
            raise ValidationError("balance cannot be negative")

    def deposit(self, amount: Decimal) -> Wallet:
        new_balance = self.balance + amount
        return (
            self.copy()
            .with_event(WalletMoneyDepositedEvent(model_id=str(self.id), amount=amount, new_balance=new_balance))
            .balance(new_balance)
            .build()
        )
```

The event is not a Kafka message. It is a domain fact: "money was deposited into this wallet."

The event is created next to the state change, inside the domain model, before any code
publishes anything to a broker. The wallet is a frozen dataclass, so this returns a *new* wallet
and the old one is untouched — which is what makes it impossible for the balance to exist
without the event that explains it.

`validate()` is the wallet's own rules, in one place, and every model must have one. Ekbatan runs
it every time a wallet is made - opened, changed, or read back from the database - so no wallet
with a negative balance can exist.

For the deeper model rules, read [Models and entities](/learn/models-and-entities/).

## 4. What an action does

An `Action` is the unit of business work. A deposit action reads the current wallet, asks the
model for the new wallet, and stages that new wallet on the action's plan. The plan is a
temporary list of objects the executor should persist after `perform()` finishes.

<ModeTabs>
<div slot="sync">

```python
class WalletDepositMoneyAction(Action["WalletDepositMoneyAction.Params", Wallet]):
    def perform(self, principal: str | None, params: Params) -> Wallet:
        wallet = self.wallet_repository.get(params.wallet_id)
        return self.plan.update(wallet.deposit(params.amount))
```

</div>
<div slot="async">

```python
class WalletDepositMoneyAction(AsyncAction["WalletDepositMoneyAction.Params", Wallet]):
    async def perform(self, principal: str | None, params: Params) -> Wallet:
        wallet = await self.wallet_repository.get(params.wallet_id)
        return self.plan.update(wallet.deposit(params.amount))
```

</div>
</ModeTabs>

The important part is what does **not** happen here:

- no manual transaction
- no manual `INSERT INTO events`
- no broker publish
- no second write to remember

The framework comes in two modes: the sync API, and `ekbatan.aio`, where every database call is
awaited. The switch above a sample shows it either way; the choice is remembered on every page.
Only the code that waits on the database differs - here, `async def perform` and `await` on the
read. [Sync or async?](/learn/sync-or-async/) helps you choose.

`perform()` declares intent. It builds the next state and stages it.

`perform()` describes the state change. The executor persists the staged objects and events
atomically.

For the full lifecycle, read [Actions](/learn/actions/).

## 5. What the executor commits

The caller invokes the action through the executor:

<ModeTabs>
<div slot="sync">

```python
wallet = executor.execute(
    WalletDepositMoneyAction,
    WalletDepositMoneyAction.Params(wallet_id=wallet_id, amount=Decimal("25.50")),
)
```

</div>
<div slot="async">

```python
wallet = await executor.execute(
    WalletDepositMoneyAction,
    WalletDepositMoneyAction.Params(wallet_id=wallet_id, amount=Decimal("25.50")),
)
```

</div>
</ModeTabs>

The executor creates a fresh plan, calls `perform()`, and only then opens the transaction that
writes everything:

```text
executor.execute(...)
        |
        v
Action.perform(...)
  - read wallet
  - build updated wallet
  - attach WalletMoneyDepositedEvent
  - plan.update(updated)
        |
        v
one DB transaction
  - UPDATE wallets SET balance = ?, version = ? WHERE id = ? AND version = ?
  - INSERT INTO events
  - commit
```

If the wallet update fails because another request changed the same row first, the transaction
rolls back. If any event row write fails, the wallet row rolls back too.

The outbox guarantee comes from the executor's commit path: the event row is written in the same
transaction as the state row.

For the API details, read [ActionExecutor](/reference/action-executor/).

## 6. What happens after commit

After commit, `events` contains a durable row. From there, you choose how to use it.

```sql
SELECT action_name, model_type, event_type, delivered FROM eventlog.events ORDER BY event_date;
```

| action_name | model_type | event_type | delivered |
| --- | --- | --- | --- |
| `WalletCreateAction` | `Wallet` | `WalletCreatedEvent` | false |
| `WalletDepositMoneyAction` | `Wallet` | `WalletMoneyDepositedEvent` | false |

```text
events
      |
      +--> in-process handler (database-backed, any service instance)
      |
      +--> handler that manually publishes to Kafka / Pulsar / RabbitMQ / ...
      |
      +--> Debezium CDC to a raw broker topic
      |
      +--> CDC raw topic -> router / stream processor -> derived topics
```

All of those paths start from the same committed row. They are downstream of the database
transaction, so they cannot make the original state change partially committed. `delivered` is
how the in-process path marks its own progress; a CDC-only deployment ignores it.

They are also at-least-once delivery paths. A handler or broker consumer can run twice after a
crash or retry. Use idempotency keys, unique constraints, or the outbox event id so duplicate
delivery is harmless.

ekbatan focuses on safely persisting events with state. Publishing and consumption are separate
steps that read from the durable outbox row.

For the practical choices, read [Consuming events](/learn/consuming-events/).

## 7. Where the rest fits

The whole framework grows from the same small model:

- **Two modes**: the sync API and `ekbatan.aio` share every rule, so the guarantees below hold in
  both.
- **Repositories** map immutable dataclasses to rows through the `to_record` / `from_record`
  you write.
- **Models** emit events; **entities** do not.
- **Actions** stage new and changed objects; they never write.
- **The executor** commits staged state and its events together, in one transaction.
- **In-process handlers, CDC, brokers and routers** consume committed outbox rows later.
- **Sharding** routes the same actions across several databases, unchanged.
- **Sagas** coordinate the workflows that should not be forced into one transaction.
- **Distributed jobs** run periodic work on exactly one instance of a cluster.
- **Keyed locks** are the pessimistic tool for when losing a version race is the wrong outcome.

You do not need all of those on day one. The important invariant stays the same:

```text
business state + event row commit together
```
