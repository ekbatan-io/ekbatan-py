This walks through what changes, file by file, for a service you already have. Starting a new
one? Pick **Async** in the [Complete project setup](/learn/complete-project-setup/) and take its files; deciding
whether to? See [Sync or async?](/learn/sync-or-async/). The finished service is the
`fastapi-wallet-rest-uv-async-pg` example (and `fastapi-wallet-rest-uv-async-mysql`, `fastapi-wallet-rest-uv-async-mariadb`), which
passes its own tests; every snippet here is from it. The full reference is
[Native asyncio](/reference/runtime/async/).

## What changes and what does not

| | changes | stays |
| --- | --- | --- |
| model, events, converters, migrations, `schema.py` | | the same files |
| repositories | the async bases; your own queries become `async def` | `to_record` / `from_record`, plain `def` |
| actions on the request path | `AsyncAction`, `async def perform`, awaited reads | what they stage |
| the executor | `AsyncActionExecutor`, awaited | its namespace, retries, cross-shard rule |
| endpoints | `async def`, awaiting | the DTOs, the error mapping |
| the keyed lock | the async provider, `async with` around `await executor.execute(...)` | the key, `max_wait`, `max_hold` |
| event handlers | `async def handle`, awaiting an async executor of their own | name, event type, envelope; run after the action, by dispatch |
| jobs, fan-out, dispatch | | sync, on threads |
| `ekbatan.yaml` | one more pool, for the handler | the urls, the logins, the settings |

## 1. Add the async driver

Beside the sync one: migrations, `schemagen` and the jobs still use it.

```sh
uv add "ekbatan[postgres,postgres-async,migrations]"        # PostgreSQL: asyncpg
uv add "ekbatan[mariadb,mariadb-async,migrations]"          # MariaDB: aiomysql (MySQL: mysql-async)
```

## 2. The repositories

The base class changes and your own queries become `async def`. The mapping stays as it is,
inside the repository: `to_record` and `from_record` are plain `def`, as mapping waits on nothing.

```python
class WalletRepository(AsyncModelRepository[Wallet, WalletsRecord, UUID]):
    def to_record(self, wallet: Wallet) -> WalletsRecord: ...
    def from_record(self, record: WalletsRecord) -> Wallet: ...

    async def find_all_by_owner(self, owner_id: UUID) -> list[Wallet]:
        return await self.find_all_where(WALLETS.c.owner_id == owner_id)

    async def total_balance(self) -> Decimal:
        query = select(func.coalesce(func.sum(WALLETS.c.balance), 0)).where(
            WALLETS.c.state != WalletState.DELETED.name
        )
        total = Decimal(0)
        async for _, conn in self.readonly_dbs():
            total += Decimal(str((await conn.execute(query)).scalar_one()))
        return total
```

The handler writes notifications through the same `NotificationRepository`, built over its own registry.

Every inherited read and write - `get_by_id`, `find_all_where`, `add`, `update`, `count` - is now a
coroutine, and a read across shards asks them all at once.

## 3. The actions

One line changes in each: `perform` is a coroutine, and it awaits its reads.

```python
class WalletDepositMoneyAction(AsyncAction["WalletDepositMoneyAction.Params", Wallet]):
    def __init__(self, clock: Clock, wallet_repository: WalletRepository) -> None:
        super().__init__(clock)
        self.wallet_repository = wallet_repository

    async def perform(self, principal: str | None, params: Params) -> Wallet:
        wallet = await self.wallet_repository.get_by_id(params.wallet_id.value)
        return self.plan.update(wallet.deposit(params.amount))
```

What it stages, and therefore what is committed and which events are written, is unchanged.

## 4. The registries, from one file

The urls in `ekbatan.yaml` keep naming the sync driver. The sync side connects with it; the async
registry reads the same url as naming the database only and connects through its async default.

```python
layout = load_ekbatan_config(config_file).sharding
migrate(layout, MIGRATIONS)                                   # sync, once, at startup

registry = AsyncDatabaseRegistry.from_config(layout)          # requests: asyncpg
executor = (
    AsyncActionExecutor.builder()
    .namespace(ekbatan.namespace)
    .database_registry(registry)
    .repository_registry(RepositoryRegistry([wallet_repository, notification_repository]))
    .action_registry(ActionRegistry([WalletCreateAction(clock), WalletDepositMoneyAction(clock, wallet_repository)]))
    .clock(clock)
    .build()
)

# the lock's leases
lock_data_source = AsyncDataSource.from_config(member.config_for("lockConfig"))
locks = AsyncPostgresKeyedLockProvider.builder().data_source(lock_data_source).build()

handler_loop = HandlerLoop()                                          # where the handler runs
handler_registry = (                                                  # the handler: asyncpg
    AsyncDatabaseRegistry.builder()
    .with_default_database(AsyncTransactionManager(
        layout.default_shard, AsyncDataSource.from_config(member.config_for("handlersConfig"))))
    .build()
)

# what polls: psycopg
jobs_data_source = DataSource.from_config(member.config_for("jobsConfig"))
events_registry = (
    DatabaseRegistry.builder()
    .with_default_database(TransactionManager(layout.default_shard, jobs_data_source))
    .build()
)
```

The handler's executor is an `AsyncActionExecutor` over `handler_registry`, with an async
`CreateNotificationAction`; the handling job is given `handler_loop`, and fan-out and dispatch are built
over `events_registry`. At shutdown: stop the jobs, close the handler's registry on its loop
(`handler_loop.run(handler_registry.aclose())`), close the loop, close `events_registry` - its
manager closes the jobs pool it was given - then the locks and `await lock_data_source.aclose()`,
and last `await registry.aclose()`.

## 5. The settings file

One pool more, for the handler, and the session time zone set the documented way on every pool -
written as libpq spells it, which asyncpg receives as its own `server_settings`:

```yaml
primaryConfig:                     # requests, on ekbatan.aio
  dataSourceProperties:
    application_name: wallet-service
    options: -c TimeZone=UTC
  url: ${WALLET_DATABASE_URL:postgresql+psycopg://localhost:5432/wallet}
  poolSize: 10
  poolTimeout: 5
handlersConfig:                    # the event handler, on its handler loop
  dataSourceProperties:
    options: -c TimeZone=UTC
  url: ${WALLET_DATABASE_URL:postgresql+psycopg://localhost:5432/wallet}
  poolSize: 5
lockConfig:                        # held lock leases, one connection each
  dataSourceProperties:
    options: -c TimeZone=UTC
  url: ${WALLET_DATABASE_URL:postgresql+psycopg://localhost:5432/wallet}
  poolSize: 5
```

On MySQL and MariaDB the same line is `init_command: SET time_zone = '+00:00'`, which PyMySQL
and aiomysql both read.

## 6. The endpoints

`async def`, and `await` every call into the service. The error mapping stays as it is: a
request that waited `poolTimeout` for a connection fails with the same SQLAlchemy `TimeoutError`
in both modes, so the 503 handler is unchanged.

```python
@app.post("/wallets/{wallet_id}/deposits", response_model=WalletResponse)
async def deposit(wallet_id: UUID, body: DepositRequest, service: Service) -> WalletResponse:
    return WalletResponse.of(
        await service.executor.execute(
            WalletDepositMoneyAction,
            WalletDepositMoneyAction.Params(wallet_id=ShardedId[Wallet](wallet_id), amount=body.amount,
                          recipient=body.recipient),
        )
    )
```

Never call the sync API from one of these: it would block the event loop for every request.

## 7. The keyed lock, around the unit of work

The deposit takes the wallet's key around `await executor.execute(...)`, as the sync service
does - with the async provider, whose holder is the request's task:

```python
lease = await service.locks.try_acquire(f"wallet:{wallet_id}", LOCK_WAIT, LOCK_HOLD)
if lease is None:
    raise HTTPException(status_code=503, detail="that wallet is busy; retry",
                        headers={"Retry-After": "1"})
async with lease:
    return WalletResponse.of(await service.executor.execute(WalletDepositMoneyAction, params))
```

A second deposit on the same wallet waits its turn on the event loop, without blocking it, and
then succeeds.

## 7b. The handler

It runs after the deposit has committed - fan-out and dispatch pick the event up on their own
threads - and it may extend `AsyncEventHandler`, with an `async def handle()`. Dispatch runs it on
the handler loop, where it awaits its own executor:

```python
class WalletMoneyDepositedEventHandler(AsyncEventHandler[WalletMoneyDepositedEvent]):
    def __init__(self, executor: AsyncActionExecutor) -> None:
        self.executor = executor

    def name(self) -> str:
        return "wallet-money-deposited-notification"

    def event_type(self) -> type[WalletMoneyDepositedEvent]:
        return WalletMoneyDepositedEvent

    async def handle(self, envelope: EventEnvelope[WalletMoneyDepositedEvent]) -> None:
        await self.executor.execute(CreateNotificationAction, CreateNotificationAction.Params(...))
```

## 8. Run it, with the same cap at the door

```sh
uvicorn fastapi_wallet_rest_async_pg.api:create_app --factory --limit-concurrency 50
```

As in the sync service: the request pool is the cap on work waiting on the database - ten
connections, each request waiting at most `poolTimeout` for one - and `--limit-concurrency` is
the cap before that: past 50 open requests uvicorn answers 503 itself. Keep it a small multiple
of the pool, so a burst waits briefly or is refused quickly.

## 9. Test it

The example's test drives the endpoints with FastAPI's `TestClient`, unchanged. To reach past
HTTP into the service, await on the loop the app runs on:

```python
wallet = client.portal.call(lambda: service.wallet_repository.get_by_id(wallet_id))
```

And an action on its own, without a database:

```python
checked = await AsyncActionSpec.of(WalletDepositMoneyAction(clock, wallet_repository)).execute(params)
checked.assert_updated(Wallet, lambda w: w.balance == Decimal("150.00"))
```
