## How to choose

Pick **async** when the service is an asyncio app - FastAPI or Starlette with `async def`
endpoints - and many requests wait on the database at the same time. Under load it does about
one and a half times the work of the same service on threads, and most requests wait less.

Pick **sync** when:

- the server is threaded (gunicorn, a worker loop), or your FastAPI endpoints are plain `def` -
  FastAPI already runs those on a thread;
- the service is mostly event handlers and jobs;
- you have no reason to change. Threads are fine for database work: Python lets other threads
  run while one waits on the database.

A lone request is a little faster on sync. The numbers are on
[Native asyncio](/reference/runtime/async/#when-to-use-it).

Do not mix them on one request path. Never call the sync API from inside an `async def`: it
blocks the event loop, and every request with it.

## What is the same in both modes

- models, entities, events, ids, the `ActionPlan` - the same classes, the same files;
- what an action stages, and what the executor writes: one transaction holding the rows and
  their events;
- the optimistic lock, soft delete, retries, sharding and the cross-shard rule - the same code;
- the tables, the migrations, the generated `schema.py` and `ekbatan.yaml` - one config file
  serves both;
- `ActionRegistry`, `RepositoryRegistry`, `ExecutionConfiguration`, config and config files;
- the keyed locks hold the same keys, so a sync service and an async one contend for one lock;
- handlers run after the action has committed, never inside it, at least once.

## What differs

| | sync | async |
| --- | --- | --- |
| install | `ekbatan[postgres]` | `ekbatan[postgres,postgres-async]` - the async extra beside the sync one |
| registry | `DatabaseRegistry` | `AsyncDatabaseRegistry` |
| repositories | `ModelRepository`, `EntityRepository` | `AsyncModelRepository`, `AsyncEntityRepository`; every read and write is awaited |
| actions | `Action`, `def perform` | `AsyncAction`, `async def perform` |
| executor | `ActionExecutor`, `executor.execute(...)` | `AsyncActionExecutor`, `await executor.execute(...)` |
| transaction | `with registry.default.transaction():` | `async with registry.default.transaction():` |
| keyed lock | `ekbatan.locks`, `with locks.acquire(...)` | `ekbatan.aio.locks`, `async with locks.acquire(...)` |
| event handler | `def handle` | `async def handle`, awaiting an executor of its own |
| testing | `ActionSpec`, `run_action` | `AsyncActionSpec`, `async_run_action` |
| shutdown | `registry.close()` | `await registry.aclose()` |

`to_record` and `from_record` stay plain `def` in both: mapping waits on nothing.

## What always runs on threads

Some work is sync in both modes. An async service builds a sync `DatabaseRegistry` beside its
async one, from the same `ekbatan.yaml`, for it:

- **the event jobs** - the two background jobs that read the outbox and call your handlers
  ([Consuming events](/learn/consuming-events/), later in this path). The handlers themselves
  may be sync or async;
- **distributed jobs** - their `execute` is a plain `def`, run on the scheduler's threads. The
  *work* inside one may still be async -
  [a job whose work is async](/reference/runtime/async/#a-job-whose-work-is-async);
- **migrations** - run once at startup, before any pool opens;
- **schemagen** and **codegen** - build steps, not part of the running service.

So an async service keeps the sync driver installed too: these use it.
