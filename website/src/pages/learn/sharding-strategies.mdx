[Adding a shard](/learn/sharding/) is the mechanics. This is the model underneath it.

## Two reasons to shard, two axes

Most sharding designs use one number for "which database does this row live on" and let it
conflate everything. A `ShardIdentifier` is a `(group, member)` pair, and the two answer
different questions:

| axis | the question | cardinality driven by | range |
| --- | --- | --- | --- |
| **group** (policy) | where is this data *allowed* to live? | data residency law, tenant isolation, business-domain separation. **You do not pick how many you have; the world picks** | 8 bits → 256 |
| **member** (capacity) | how many writes per second can one database take? | capacity planning. You add members when one starts to fall over | 6 bits → 64 per group |

The split matters because the two have completely different operational profiles. A new
**group** — "we signed a bank that requires onshore data" — is a major event: new
infrastructure, new region, new compliance posture, a separate failure domain. A new **member**
is routine: same region, same VPC, same playbook, more compute.

Conflating them into "shard #47" forces every routing decision through one lens. Routing for
compliance is deterministic from the customer's properties; routing for capacity is whatever
distributes load, usually a hash.

## Three strategies, in order of weight

### One database (no sharding)

Everything at `DEFAULT_SHARD`. You write actions exactly as if sharding did not exist — the
registry is still in the path, and every call resolves to the same database.

```python
registry = DatabaseRegistry.from_config(ShardingConfig.single(url))
```

Nothing opts in, and nothing costs anything: a repository with no strategy uses
`NoShardingStrategy`, which resolves every key to the default shard. Its scatter accessors visit
only that shard too, so a repository that opted out cannot wander onto a sibling's databases.

> Use it until you have a write-throughput problem or a policy forcing data location — which is
> almost everyone. Stay here as long as you can.

### Shard bits in the id (`EmbeddedBitsShardingStrategy`)

The shard pair is encoded into the UUID itself, so the shard is recoverable from the id with no
lookup and no extra column. Chosen at creation, and bonded to the row for its life.

```python
class WalletId(ShardedId["Wallet"]):
    pass


wallet_id = WalletId.generate(ShardIdentifier(group=1, member=0))
```

The layout is a cross-language contract: the same bits, in the same places, so a Java service
and a Python one reading the same id agree about where the row lives.

> Use it when each row's shard is decidable from what you know at creation and you will never
> move rows between shards. That covers most cases.

### Your own strategy

If you need to re-shard live data, or the shard is not knowable at creation but is derivable
from the row, supply a `ShardingStrategy` and override `shard_for` on the repository.

The cost is that the id stops being self-describing: any read starting from an id alone needs
the strategy to find the row first, which is a round trip you pay implicitly on every lookup. A
repository whose strategy cannot resolve a shard from an id says so at construction rather than
failing on the first read.

## Why cross-shard is refused

By default an action's staged changes must all route to one shard. One transaction, everything
written, commit. **That is the only way the outbox guarantee survives**, because
atomic-across-databases does not exist.

With `allow_cross_shard=True` the executor opens **one transaction per shard**, each committing
independently. A failure rolls back only its own shard; shards that already committed stay
committed, and the framework logs that loudly, naming them.

So you are back in [dual-write](/learn/the-dual-write-trap/) territory for that action — except
the two systems are now two shards of your own database rather than a database and a broker.
The mitigation is a [saga](/learn/sagas/): one action per shard, chained by outbox events, with
compensation.

Prefer opting in **per call**, so the risk is visible at the call site rather than buried in a
builder somewhere.

## What sharding does not solve

- **Cross-shard transactions.** No framework can; that is a property of distributed systems.
- **Scatter-gather latency.** A predicate across N members hits N databases, and here they are
  visited sequentially, so it is the sum rather than the max.
- **Hot shards.** If 80% of traffic targets one customer, that customer's shard is hot however
  many others exist.

If you are reaching for sharding to fix a *read latency* problem, it is probably the wrong tool.
