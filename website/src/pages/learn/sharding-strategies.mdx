[Adding a shard](/learn/sharding/) is the mechanics. This is the model underneath it.

## Two reasons to shard, two axes

Most sharding designs use one number for "which database does this row live on", and make it
answer two different questions at once. A `ShardIdentifier` is a `(group, member)` pair, and the two answer
different questions:

| axis | the question | what decides how many | range |
| --- | --- | --- | --- |
| **group** (policy) | where is this data *allowed* to live? | data residency law, tenant isolation, business-domain separation. **You do not pick how many you have; the world picks** | 8 bits → 256 |
| **member** (capacity) | how many writes per second can one database take? | capacity planning. You add members when one starts to fall over | 6 bits → 64 per group |

The split matters because the two have completely different operational profiles. A new **group** — "we signed a bank that requires its data to stay in the country" — is a major
event: new infrastructure, a new region, new compliance rules, something that can fail on its
own. A new **member** is routine: the same region, the same network, the same procedures, more
machines.

Folding both into one "shard #47" forces every routing decision through one lens. Routing for
compliance is deterministic from the customer's properties; routing for capacity is whatever
distributes load, usually a hash.

## Three strategies, in order of weight

### Single-database (no sharding)

Everything at `DEFAULT_SHARD`. You write actions exactly as if sharding did not exist — the
registry is still in the path, and every call resolves to the same database.

<ModeTabs>
<div slot="sync">

```python
registry = DatabaseRegistry.from_config(ShardingConfig.single(url))
```

</div>
<div slot="async">

```python
registry = AsyncDatabaseRegistry.from_config(ShardingConfig.single(url))
```

</div>
</ModeTabs>

Nothing opts in, and nothing costs anything: a repository with no strategy uses
`NoShardingStrategy`, which resolves every key to the default shard. Its searches across shards look only at that one too, so a repository without sharding never
reads another repository's databases.

> Use it until you have a write-throughput problem or a policy forcing data location — which is
> almost everyone. Stay here as long as you can.

### Embedded-bits UUID (`EmbeddedBitsShardingStrategy`)

The shard pair is encoded into the UUID itself, so the shard is recoverable from the id with no
lookup and no extra column. It is chosen when the row is created, and stays with the row for its whole life.

```python

wallet_id = ShardedId[Wallet].generate(ShardIdentifier(group=1, member=0))
```

When a request arrives carrying a wallet id, the framework reads the shard bits out of it,
finds the matching database in the registry, and opens the transaction there. No round trip to
a directory service, and no sticky session at the load balancer — the id is self-describing.

The shard is chosen **at creation time**: your create action calls `ShardedId[Wallet].generate(shard)`,
and from then on the id and its shard stay together for the row's whole life. Choosing it is your
call — typically the create action maps something you already know (tenant, region, regulatory
class) onto a shard.

The layout is fixed - the same bits, in the same places - so every service reading the id agrees
about where the row lives, including a Java service reading the id in an event
([Running beside a Java service](/reference/beside-java/#ids)).

> Use it when each row's shard is decidable from what you know at creation and you will never
> move rows between shards. That covers most cases.

### Custom sharding strategy (full control)

If embedded bits do not fit — you need to re-shard live data, or the shard is not knowable at
creation but is derivable from the row's columns — supply a `ShardingStrategy` of your own. It
takes a model or a key and returns a `ShardIdentifier`, and the framework calls it once per
persistence operation, before the transaction opens.

> **Use it when** the routing is more dynamic than "fixed at creation": hash-based rebalancing,
> time-window routing, hot-key detection.

The cost is that **the id stops being self-describing.** Any read that starts from an id alone —
`wallet_repository.get_by_id(wallet_id)` — needs the strategy to find the row before it knows which database to
look in, and that is a round trip you pay implicitly on every lookup. Use embedded bits if you
can; reach for this when you cannot.

A strategy declares whether its ids are shard-aware. One that says no is fine in itself — it
just has to route from something other than the id — but the moment an id-only path like
`get_by_id(id)` is called on it, the repository raises `UnsupportedError` naming the strategy and
telling you to override `shard_for()`. It is refused rather than guessed at, because guessing
here means reading the right row from the wrong database and finding nothing.

## Cross-shard actions: one transaction per shard, never atomic across

By default an action's staged changes must all route to one shard. One transaction, everything
written, commit. **That is the only way the outbox guarantee survives**, because
atomic-across-databases does not exist.

With `allow_cross_shard=True` the executor groups the staged changes by shard and opens **one
transaction per shard**, in deterministic order, rolling each back independently on failure.
Shards that already committed stay committed, and the framework logs that loudly, naming them.

<ModeTabs>
<div slot="sync">

```python
executor.execute(
    None,
    TransferAction,
    params,
    config=ExecutionConfiguration(allow_cross_shard=True),
)
```

</div>
<div slot="async">

```python
await executor.execute(
    None,
    TransferAction,
    params,
    config=ExecutionConfiguration(allow_cross_shard=True),
)
```

</div>
</ModeTabs>

Prefer opting in on one explicit call. Setting it as an executor-wide default should be
reserved for a dedicated executor whose actions are *all* designed for per-shard commits and
eventual consistency.

That buys cross-shard workflows — a wallet-to-wallet transfer whose two wallets live on
different shards — at two prices:

- **Per-shard atomicity, not global atomicity.** Shard A can commit while shard B rolls back.
- **No cross-shard reads inside one transaction.** A join across shards happens in application
  code, after each shard's transaction has committed.

So you are back in [dual-write](/learn/the-dual-write-trap/) territory for that action — except
the two systems are now two shards of your own database rather than a database and a broker.
The mitigation is a [saga](/learn/sagas/): one action per shard, chained by outbox events, with
compensation.

The good news is that most actions need none of this. Routing customers to the same shard as
their wallets, and orders to the same shard as their customer, removes most cross-shard
pressure for free.

## What sharding doesn't solve

- **Cross-shard transactions.** No framework can; that is a property of distributed systems.
- **Searches across shards.** A search by anything but the id asks all N members. In sync mode they
  are visited one after another, so it is the sum; in async mode they are asked at the same
  time, so it is the slowest one.
- **Hot shards.** If 80% of traffic targets one customer, that customer's shard is hot however
  many others exist.

Sharding is a **write-throughput-and-policy** tool. Pre-splitting a hot tenant across several
members in a group of its own is a separate technique, and the one that actually answers the
third bullet.

If you are reaching for sharding to fix a *read latency* problem, it is probably the wrong tool:
caching, read replicas and precomputed read tables are the usual right answers, and none of them
costs you cross-shard transactions.
