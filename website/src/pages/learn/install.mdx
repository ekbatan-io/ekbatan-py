## What you need

**Python 3.13 or newer**, and a database: PostgreSQL, MySQL or MariaDB.

SQLite works, in both modes, and the test suite runs on it, but it is not a supported production
dialect — it has no `SKIP LOCKED`, so the job scheduler degrades to behaviour that is fine for one
process and wrong for a cluster, and it has no keyed lock of its own (use the Redis one).

## Install

<ModeTabs>
<div slot="sync">

```bash
uv add "ekbatan[postgres]"
```

</div>
<div slot="async">

```bash
# the async extra sits beside the sync one: migrations, schemagen and the jobs use it
uv add "ekbatan[postgres,postgres-async]"
```

</div>
</ModeTabs>

Everything optional is an extra, and nothing you do not name is installed. Async mode adds one
extra per database; see [Sync or async?](/learn/sync-or-async/) for choosing:

| extra | brings | when |
|---|---|---|
| `postgres` | psycopg 3 | your dialect |
| `mysql`, `mariadb` | PyMySQL | your dialect |
| `postgres-async` | asyncpg | the async API, `ekbatan.aio`, on PostgreSQL - beside `postgres` |
| `mysql-async`, `mariadb-async` | aiomysql | `ekbatan.aio` on MySQL or MariaDB - beside the sync extra |
| `sqlite-async` | aiosqlite | `ekbatan.aio` on SQLite |
| `migrations` | yoyo | you want SQL migrations run across every shard |
| `redis` | redis-py | the Redis keyed lock rather than the SQL one |
| `avro` | fastavro | reading the [event stream](/reference/events/streaming/#reading-avro-and-protobuf) in Avro |
| `protobuf` | protobuf | reading the [event stream](/reference/events/streaming/#reading-avro-and-protobuf) in Protobuf |
| `codegen` | testcontainers | **development only** — see below |

`SQLAlchemy` and `ekbatan-py-db-scheduler` come unconditionally.

`codegen` belongs in the dev group, not the runtime dependencies. It starts a database
container to reflect your schema — a thing your build does and your deployment must never do:

```bash
uv add --dev "ekbatan[codegen]"
```

That is the whole of the setup. There is no plugin to register, no build step to hook into and
no flag to remember: Python knows a function's parameter names and a dataclass's fields at
runtime, so the framework reads them from your classes as they are.

## The two generators

One is committed, one is not, and the difference is what each is derived from.

**Typed builders — committed.**

```bash
uv run python -m ekbatan.codegen myapp.model --out myapp/builders.py
```

`wallet.copy().balance(...)` works with nothing generated. What it cannot do is tell a *type
checker* that `.balance(...)` takes a `Decimal` — the setters resolve by name at runtime, so a
checker sees only `__getattr__`. That is the one thing worth generating, and the only thing
this generates. Commit the output: it is derived from source you already have.

**Table definitions — gitignored.**

```toml
# pyproject.toml
[tool.ekbatan.schemagen]
migrations = "migrations"
out = "myapp/schema.py"
image = "postgres:17-alpine"
```

```
uv run python -m ekbatan.schemagen
```

Starts a throwaway container, runs **your** migrations into it, reflects the result. Forced
types, includes and excludes go in the same table - see [schemagen](/reference/schemagen/). The
output is gitignored because it is derived from a database you have to start, and it is
rebuilt whenever the migrations change.

**Gitignored is not left out of the package - check that it is not.** Some build tools leave a
gitignored file out of the wheel: poetry-core and hatchling drop `schema.py` unless told to keep
it, while `uv_build` keeps it. The wheel then imports a module it does not contain, and fails at
startup. [Complete project setup](/learn/complete-project-setup/) has the one line each tool needs, and a command that lists what
a wheel holds.

## A Makefile, because uv has no task runner

`uv` manages dependencies and runs commands. What it does not have is a **dependency graph**:
something that knows `schema.py` comes from `migrations/` and rebuilds it when they change.

```make
myapp/schema.py: $(wildcard migrations/*.sql) pyproject.toml
	uv run python -m ekbatan.schemagen

lint: myapp/schema.py
	uv run mypy
```

The dependency on the migration files is what makes this bearable in front of every other
target: **it starts a container when they change and does nothing when they have not.**

`lint` depends on it because mypy reads the generated module — a fresh clone would otherwise
report `cannot find implementation for module myapp.schema`, which is true and unhelpful.
