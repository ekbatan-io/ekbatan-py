# wallet-service-poetry-sqlite

A wallet, end to end, in about two hundred lines. Runs on SQLite so you can try it now:

<!-- build: written by scripts/sync-examples.py -->
```
make run        # run it
make            # test the built wheel, installed
```

Built with **Poetry**. The same project with [uv](../wallet-service-uv-sqlite) and [pip and setuptools](../wallet-service-pip-sqlite) differs only in `pyproject.toml`, `Makefile` and `.gitignore`.

Needs `poetry` 2 on the path.
<!-- /build -->

It starts the jobs, creates a wallet, deposits into it, waits while the in-process handler
reacts to the deposit by writing a notification, runs a scheduled job, and prints the outbox so
you can see what a consumer would read. Nobody calls the handler: the fan-out and handling jobs
run in the background, as in any service, switched on by `local-event-handler.handling.enabled`
in `ekbatan.yaml`.

## What to look at, in order

**`model.py`** - `Wallet.deposit`. Five lines, one of which says what happened. No transaction,
no flush, no publish, no outbox. That is the whole argument for the framework.

**`actions.py`** - `DepositMoneyAction.perform`. Three lines: read, change, stage. The executor turns
that into one transaction holding the row and its event.

**`handlers.py`** - `MoneyDepositedEventHandler`. Reacts to a committed event by starting another unit of
work. It reads the recipient off the producing action's parameters rather than the event,
because a delivery address has no business inside a money-deposited event.

**`jobs.py`** - `PayStipendJob`. The same actions, on a schedule, one instance across a cluster.
A daily job is due the moment it is registered, so it runs once at startup; `start()` waits for
that run, so a wallet opened afterwards is not paid by surprise.

**`repository.py`** - `WalletRepository`. Where a query that means something to the business
lives, and where the sharding strategy is named. `to_record` and `from_record` name every column,
each conversion a decision about how a value is stored, and both are typed by the table's
record - `WalletsRecord`, written by hand in `schema.py` beside `WALLETS` - so mypy catches a
column left out, misspelt or given the wrong type.

**`builders.py`** - generated by `python -m ekbatan.codegen`, and the only generated file. It
exists so a type checker can see that `.balance(...)` takes a `Decimal`; everything else the
builder does needs no generation.

**`app.py`** - the wiring, all of it in one place, away from everything above.

**`ekbatan.yaml`** - the database, the namespace and the handling switch, in the same keys as
the Java examples' `application.yml`. The url is `${WALLET_DATABASE_URL:...}`; the script and
the test point it at a temporary file.

## What it does not show

That state and its events commit together even when the process dies mid-write. That is the
guarantee the whole design exists for, and no example can demonstrate it - only a test can, and
the framework has them.
