# wallet-service-uv-async-sqlite

The async twin of [`wallet-service-uv-sqlite`](../wallet-service-uv-sqlite): the same wallet, end to end,
with every unit of work awaited on `ekbatan.aio`. Runs on SQLite, through aiosqlite, so you can
try it now:

<!-- build: written by scripts/sync-examples.py -->
```
make run        # run it
make            # test the built wheel, installed
```

Built with **uv**. The same project with [pip and setuptools](../wallet-service-pip-async-sqlite) and [Poetry](../wallet-service-poetry-async-sqlite) differs only in `pyproject.toml`, `Makefile` and `.gitignore`.
<!-- /build -->

It starts the jobs, creates a wallet, deposits into it, waits while the in-process handler
reacts to the deposit by writing a notification, runs a scheduled job, and prints the outbox so
you can see what a consumer would read. Nobody calls the handler: the fan-out and handling jobs run in the
background, on threads, as in any service, switched on by `local-event-handler.handling.enabled`
in `ekbatan.yaml`.

## What to look at, in order

**`model.py`** - `Wallet.deposit`. Five lines, one of which says what happened. No transaction,
no flush, no publish, no outbox. That is the whole argument for the framework.

**`actions.py`** - `DepositMoneyAction.perform`. Three lines: read (awaited), change, stage. The
executor turns that into one transaction holding the row and its event.

**`handlers.py`** - `MoneyDepositedEventHandler`. Reacts to a committed event by starting another unit of
work, awaited. It reads the recipient off the producing action's parameters rather than the
event, because a delivery address has no business inside a money-deposited event.

**`jobs.py`** - `PayStipendJob`. The same actions, on a schedule, one instance across a cluster;
its work awaited on the handler loop. A daily job is due the moment it is registered, so it runs
once at startup; `start()` waits for that run, so a wallet opened afterwards is not paid by
surprise.

**`repository.py`** - `WalletRepository`. Where a query that means something to the business
lives, and where the sharding strategy is named. `to_record` and `from_record` name every column,
each conversion a decision about how a value is stored, and both are typed by the table's
record - `WalletsRecord`, written by hand in `schema.py` beside `WALLETS` - so mypy catches a
column left out, misspelt or given the wrong type.

**`builders.py`** - generated by `python -m ekbatan.codegen`, and the only generated file. It
exists so a type checker can see that `.balance(...)` takes a `Decimal`; everything else the
builder does needs no generation.

**`app.py`** - the wiring, all of it in one place, away from everything above.

**`ekbatan.yaml`** - the database, the namespace and the handling switch. The url is
`${WALLET_DATABASE_URL:...}`; the script and the test point it at a temporary file.

## What is the same as the sync twin

`model.py` and `schema.py`, byte for byte. The rows each unit of work writes, the events in the
outbox, the optimistic lock, soft delete and the handler's at-least-once delivery mean the same
thing in both modes - they are the same code.

## What is different

**`actions.py`** - `AsyncAction`, and `perform` is `async def`: it awaits its reads. What it
stages is the same.

**`repository.py`** - the repositories extend `AsyncModelRepository` and
`AsyncEntityRepository`, and every query of their own is `async def`. `to_record` and
`from_record` stay plain functions, written in each repository as in the sync twin.

**`handlers.py`** - `MoneyDepositedEventHandler.handle` is `async def` and awaits an executor of
its own. It still runs after the deposit has committed, never inside it: dispatch runs it on
its handler loop, one event loop on a thread of its own.

**`jobs.py`** - the daily stipend is still a sync job: db-scheduler claims its row and calls
`execute` on one of its threads. Its work is a coroutine, handed to the handler loop with
`loop.run(...)`, where it awaits the handler's executor and repository.

**`app.py`** - an `AsyncDatabaseRegistry` and an `AsyncActionExecutor` for the units of work; a
second async registry and executor for the handler and the stipend's work, used only on the
handler loop; and a sync `DatabaseRegistry` for what polls - db-scheduler, fan-out, dispatch and
the stipend - built from the same `ekbatan.yaml`. `start()` is awaited and returns once the
stipend's first run is over; `aclose()` closes everything in order.

**`__main__.py`** - the narration is a coroutine, run with `asyncio.run`.

## What it leaves out

Keyed locks: neither twin takes one. SQLite has no advisory locks, so there is no keyed lock
provider for it, sync or async; a service on SQLite that needs one uses the Redis provider
(`ekbatan.aio.locks.redis.AsyncRedisKeyedLockProvider` here). The server-database examples take
one around the deposit.

## What it does not show

That state and its events commit together even when the process dies mid-write. That is the
guarantee the whole design exists for, and no example can demonstrate it - only a test can, and
the framework has them.
